# Phase: Analyze

수집된 리뷰를 하나씩 검토하고, 수정 여부를 분류하는 페이즈.

## 입력

- fetch 페이즈에서 수집한 리뷰 데이터
- `docs/review-decisions.md`: 이전에 결정된 트레이드오프 기록

## 절차

### 1. 기존 결정 로드

`docs/review-decisions.md`를 읽어 이전에 결정된 트레이드오프를 확인한다.
각 결정의 `keywords` 필드를 기준으로 새 리뷰와 매칭한다.

### 2. 리뷰 항목별 검토

각 리뷰 항목에 대해:

1. **대상 코드 확인**: 리뷰가 지적하는 파일/라인을 Read로 확인
2. **기존 결정 매칭**: `docs/review-decisions.md`에서 키워드가 일치하는 기존 결정이 있는지 확인
   - 일치하면: `ALREADY_DECIDED`로 분류하고 기존 결정을 참조
3. **코드 대조 분석**: 리뷰 제안이 현재 코드에 적합한지 판단
4. **분류**: 아래 카테고리 중 하나로 분류

### 3. 분류 카테고리

| 카테고리 | 의미 | 후속 액션 |
|----------|------|----------|
| **AGREE** | 수정 필요 | plan 페이즈에서 계획 작성 |
| **TRADEOFF** | 이견 있음, 개발자 판단 필요 | 사유를 설명하고 개발자에게 확인 |
| **ALREADY_DECIDED** | 이전에 결정된 사안의 반복 지적 | 자동 skip, 요약만 보고 |
| **NOT_APPLICABLE** | pg-simulator 등 현재 범위 밖 | skip |

### 4. 분류 기준

**AGREE로 분류하는 경우:**
- 버그 가능성이 있는 코드 지적
- 누락된 검증/방어 로직
- 성능 개선 (인덱스, 쿼리 최적화)
- 테스트 커버리지 부족
- 로깅/관측성 개선
- 보안 취약점

**TRADEOFF로 분류하는 경우:**
- 우리가 의도적으로 선택한 설계 방향과 충돌
- 이전 라운드에서 반영한 수정을 되돌리라는 제안
- 현재 프로젝트 단계(학습/시뮬레이터)에서 과도한 제안
- 두 가지 모두 합리적인 대안이 있는 경우

**ALREADY_DECIDED로 분류하는 경우:**
- `docs/review-decisions.md`에 동일한 주제의 결정이 존재
- 이전 리뷰 라운드에서 이미 논의되고 기각된 사안

### 5. 결과 보고 형식

```markdown
## 리뷰 분석 결과

### AGREE — 수정 필요 (N건)
| # | 파일 | 내용 | 심각도 |
|---|------|------|--------|
| 1 | ... | ... | ... |

### TRADEOFF — 이견/논의 필요 (N건)
각 항목에 대해:
- **리뷰 요지**: ...
- **현재 코드**: ...
- **우리 판단**: ...
- **근거**: ...

### ALREADY_DECIDED — 이전 결정 반복 (N건)
| # | 파일 | 기존 결정 ID | 요약 |
|---|------|-------------|------|

### NOT_APPLICABLE — 범위 밖 (N건)
| # | 파일 | 사유 |
|---|------|------|
```

### 6. review-summary.md 작성

분류 결과를 프로젝트 루트의 `review-summary.md`에 기록한다.
개발자가 파일을 보고 TRADEOFF 판단을 내릴 수 있도록 체크박스를 포함한다.

**기존 파일이 있으면 덮어쓴다** (PR별 문서이므로 이전 내용은 불필요).

**형식:**
```markdown
# PR #{number} Review Summary — {제목}

> 분석 일시: {날짜}
> 리뷰어: {리뷰어 목록}
> 총 항목: {N}건

## 집계
| 분류 | 건수 | 비율 |
|------|------|------|

## AGREE — 수정 필요 (N건)
| # | 파일 | 요약 | 근거 |
|---|------|------|------|

## TRADEOFF — 판단 필요 (N건)
TRADEOFF 항목은 유사 주제끼리 그룹으로 묶어 제시한다.
각 그룹에 **판단 포인트**와 체크박스(`[ ] 수용 / [ ] 기각 / [ ] 후순위`)를 포함한다.

## DISMISS — 불필요/기처리 (N건)
| # | 리뷰어 | 파일 | 요약 | 사유 |
|---|--------|------|------|------|
```

### 7. 개발자 확인

TRADEOFF 항목이 있으면 개발자에게 `review-summary.md`를 확인하고 각 그룹의 방향을 판단하도록 안내한다.
확인 결과에 따라 AGREE 또는 기각으로 최종 분류를 확정한다.

TRADEOFF 항목이 없으면 바로 plan 페이즈로 진행한다.
