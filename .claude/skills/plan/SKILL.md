요구사항/PRD: $ARGUMENTS

## 전제 조건

- 요구사항 또는 PRD가 있어야 한다 (`$ARGUMENTS` 또는 `docs/requirements/`)
- `/design` 완료 후 실행하면 설계 문서를 기반으로 더 정밀한 계획 수립 가능


## 절차

1. `$ARGUMENTS`가 있으면 해당 요구사항 분석, 없으면 `PRD.md` 확인
2. 기존 `plan.md`가 있으면 진행 상황 파악 후 추가/수정 제안
3. 영향 범위 파악: 기존 코드를 탐색하여 관련 파일과 의존관계 확인
4. 요구사항을 TDD로 구현할 수 있는 단위로 분해
5. 체크리스트 형태로 작성
6. 개발자 확인 후 저장

## plan.md 형식

```markdown
# 기능명

## 개요

요구사항 요약

## 영향 범위

- 신규 파일: ...
- 수정 파일: ...
- 관련 기존 파일: ...

## 구현 계획

### A. Domain Model

- [ ] [P-A] A-1: [RED] 상품 Entity 필수 필드 검증 (~하면 ~한다) → [GREEN] 최소 구현
- [ ] [P-A] A-2: [RED] 상품 Entity 비즈니스 메서드 → [GREEN] 최소 구현
- [ ] [P-B] A-3: [RED] 주문 Entity 필수 필드 검증 → [GREEN] 최소 구현
- [ ] [P-B] A-4: [RED] 주문 Entity 비즈니스 메서드 → [GREEN] 최소 구현

### B. Domain Service

- [ ] [P-A] B-1: [RED] 상품 도메인 로직 → [GREEN] 최소 구현
- [ ] [P-B] B-2: [RED] 주문 도메인 로직 → [GREEN] 최소 구현

### C. Repository

- [ ] [P-A] C-1: [RED] 상품 Repository 인터페이스 + 구현 → [GREEN] 최소 구현
- [ ] [P-B] C-2: [RED] 주문 Repository 인터페이스 + 구현 → [GREEN] 최소 구현

--- checkpoint: 도메인 + 저장소 검수 ---

### D. Application Service

- [ ] [P-A] D-1: [RED] 상품 Service 핵심 로직 → [GREEN] 최소 구현
- [ ] [P-B] D-2: [RED] 주문 Service 핵심 로직 → [GREEN] 최소 구현

--- checkpoint: 서비스 레이어 검수 ---

### E. 진입점 + 통합 테스트

- [ ] E-1: [RED] 진입점 구현 → [GREEN] 최소 구현
- [ ] E-2: [RED] 통합 시나리오 → [GREEN] 최소 구현

--- checkpoint: 전체 통합 검수 ---

## 고려사항

- 기존 패턴과의 일관성
- 성능 영향
```

## 표기법

### 항목 ID `{섹션}-{순번}`

각 항목에 **섹션 알파벳 + 순번** 형태의 ID를 부여한다:

- 형식: `A-1`, `B-2`, `E-1`
- 섹션 알파벳은 레이어 순서를 따른다 (A=Domain Model, B=Domain Service, ...)
- ID는 서브에이전트에 작업 범위를 지정할 때 사용한다 (예: "A-1부터 A-4까지 구현해줘")

### TDD 쌍 `[RED] → [GREEN]`

각 항목은 `[RED] 테스트 설명 → [GREEN] 최소 구현` 쌍으로 구성한다.
"~하면 ~한다" 형태로 행위를 명시한다.

### 병렬 그룹 `[P-X]`

같은 `[P-X]` 태그를 가진 항목은 독립적으로 동시 진행 가능.
이 표기는 **사람을 위한 신호** — "터미널 탭 하나 더 열어서 시켜도 꼬이지 않겠구나"의 판단 근거.
단일 도메인 작업이면 병렬 그룹 생략 가능 (강제하지 않음).

### 검수 단위 `--- checkpoint ---`

`--- checkpoint: 설명 ---` 구분선으로 검수 지점을 표시.

### 체크박스 상태 관리

```markdown
- [ ] A-1: 미착수
- [x] A-1: 검증 완료 (테스트 통과 확인 후 체크)
```

- **체크 시점**: 서브에이전트 작업 후, 메인에서 테스트 통과를 확인하고 체크한다
- **미체크 = 미검증**: 서브에이전트가 "완료"를 보고해도 메인에서 검증 전까지 체크하지 않는다

## 규칙

- 각 항목은 하나의 테스트로 검증 가능한 크기
- 도메인 → 저장소 → 서비스 → 진입점 순서 (의존성 방향)
- 항목은 구체적으로 (예: "로그인 ID가 빈 값이면 회원가입 실패")
- 레이어 경계 또는 통합 지점에 `--- checkpoint ---` 배치
- 의존관계가 있는 항목은 같은 그룹 내에서 순서대로 배치
- 계획만 세우고 코드는 작성하지 않는다
- 과도한 설계 지양 — 현재 필요한 최소한의 구조만 제안
- 불확실한 부분은 추측하지 말고 질문
- 개발자 확인 없이 임의 생성 금지
- **Step이 비대해지면 sub-step으로 분할**: 한 step의 예상 변경 파일이 많아지면 sub-step으로 분할한다. 세션 크기를 제한하여 실행 시 규칙 준수율을 유지하기 위한 것이다.
    - 프로덕션 코드와 그에 대응하는 테스트는 하나의 단위로 취급한다
    - interface + impl 쌍(예: Repository)도 하나의 단위로 취급한다
    - 단, 무관한 모듈/도메인의 파일을 한 step에 묶지 않는다

## 이 프로젝트의 컨벤션

### 레이어 순서

- 도메인 모델 → 저장소 (Repository 인터페이스 + Fake + 구현체) → 서비스 (UseCase/Facade) → API (Controller + ApiSpec)

### Gotchas

- Fake Repository 생성 항목을 빠뜨리지 않는다 (단위 테스트에 필수)
- checkpoint에 `--- checkpoint: lint + test ---` 형태로 검증 지점을 반드시 포함
- 의존관계가 있는 항목은 같은 그룹 내에서 순서대로 배치
