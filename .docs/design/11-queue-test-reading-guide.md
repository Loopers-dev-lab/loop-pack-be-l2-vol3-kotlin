# 11. Queue Test Reading Guide

## 목적

이 문서는 대기열 전략 테스트를 **"돌리는 법"** 보다
**"어떻게 봐야 제대로 학습이 되는지"** 에 초점을 맞춘다.

즉 아래 질문에 답할 수 있게 만드는 문서다.

- 같은 요청을 넣었을 때 왜 전략마다 다르게 보이는가
- 어디를 보면 병목을 빨리 알아차릴 수 있는가
- 어떤 결론은 내려도 되고, 어떤 결론은 아직 이르다고 봐야 하는가
- 한 번의 테스트 결과를 어떻게 비교 가능한 실험 기록으로 남길 수 있는가

---

## 한 줄 요약

**대기열 전략 테스트는 "누가 더 빠른가"만 보면 안 된다.**

반드시 같이 봐야 한다.

1. **사용자 경험**
   - 대기 순번이 자연스러운가
   - admitted 전환이 안정적인가
   - 주문 성공까지 이어지는가

2. **시스템 병목**
   - Redis가 버거운가
   - DB lock이 몰리는가
   - Kafka lag가 생기는가

3. **운영 복잡도**
   - 장애 지점이 몇 개인가
   - 상태 추적이 쉬운가
   - 실서비스 운영 난이도가 낮은가

---

## 테스트를 보기 전에 고정해야 하는 것

전략 비교는 **입력 조건이 같아야만 의미**가 있다.

아래는 반드시 고정한다.

- 사용자 수
- 요청 패턴
  - 동시에 진입
  - 초당 일정량 진입
- 테스트 시간
- warm-up 시간
- queue polling 주기
- 주문 요청 payload
- 인프라 크기
  - DB
  - Redis
  - Kafka
- 앱 설정
  - `queue.experiment.scheduler.fixed-delay`
  - `queue.experiment.token-ttl`
  - `queue.experiment.batch-size-override`

이 중 하나라도 바뀌면
**전략 차이인지, 환경 차이인지** 구분이 흐려진다.

---

## 반드시 남겨야 하는 관찰 기록

각 전략 테스트가 끝날 때 아래를 남긴다.

### 0. 실험 메타데이터

- 실행 시각
- 활성 전략
- 사용자 수 / arrival pattern
- warm-up 시간
- 본 측정 시간
- 앱 버전 또는 커밋 기준
- JVM / 인프라 조건

이 정보가 없으면
나중에 같은 결과를 다시 재현하기 어렵다.

### 1. 요청 관점

- 몇 명이 진입했는가
- 몇 명이 admitted 되었는가
- 몇 명이 실제 주문까지 성공했는가
- 실패는 어떤 종류였는가
  - timeout
  - invalid token
  - lock acquire failure
  - server error

### 2. 사용자 경험 관점

- 순번이 직관적인가
- 대기 시간이 예측 가능했는가
- admitted 되었는데 주문이 실패하는 비율은 어떤가
- polling 결과가 흔들리거나 비어 보이는 순간은 없었는가

### 3. 시스템 관점

- RPS
- HTTP p95 / p99
- 5xx error rate
- DB connection usage / lock wait
- Redis CPU / command latency
- Kafka lag / consumer delay

### 4. 해석 관점

- 이 전략의 병목은 어디인가
- 이 전략은 사용자 경험이 좋은가
- 이 전략은 운영이 쉬운가
- 이 전략은 트래픽 10배에서 어디가 먼저 무너질 것 같은가

---

## 지표를 읽는 기본 순서

한 번의 테스트는 아래 순서로 읽는 게 가장 안전하다.

### 1. RPS부터 본다

먼저 요청이 실제로 들어왔는지 확인한다.

- RPS가 기대보다 낮다
  - 부하 생성기가 약한 것일 수 있다
  - 앱이 아니라 테스트 도구가 병목일 수 있다

즉, RPS를 보기 전에는 latency 해석이 흔들린다.

### 2. p95 / p99를 본다

- `p50`: 평소 경험
- `p95`: 대부분의 나쁜 경험
- `p99`: tail latency

읽는 법은 단순하다.

- `p50`은 안정적인데 `p95`, `p99`만 튄다
  - 락 경합
  - 큐 적체
  - 재시도
  - Kafka lag
  - GC 같은 **꼬리 문제**를 의심한다

- `p50`, `p95`, `p99`가 다 같이 오른다
  - 시스템 전체가 느려진 것이다
  - DB, Redis, CPU 같은 **공통 병목** 가능성이 높다

### 3. error rate를 본다

latency가 나빠도 실패가 거의 없으면
"느리지만 버틴다" 쪽일 수 있다.

반대로 latency는 괜찮아 보여도
error rate가 올라가면 이미 실서비스 체감은 나쁘다.

### 4. saturation을 본다

마지막으로 왜 그런지 본다.

- DB lock wait 증가
- connection pool 고갈
- Redis 명령 지연
- Kafka consumer lag 증가

이 지점에서 비로소
**"무슨 문제가 생겼는가"** 를
**"왜 그랬는가"** 로 연결할 수 있다.

## 전략별로 특히 봐야 하는 포인트

## 1. REDIS_ONLY

### 이 전략에서 배우는 것

- 가장 단순한 FIFO 대기열이 얼마나 빠른가
- polling 기반 조회가 Redis에서 얼마나 잘 버티는가

### 꼭 봐야 하는 것

- 순번 일관성
- admitted 전환 속도
- polling 증가 시 Redis 부하

### 이런 결과면 이렇게 읽는다

- 빠르고 단순하며 순번도 자연스럽다
  - 사용자 경험 기준선으로 삼기 좋다
- polling이 늘수록 Redis 부담이 빠르게 오른다
  - 조회 패턴 최적화가 필요하다

---

## 2. REDIS_KAFKA

### 이 전략에서 배우는 것

- 빠른 waiting room과 비동기 전달을 섞으면 어떤 trade-off가 생기는가

### 꼭 봐야 하는 것

- waiting -> admitted 전환 안정성
- Kafka send / consume 지연
- 사용자에게 상태가 비어 보이는 순간이 있는가

### 이런 결과면 이렇게 읽는다

- Redis Only보다 약간 느리지만 상태 전파가 안정적이다
  - 분리형 구조로 갈 가치가 있다
- Kafka lag가 생길 때 admitted 체감이 흔들린다
  - 사용자 UX보다 이벤트 decoupling 쪽 이점이 큰 구조다

---

## 3. KAFKA_ONLY

### 이 전략에서 배우는 것

- Kafka는 강력한 이벤트 시스템이지만
  사용자용 대기열 UX와는 결이 다르다는 점

### 꼭 봐야 하는 것

- 순번 해석 가능성
- projection store 필요성
- offset 기반 질서가 사용자에게 직관적인가

### 이런 결과면 이렇게 읽는다

- throughput은 괜찮은데 queue UX는 복잡하다
  - 이벤트 처리에는 좋지만 대기열 UX에는 추가 보완이 필요하다
- 상태 추적이 어려워진다
  - 운영 난이도가 빠르게 올라간다

---

## 4. PESSIMISTIC_LOCK

### 이 전략에서 배우는 것

- 정합성을 강하게 잡으면 왜 병목이 DB로 몰리는가

### 꼭 봐야 하는 것

- lock wait
- transaction time
- DB connection pool 사용률
- p95 / p99 급등 시점

### 이런 결과면 이렇게 읽는다

- 낮은 트래픽에서는 잘 버틴다
  - 단순성과 정합성이 장점이다
- 부하가 커질수록 tail latency가 급격히 나빠진다
  - DB 락 기반 방식의 한계가 드러난다

---

## 5. DISTRIBUTED_LOCK

### 이 전략에서 배우는 것

- 여러 처리 주체가 동시에 admission을 시도할 때
  coordination 비용이 어떻게 생기는가

### 꼭 봐야 하는 것

- lock acquire 실패율
- retry 여부
- admission 지연
- Redis lock 관리 비용

### 이런 결과면 이렇게 읽는다

- DB lock보다는 낫지만 lock 실패가 눈에 띈다
  - 분산 제어의 비용을 치르는 구조다
- 다중 인스턴스에서 중복 admission 방지가 잘 된다
  - 수평 확장 환경에 더 적합하다

---

## 잘못된 결론을 피하는 법

아래 결론은 성급하다.

반대로 아래 조건을 만족하면
비교적 안전한 결론이라고 볼 수 있다.

- 같은 조건에서 여러 번 반복해도 방향이 비슷하다
- p95 / p99 개선이 throughput 저하 없이 유지된다
- error rate가 새로 나빠지지 않는다
- 자원 사용량 증가가 설명 가능한 수준이다
- 병목 원인을 saturation 지표로 같이 설명할 수 있다

### 1. "p95가 낮으니 무조건 좋은 전략이다"

아니다.

- error rate가 높을 수 있다
- admitted 이후 주문 성공률이 낮을 수 있다
- 운영 복잡도가 너무 높을 수 있다

### 2. "throughput이 높으니 실서비스에 적합하다"

아니다.

사용자는 throughput보다
**순번 일관성, 대기 예측 가능성, 실패 경험**에 더 민감하다.

### 3. "한 번 돌려봤더니 이 전략이 최고였다"

아니다.

반드시 아래 3구간으로 나눠 봐야 한다.

- 목표 이하 부하
- 목표 부하
- 목표 초과 부하

전략 차이는 보통 **목표 부하 근처** 또는 **초과 구간**에서 드러난다.

---

## 추천 실험 순서

학습 목적이면 아래 순서가 가장 좋다.

1. `REDIS_ONLY`
   - 기준선 파악
2. `PESSIMISTIC_LOCK`
   - DB 락 기반 한계 체감
3. `DISTRIBUTED_LOCK`
   - 분산 제어 개념 체감
4. `REDIS_KAFKA`
   - decoupling 이점과 지연 trade-off 이해
5. `KAFKA_ONLY`
   - 이벤트 스트림과 대기열 UX 차이 이해

이 순서가 좋은 이유는
**단순 -> 무거운 정합성 -> 분산 제어 -> 비동기 결합 -> 이벤트 중심 구조**로
개념 난이도가 올라가기 때문이다.

---

## 테스트가 끝날 때 반드시 적을 질문

각 전략마다 아래 다섯 문장을 직접 적어본다.

1. 이 전략의 가장 큰 장점은 무엇인가
2. 이 전략의 병목은 어디인가
3. 이 전략은 사용자 경험이 좋은가
4. 이 전략은 운영이 쉬운가
5. 이 전략은 지금 팀/서비스 상황에 현실적인가

이 다섯 줄만 제대로 적어도
단순 벤치마크가 아니라 **학습 테스트**가 된다.

---

## 이 레포 기준으로 지금 바로 볼 수 있는 것

현재 레포에는 아래 기반이 이미 있다.

- Prometheus scrape: `/actuator/prometheus`
- Grafana dashboard: `commerce-api-performance`
- HTTP histogram 기반 p95 계산

즉 지금 바로 가능한 학습:

- HTTP RPS
- HTTP p95
- 5xx error rate
- 기본 자원 사용량

반면 아직 queue 전용 custom metrics는 없다.

예를 들면 아래는 아직 직접 보이지 않는다.

- strategy별 queue depth
- admit count
- token issue count
- token expire count
- strategy별 waiting time histogram
- lock acquire failure count

따라서 현재 단계에서는
**HTTP 결과와 시스템 자원 관점으로 먼저 학습하고**,
다음 단계에서 queue 전용 메트릭을 추가하는 것이 가장 자연스럽다.

---

## 결론

이 테스트를 잘 본다는 것은
"가장 빠른 전략을 고르는 것"이 아니다.

정확히는 아래를 같이 판단하는 것이다.

- 사용자에게 가장 자연스러운 전략은 무엇인가
- 목표 트래픽에서 가장 먼저 무너지는 지점은 어디인가
- 운영 복잡도까지 포함하면 무엇이 가장 현실적인가

그래서 테스트를 볼 때는 항상

**RPS -> latency -> error -> saturation -> 해석**

순서로 읽는 것이 가장 안전하다.
