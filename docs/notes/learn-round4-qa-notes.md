## Q1. "트랜잭션이면 안전한 줄 알았다" — `@Transactional`의 한계

**[질문]**
`Product.stock = 5`인 상태에서 사용자 A(3개)와 사용자 B(4개)가 거의 동시에 `OrderFacade.placeOrder()`를 호출. `@Transactional` + 도메인 음수 방지 가드(`StockQuantity` VO)는 모두 갖춰져 있음.

```kotlin
@Transactional
fun placeOrder(userId: Long, productId: Long, quantity: Int): Order {
    val product = productService.findById(productId)   // SELECT stock
    product.deductStock(quantity)                       // 도메인 가드
    productService.save(product)                        // UPDATE stock
    return orderRepository.save(Order(...))
}
```

(a) 이 코드는 동시 실행 시 어떤 시나리오가 발생할 수 있는가?
(b) DB 격리 수준을 `SERIALIZABLE`로 올리면 (a)가 해결되는가?
(c) "재고 음수가 안 됐으니 괜찮은 거 아닌가요?"라는 동료에게 어떻게 반박할 것인가?

**[1차 답변]**
> a : A와 B가 동시에 Product.stock = 5 를 조회하고, A는 2를 저장, B 는 1을 저장 시도하면서 A가 먼저하면 B 값으로 덮어씌고 B가 먼저하면 A 값으로 덮어씌가 된다
>
> b : 해결된다. db 가 직렬화로 된다. 그러나 데드락 발생이 될 수 있다.
>
> c : db는 모든 서비스에서 같이 사용하기 때문에 SERIALIZABLE 로 변경하면 성능 뿐만 아니라 다른 문제를 발생할 수 있다

**[1차 평가]**
- (a) ✅ Lost Update 타임라인 정확
- (b) ⚠️ "데드락 발생 가능" 키워드는 맞지만 *왜* 발생하는지 메커니즘 설명 부족
- (c) ❌ 질문 의도 빗나감 — 동료의 *"음수 안 됐으니 괜찮다"* 말의 잘못을 짚어야 했음 (SERIALIZABLE 단점이 아님)

**[후속 질문 (b'): SERIALIZABLE은 "직렬 실행"인가? 데드락은 왜 발생하는가?]**
**[후속 질문 (c'): 동료의 "음수 안 됐으니 OK"가 잘못된 이유 — 재고와 주문의 관점에서]**

**[2차 답변]**
> b : a, b 가 공유락을 동시에 획득하고, 쓰기를 위해 배타락을 획득해야하지만 공유락을 모두 반환하기를 기다리다가 영원히 기다리는 상황이 발생하게 된다.
>
> c : a = 3, b = 4 를 주문하면 총 7개가 팔렸다. 근데 결과는 1 또는 2 인 상황이다. 우리는 a, b 고객에게 배송을 해야하는데 재고가 부족하다. 데이터 정합성 문제 뿐만아니라 신뢰성 문제까지 발생한다.

**[2차 평가]**
- (b') ✅ S Lock → X Lock 승격 충돌 메커니즘 정확
- (c') ✅ "7개 팔렸는데 DB는 1~2개" — Lost Update 본질을 한 줄로 압축

**[악마의 변호인: "영원히 기다린다"는 정말인가?]**
힌트: MySQL InnoDB의 `innodb_deadlock_detect=ON` 기본 동작 — wait-for graph로 사이클 감지 시 희생자(victim) 트랜잭션 자동 롤백. → 애플리케이션은 `DeadlockLoserDataAccessException` 수신 → **재시도(retry) 패턴 필요**.

**[Q1 종합 정리]**
1. **`@Transactional` ≠ 동시성 안전** — ACID는 단일 트랜잭션의 원자성/일관성/격리성/지속성을 보장하지만, 동시 실행 시 격리성은 격리 수준에 의존
2. **SERIALIZABLE의 동작 메커니즘** — 직렬 실행이 아니라 *결과가 직렬 실행과 동일하도록 락을 강제*. MySQL InnoDB는 일반 SELECT를 `SELECT ... LOCK IN SHARE MODE`로 자동 변환 → S Lock 동시 획득 → UPDATE 시 X Lock 승격 충돌 → 데드락 빈발
3. **데드락 ≠ 영원한 대기** — InnoDB는 wait-for graph로 사이클 감지, 희생자 트랜잭션 자동 롤백. 애플리케이션은 재시도 로직으로 대응
4. **"음수 방지 ≠ 동시성 안전"** — 도메인 가드(VO)는 단일 트랜잭션 내 invariant. Lost Update 시 *총 차감량과 실제 재고 감소량의 불일치*가 더 치명적 [글감]
5. **격리 수준 상승은 "트랜잭션 단위" 옵션** — Spring `@Transactional(isolation = SERIALIZABLE)`로 메서드별 적용 가능. 사용자가 (c)에서 "DB 전체 설정이라 다른 서비스에 영향"이라고 한 표현은 미묘하게 부정확
6. **결론: 동시성 제어는 별도 메커니즘** — 격리 수준 상향은 비용 큼(데드락+처리량 저하). 실무 표준은 **명시적 락(낙관적/비관적) + 재시도** [글감]

## Q2. 쿠폰의 동시성 — 어떤 락이 적절한가?

**[질문]**
쿠폰 도메인에는 두 가지 동시성 위험 지점이 있음:
- 시나리오 A: 쿠폰 사용(use) — 같은 사용자가 모바일/PC 동시 주문 시 한 쿠폰의 중복 사용
- 시나리오 B: 쿠폰 발급(issue) — 선착순 100장 한정에 200명 동시 발급 요청

(a) 시나리오 A에 적합한 락은? 근거는?
(b) 시나리오 B에 적합한 락은? A와 다른 선택을 할 이유는?
(c) 시나리오 B에서 락 외 대안은?

**[1차 답변]**
> a : 낙관적락, 하나의 쿠폰을 동시에 접근 하고, 한번의 상태만 변경하면 되기 때문에 선택했다.
> b : 충돌 빈도가 높기 때문에 비관적락을 사용하는게 좋다. 낙관적락을 하면 에러 발생 후 재시도를 계속하기 때문에 오히려 더 문제가 될 수 있다.
> c : 이건 모르겠네

**[1차 평가 + 보강 + 힌트]**
- (a) ✅ 결론 적절. "한 번의 상태 변경"이라는 표현에 충돌 빈도 낮음이 함축됨
- (b) ✅ "낙관적 락 + 재시도 폭주(retry storm)"의 핵심 문제 정확히 짚음
- (c) "모르겠다" → 1차 힌트: Redis `INCR`로 100명까지만 통과시키는 패턴

**[흔들기 (a): 낙관적 락 충돌 시 사용자에게 어떤 응답을?]**
**[1차 힌트 (c): Redis INCR의 원자성 활용]**

**[2차 답변]**
> a : DB의 쿠폰 상태는 AVAILABLE 일 것이다. 재시도를 한다면 상태 확인 을 하기 때문에 쿠폰 사용했다고 반환해야 한다.
> c : Redis 의 INCR 를 사용하여 100명까지 올리고, 101 명 부터는 소진되었다고 반환한다.

**[2차 평가]**
- (a) ⚠️ 메커니즘 오해 — *"DB는 AVAILABLE"* 은 틀림. 패배한 트랜잭션이 본 시점에 승리한 트랜잭션이 이미 커밋되어 DB는 `USED, version=1` 상태. 따라서 재시도는 무의미하고 *비즈니스 예외로 응답*이 정답
- (c) ✅ 정확. Redis 분산 카운터 패턴

**[정정: 낙관적 락 충돌의 정확한 의미]**
낙관적 락의 충돌 = "이미 다른 누군가가 처리 완료했다"는 신호. 재시도 시 SELECT 결과는 `USED`이고 도메인 가드(`require(status == AVAILABLE)`)에서 즉시 비즈니스 예외. 재시도가 의미 있는 케이스는 *경쟁* 시나리오가 아니라 *우연한 충돌*(같은 사용자가 잔액 갱신 중 적립 들어옴 등) [글감]

**[3차 흔들기 (c-1): Redis ↔ DB 두 단계 정합성]**
(c-1-α) Redis INCR 성공 + DB INSERT 실패 시 결과는?
(c-1-β) DECR 보상이 실패할 수 있는 상황은?
(c-1-γ) 완전 보장 불가 → 현실적 타협안은?

**[3차 답변]**
> c-1-α : DB INSERT 실패하면 DB INSERT 실패를 한 만큼 쿠폰 발급을 못 받았을것 이다.
> c-1-β : redis가 다운 될 수 있고, 네트워크 에러일 수 있다.
> c-1-γ : 99명 까지 받을 것이다.

**[3차 평가]**
모두 정확. 특히 (c-1-γ)의 *"under-issue is safe, over-issue is dangerous"* 비즈니스 판단이 핵심. 100장→101장 발급은 보상 필요, 99장 발급은 비즈니스 손실 미미. 이 비대칭성을 의식한 설계가 분산 시스템의 정수 [글감]

**[Q2 종합 정리]**
1. **락 선택 = 충돌 빈도 × 재시도 비용**의 곱 — 빈도 낮음=낙관적, 빈도 높음=비관적
2. **낙관적 락 충돌 = "이미 처리됨"의 신호** — 재시도 무의미, 비즈니스 예외로 응답. `@Retryable` 무지성 적용 금지
3. **비관적 락 vs 낙관적 락의 진짜 차이** = 충돌을 *기다릴 것인가*, *실패시킬 것인가*의 설계 의지
4. **분산 카운터 패턴(Redis INCR)** = 락 없는 대안. 단 Redis(in-memory) ↔ DB(persistent) 두 단계의 정합성 문제 존재
5. **두 단계 정합성의 본질적 한계** — 완전 보장 불가. *under-issue 허용* 비즈니스 트레이드오프로 해결 [글감]
6. **운영 보정 패턴** — 트래픽 종료 후 배치로 Redis 카운터와 DB 행 수 비교, 누락분 감지/보충 발급 결정. *실시간 정합성 포기 + eventual consistency + 운영 개입* 패턴

## Q3. 재고 차감 — 락을 어디에 걸 것인가?

**[질문]**
시나리오: 다음 주 *스투시 반팔티 100장 한정* 출시, 1000명 동시 주문 예상.
프로젝트 현황: `Order`에 `@Version` 적용 / `Product`는 락 없음.

(a) Order에 걸린 `@Version`이 1000명 동시 주문 충돌을 막는가?
(b) Product에 `@Version` 추가하면?
(c) 비관적 락(`SELECT FOR UPDATE`)으로 가면? 처리량/UX/대안은?

**[답변]**
> a : order에 @Version 이 있는데 의미가 없다.
> b : 락의 역할은 될 수 있지만 재시도 하는 상황이 매우 많아 성능이 안좋아 질것이다.
> c-1 : 1000 명 모두 될려면, 50000ms 이다.
> c-2 : 로딩 화면을 보거나, 대기열 화면을 볼것이다.
> c-3 : Redis의 INCR 를 사용할 수 잇다

**[평가]**
- (a) ✅ 락의 위치가 잘못됐음을 정확히 인지. *충돌 자원 = Product, 락 위치 = Order = 동시성 제어 작동 안함* [글감]
- (b) ✅ Q2 시나리오 B(쿠폰 발급)와 동일 = retry storm
- (c-1) ✅ 1000명 × 50ms = 50초. HTTP 타임아웃에 걸려 사실상 서비스 불가
- (c-2) ✅ "대기열 화면" 발상은 단순 UX가 아니라 *시스템 컴포넌트 결정*. Round 8 Redis Sorted Set 입장 토큰 패턴과 연결
- (c-3) ⚠️ "Redis INCR" 방향만. 디테일 부족 → 흐름 A/B/C 중 선택 흔들기

**[흔들기 (c-3-α): Redis INCR 적용 흐름]**
- 흐름 A: DB 먼저 → 성공 시 Redis 갱신
- 흐름 B: Redis DECR 먼저 (Redis가 진실의 원천)
- 흐름 C: Redis 사전 점유 → DB 차감 → 확정 처리

**[흔들기 (c-3-β): 재고는 쿠폰과 어떻게 다른가?]**

**[2차 답변]**
> c-3-α: 흐름 C 이 안전하다고 생각된다,
> c-3-β :  redis에서 미리 차감한다면 db 커밋전에 오류가 발생하면 redis 증가를 보상 처리해야 한다.

**[2차 평가]**
- (c-3-α) ✅ 흐름 C 선택 적절
- (c-3-β) ❌ Q2 결론 반복. *재고와 쿠폰의 결정적 차이*를 못 짚음 → 직접 보강

**[보강 (흐름 A/B/C의 본질)]**
- A: DB 락 경합 그대로 노출 → 처리량 문제
- B: Redis가 진실의 원천 → Redis 장애 = 전체 차감 불능
- C: **Redis = 게이트키퍼(gatekeeper), DB = 진실의 원천**. 1000명 → 100명 fast-path 필터 → DB로 전달. *거절(reject) 책임과 차감(deduct) 책임 분리* [글감]

**[보강 (재고 vs 쿠폰)]**
- 쿠폰: 이벤트성. 200명 몰리고 끝. 누설 발생 시 *그 이벤트 한정* 운영 보정 한 번
- 재고: 상시 작동. 주문/취소 반복. 누설이 시간이 지날수록 누적 → *지속적 운영 보정 필수* [글감]

**[Q3 종합 정리]**
1. **락의 첫 번째 질문 = "충돌 자원이 어디인가?"** — 락의 종류(낙관적/비관적)보다 *위치(scope)*가 더 본질적. 충돌 자원이 아닌 곳의 락 = 가짜 보안
2. **공유 자원 식별 = Aggregate 경계 인식과 동일** — Round 3 Q2에서 "Product와 Brand는 별도 Aggregate"라고 판단한 사고와 동일. 즉 *어떤 행이 동시에 수정되는가*를 추적
3. **비관적 락의 처리량 한계** — N명 × 트랜잭션 시간. HTTP 타임아웃에 걸려 사실상 서비스 불가능
4. **fast-path 게이트키퍼 패턴** — Redis 같은 in-memory 자원에 *거절 결정*을 위임, DB는 *통과한 것만 처리*. 처리량과 정합성을 모두 잡는 실무 표준
5. **재고의 운영 보정은 상시화 필요** — 쿠폰의 *이벤트성 보정*과 달리 *주기적 동기화* 필요. DB stock을 source of truth로 두고 Redis는 hot-path 캐시
6. **대기열 패턴과의 연결** — c-2의 "대기열 화면"은 단순 UX가 아니라 시스템 컴포넌트. Round 8의 Redis Sorted Set 입장 토큰 = "거절을 결정하는 게이트키퍼"의 또 다른 형태

## Q4. 좋아요 카운터 — "한 번에 수십 개씩 빠져요!" *(진행 중 — 답변 대기)*

**[질문]**
시나리오: 인기 인플루언서 추천 → 1000명 동시 좋아요 → 결과는 723. *수십 개가 빠짐*.

```kotlin
@Transactional
fun like(userId: Long, productId: Long) {
    if (likeRepository.existsBy(userId, productId)) return
    likeRepository.save(Like(userId, productId))
    val product = productRepository.findById(productId)
    product.increaseLike()
    productRepository.save(product)
}
```

(a) "수십 개씩 빠진다"의 정확한 메커니즘은? Lost Update가 *카운터 증가*에서도 동일하게 발생하는가?
(b) "느슨한 일관성"의 허용 범위 기준은? (절대 수치 / 비율 / 다른 기준)
(c) 해결책 옵션 비교 (각 trade-off):
- A: Product 비관적 락
- B: Product 낙관적 락
- C: Redis INCR 분리 (DB는 정렬용 비정규화 컬럼)
- D: SELECT COUNT(*) 매번 집계
- E: 비동기 이벤트 (Outbox + Kafka)

> 💡 프로젝트 LikeFacade는 실제로 E 사용 중. 이유까지 추론

**[1차 답변]**
> a : 다룬 재고 차감의 Lost Update와 같은 메커니즘 이다.
> b : 비율을 가지는게 좋을 것이다. 절대 수치는 좋아요가 증가할 때마다 숫자가 바뀔 수 있는게 아니니 비율이 맞다고 생각된다
> c-A : 좋은 결정 중 하나라 생각된다. 하지만 좋아요는 매우 자주 발생하기 때문에 db에 부하를 많이 주면서 락 으로 인한 쓰레드를 계속 잡게 된다.
> c-B : 좋아요 경합이 발생하면서 재시도가 자주 발생하고, 트래픽이 더 늘어나면 실패하는 것도 발생하게 된다
> c-C : 이벤트 성의 단기간 트래픽은 괜찬지만 장기간 트래픽에서는 점점 오차가 많이 발생하게 된다
> c-D : 가장 안좋은 방법이다. Lost Update가 발생한다
> c-E : outbox 에서 원자성이 유지되고, polling을 통해 kafka 에 producer 하게 된다

**[1차 평가]**
- (a) ⚠️ 결론은 맞지만 표면적 — "같다"고만 하고 끝나면, 같은 메커니즘에 다른 해결책을 쓰는 모순을 설명할 수 없음
- (b) ✅ 방향 정확
- (c-A, B, C) ✅ 정확. 특히 C에 Q3의 "지속적 누설" 통찰을 그대로 적용한 것이 좋음
- (c-D) ❌ 메커니즘 오해 — COUNT(*)는 SELECT만 하므로 Lost Update의 정의에 해당하지 않음. 진짜 약점은 *읽기 비용*
- (c-E) ⚠️ 절반만 — "원자성 + polling"은 맞지만, *왜* E가 안전한지의 결정적 메커니즘(Kafka 파티션) 누락

**[후속 질문 — 사용자 요청에 따라 정답 제시]**
사용자가 "전부 그냥 해줘"라고 명시적 요청 → 세 질문 모두 직접 답변 제시.

**[(a') 정답: 빈칸 = "비즈니스 허용 오차(business tolerance)"]**
| | 재고 (Q1) | 좋아요 (Q4) |
|---|---|---|
| 메커니즘 | Lost Update | Lost Update (똑같음) |
| 1개 손실의 의미 | 배송 실패 → 신뢰도 추락 | 사용자 인지 불가 |
| 5% 손실의 의미 | 재해 | 무해, 측정도 어려움 |
| 데이터 정합성 = 비즈니스 정합성? | = | ≠ |
| 해결책 | 강한 동시성 제어 (락, 분산 카운터) | 약한 동시성 제어 (eventual consistency) |

핵심: 재고는 "데이터 한 줄 = 비즈니스 약속 한 건". 좋아요는 "데이터 한 줄 = 인기 신호의 1/N". 같은 race condition도 *허용 오차*가 다르면 다른 도구를 써야 한다. [글감]

**[(c-D') 정답: D의 진짜 약점은 *읽기 비용*]**
- COUNT(*)는 UPDATE가 없으므로 Lost Update와 무관. 정합성 자체는 가장 좋음
- 1만 RPS × 100만 row 인덱스 leaf 풀스캔 = DB CPU·IO 폭사
- InnoDB는 MVCC 때문에 COUNT 캐싱 불가, 모든 candidate row의 visibility 확인 필요
- LIMIT 단축 불가, 캐싱은 thundering herd 동반
- 결론: D = "쓰기 충돌"을 "읽기 비용 폭증"으로 *옮긴 것*. 비용이 사라진 게 아님

**[(c-E') 정답: 안전성의 정체는 "Kafka 파티션 키 = product_id"]**
1. Outbox + Kafka 자체가 동시성을 막는 게 아님. 그냥 Consumer를 병렬로 띄우면 진짜로 Lost Update 발생
2. Kafka 핵심 메커니즘:
   - 같은 파티션 내 메시지 순서 보장
   - 하나의 파티션은 같은 Consumer Group에서 *오직 하나의 Consumer*가 점유
   - 파티션 키 = `product_id` → `hash(productId) % N` → 같은 상품은 항상 같은 파티션 → 같은 Consumer가 *순차 처리*
3. 결과: *락이 아니라 키로 직렬화*. 동시성 안전 확보 + 서로 다른 상품은 다른 파티션에서 병렬 처리 → 처리량도 확보 [글감]

**[Q4 종합 정리]**
1. **Lost Update 메커니즘은 도메인 무관, 하지만 해결책은 도메인 의존** — 비즈니스 허용 오차가 해결책의 비용 한계를 결정 [글감]
2. **옵션 D(COUNT)의 함정** — 정합성은 최고지만 *읽기 부하로 비용이 옮겨갈 뿐* 사라지지 않음
3. **Outbox 패턴의 두 원자성** — ① Like INSERT와 Outbox INSERT의 동일 트랜잭션 원자성(Kafka 직접 호출의 위험 회피) ② Polling이 At-Least-Once 보장
4. **Kafka 파티션 키로 직렬화** — 락 없이 순서 만들기. Outbox+Kafka 패턴의 진짜 묘수 [글감]
5. **재고는 락, 좋아요는 키로 줄세우기** — 분산 시스템에서 race condition을 푸는 두 가지 큰 방향 [글감]
6. **fast-path 게이트키퍼(Q3) vs 키 직렬화(Q4)** — 둘 다 "DB 락을 피하는" 패턴. 전자는 거절로 줄이고, 후자는 키로 줄세움

## Q5. 백지 설계 — 가상의 신규 서비스 (3 기능 동시 출시)

**[시나리오]**
1. **선착순 1만개 한정 굿즈** — 출시 1분간 5만명 동시 주문
2. **상품 좋아요** — 평소 1만 RPS, 인기 상품엔 1초간 1만명 동시 like
3. **단골 5% 쿠폰** — 1인 1매, 매일 자정 1만장 자동 발급, 30분 내 80% 소진

**[1차 답변]**
> 굿즈 판매: redis로 재고만큼 개수 증가, 초과 시 재고 부족 반환. 비관적 락 사용. 보정 작업 불필요
> 좋아요: outbox + kafka 사용. outbox에 좋아요 누른 순서대로 저장, kafka에 직렬화해서 전송 → 컨슈머에서 순차 처리
> 단골 쿠폰: 낙관적 락. 1인 1매. 실패 시 재시도

**[1차 평가]**
- 굿즈: ✅ Q3 게이트키퍼 패턴 즉시 적용. 다만 "DB가 진실의 원천" 흐름 C 일부 누락, 보정 불필요 단정 위험
- 좋아요: ⚠️ Outbox+Kafka는 정확하지만 *파티션 키* 키워드 누락 ("직렬화" 표현 모호)
- 쿠폰: ❌ Q2 정정 사항 미적용 (낙관적 락 충돌 = 재시도 무의미). 자정 트래픽 폭주의 임펄스 모양 인식 부족 → 시나리오 B와 동일 패턴 미인식

**[정답 정리 — 사용자 명시 요청에 따라 직접 제시]**

**① 굿즈 판매 보완**
- 흐름 C: `Redis INCR (1만 한정) → 통과한 요청만 DB INSERT (주문+재고 차감)`
- Redis = 게이트, DB = 진실의 원천
- 보정 필요: Redis 카운터 vs DB 행 수 정합성 검증 배치 (under-fulfill 클레임, over-issue 신뢰 추락 둘 다 가능)

**② 단골 쿠폰 (정정)**
- (2-a) 낙관적 락 충돌 시 재시도 무의미 — Q2 결론. 패배자는 "이미 마감되었습니다" 비즈니스 예외로 응답
- (2-b) 자정 0시 정각 = *임펄스 트래픽*. 평균 RPS와 다름. Q2 시나리오 B와 동일 패턴
- 정답 도구: **Redis 게이트키퍼 + DB unique constraint(user_id, coupon_template_id)**
- 2단 방어: Redis(전체 1만장 한도) + DB unique(1인 1매 / 모바일×PC 동시 발급 차단)

**③ 좋아요 — 결정적 키워드**
- 파티션 키 = **`product_id`**
- 같은 상품의 좋아요는 같은 Kafka 파티션 → 같은 Consumer 순차 UPDATE → 락 없는 동시성 안전

**[통합 질문 — 데이터 정합성 vs 비즈니스 정합성]**
| 기능 | = 또는 ≠ | 도구 선택 반영 |
|---|---|---|
| 굿즈 재고 | = (1개 = 굿즈 1개) | 강한 동시성 (Redis 게이트 + DB) |
| 좋아요 | ≠ (±5% 무해) | 약한 동시성 (Outbox+Kafka eventual) |
| 단골 쿠폰 | = (1인 2장/1만 1장 = 사고) | 강한 동시성 (Redis 게이트 + DB unique) |

**[통합 질문 — 인프라 장애 영향]**
| 장애 | 가장 빨리 무너지는 기능 | 이유 |
|---|---|---|
| DB | 모두 (특히 굿즈/쿠폰 즉시) | DB = 진실의 원천. 좋아요는 Outbox INSERT조차 DB |
| Redis | **굿즈, 쿠폰 (폭포식)** | 게이트키퍼 상실 → 5만 RPS가 DB 직격 → DB도 같이 무너짐. 좋아요는 무관 |
| Kafka | 좋아요만, 그것도 *천천히* | Like INSERT는 동기. Outbox에 쌓이다 복구 후 따라잡음. 사용자 인지 불가 = E의 resilience 효과 |

**[Q5 종합 정리]**
1. **백지 설계의 진짜 평가축 = 재적용 능력** — 같은 패턴을 다른 도메인 이름에서도 알아보는가
2. **굿즈와 쿠폰은 "충돌 모양"이 같다** — 임펄스 트래픽 + 한정 수량. 도메인 이름이 달라도 도구는 같음(Redis 게이트키퍼)
3. **Redis는 단순 캐시가 아닌 critical path** — 굿즈/쿠폰의 게이트키퍼는 죽으면 DB까지 죽이는 *폭포식 장애*의 진원지. Sentinel/Cluster로 단일 장애점 제거 필수 [글감]
4. **Kafka 장애 = 좋아요의 *지연된* 무너짐** — 사용자 인지 없음. 옵션 E는 빠를 뿐 아니라 *장애를 흡수*. 이것이 비동기의 진짜 가치 [글감]
5. **2단 방어 = Redis 게이트(전체 한도) + DB unique(개별 제약)** — 락 없이 동시성과 비즈니스 invariant를 모두 보장하는 표준 패턴 [글감]
6. **"=" 도메인은 정합성을 비싸게 사고, "≠" 도메인은 정합성을 양보해서 비용을 산다** — 같은 race condition도 도메인이 결정 [글감]

## 구현 준비도 판정

**백지 설계 결과 요약:**
- 굿즈 판매: Redis 게이트키퍼 패턴 즉시 적용 ✅ — Q3의 통찰이 체화됨
- 좋아요: Outbox + Kafka 정확히 선택 ✅ — 다만 *파티션 키*라는 결정적 키워드는 추가 학습 필요
- 단골 쿠폰: 낙관적 락 + 재시도로 답변 ❌ — Q2의 정정 사항(낙관적 락 충돌 = 이미 처리됨)을 *다른 도메인 이름(쿠폰)*에서 재적용하지 못함

**커버된 포인트:**
- ✅ Q1 트랜잭션 한계 / SERIALIZABLE 데드락 / 음수 방지 ≠ 동시성 안전
- ✅ Q2 낙관적 vs 비관적 락의 충돌 빈도 기준 / Redis INCR 분산 카운터 / under-issue 비대칭성
- ✅ Q3 락의 위치(scope)가 종류보다 본질적 / fast-path 게이트키퍼 / 흐름 A/B/C
- ✅ Q4 데이터 정합성 ≠ 비즈니스 정합성 / Outbox + Kafka 파티션 직렬화 / D 옵션의 읽기 비용 함정
- ✅ Q5(부분) 굿즈에 게이트키퍼 패턴 즉시 재적용 / Redis 폭포식 장애 / Kafka 장애의 흡수 효과

**보완이 필요한 포인트:**
- ⚠️ **임펄스 트래픽 vs 평균 RPS**의 구분 — "30분에 80% 소진"의 평균값에 속아 자정 0시 정각의 폭주를 놓침
- ⚠️ **같은 패턴의 다른 이름 인식** — 쿠폰 자정 발급 = Q2 시나리오 B와 동일하다는 *재인식*. 도구는 도메인 이름이 아니라 *충돌의 모양*에 따라 결정
- ⚠️ **Kafka 파티션 키 = `product_id`** 같은 결정적 키워드는 *명시*하는 습관 (구현 시 SerializationException 등 디버깅에 직결)
- ⚠️ **낙관적 락에 무지성 재시도 금지** — `@Retryable` 적용 전 *경쟁 vs 우연한 충돌* 분류부터

**판정: 일부 보완 필요**
구조적 이해는 충분함. 다만 *같은 패턴의 다른 도메인 재인식*에서 한 번 더 흔들리면 실전에서 잘못된 도구를 고를 수 있음. 구현 시 Q2 시나리오 B의 결론을 항상 떠올릴 것.

10. **Lost Update를 락으로 막을지, 키로 줄세울지** — 분산 시스템의 두 가지 풀이 [Q4]
11. **Outbox + Kafka 파티션 키 = 락 없는 동시성 안전** — 진짜 묘수는 "비동기"가 아니라 "키 직렬화" [Q4]
12. **Redis는 캐시가 아닌 critical path** — 게이트키퍼는 죽으면 DB까지 죽이는 폭포식 장애의 진원지 [Q5]
13. **Kafka 장애 = 좋아요의 *지연된* 무너짐** — 옵션 E의 가치는 속도뿐 아니라 *장애 흡수* [Q5]
14. **2단 방어 = Redis 게이트 + DB unique** — 락 없이 동시성과 비즈니스 invariant를 모두 잡는 패턴 [Q5]
15. **임펄스 트래픽 vs 평균 RPS** — "30분 80% 소진"이라는 평균값에 속지 마라. 자정 0시 정각의 1초가 진짜 적 [Q5]

## 핵심 개념 정리 — Round 4 학습 요약

### 1. 트랜잭션과 동시성의 분리
- `@Transactional`은 ACID 보장. 동시성은 격리 수준 + 락의 별도 메커니즘
- SERIALIZABLE은 직렬 *실행*이 아니라 *결과의 직렬성*. InnoDB에서는 S Lock → X Lock 승격 충돌로 데드락 빈발
- 실무 표준: 명시적 락(낙관적/비관적) + 재시도 또는 분산 카운터

### 2. 락 선택의 삼각형 — 빈도, 비용, 의미
| 락 종류 | 충돌 빈도 | 충돌의 의미 | 응답 전략 |
|---|---|---|---|
| 비관적 | 높음 (선착순, 임펄스) | "기다리겠다" | 직렬 실행 |
| 낙관적 | 낮음 (우연한 충돌) | "실패하겠다" | 비즈니스 예외 또는 *드물게* 재시도 |
| 분산 카운터 (Redis) | 매우 높음 | "거절하겠다" | fast-path에서 미리 거절 |

### 3. 충돌 자원 식별의 우선순위
- 락의 종류보다 *위치(scope)* 가 본질적
- 충돌 자원 = Aggregate 경계 인식과 동일 (Round 3 Q2)
- 잘못된 위치의 락 = 가짜 보안 (Order에 @Version, Product 동시 차감 미보호)

### 4. 도메인별 정합성 전략
| 도메인 | 데이터 = 비즈니스 | 표준 도구 |
|---|---|---|
| 재고 (한정 굿즈) | = | Redis 게이트키퍼 + DB 락/INSERT (흐름 C) |
| 쿠폰 (선착순 발급) | = | Redis 게이트키퍼 + DB unique (2단 방어) |
| 카운터 (좋아요) | ≠ | Outbox + Kafka 파티션 키(`product_id`) |

### 5. 분산 동시성의 두 가지 풀이
- **락(또는 거절)으로 막기** — 비관적 락, 낙관적 락, Redis 게이트키퍼
- **키로 줄세우기** — Kafka 파티션 키 = product_id로 시간 직렬화
- 같은 Lost Update도 *허용 오차*에 따라 다른 도구 선택

### 6. 운영 보정의 비대칭성
- Under-issue/under-fulfill 안전, Over-issue/over-fulfill 위험
- Redis-DB 두 단계 정합성은 *완전 보장 불가* → 운영 보정 배치로 결합
- 재고는 *상시*, 쿠폰은 *이벤트성* 보정

## 구현 연결 포인트

학습 내용 중 실제 구현 시 주의할 결정/인사이트:

1. **Q2 결론을 코드에 반영** — 낙관적 락 충돌 시 `@Retryable` 자동 적용 전, *경쟁(competition)* 시나리오인지 *우연한 충돌(accidental conflict)*인지 분류. 쿠폰 발급, 굿즈 차감 같은 경쟁 시나리오는 재시도 금지
2. **Kafka 파티션 키 명시** — `LikeFacade.like()`에서 Outbox publish 시 `aggregateId = productId.toString()`으로 일관 유지. Consumer 측 파티션 라우팅이 깨지지 않도록 키 설계 코드리뷰 시 항상 확인
3. **Redis-DB 정합성 검증 배치** — 굿즈/쿠폰 출시 후 Redis 카운터와 DB 행 수 비교 작업을 출시 시점부터 운영 단계에 같이 준비. 사후 추가는 누설 흔적 추적이 어려움
4. **임펄스 트래픽 부하 테스트** — 평균 RPS가 아닌 *순간 스파이크* 시나리오로 부하 테스트. 자정 0시 정각, 출시 직후 1초 같은 *시간 정렬된 트리거*가 있는 모든 기능 대상
5. **InnoDB MVCC 인지** — 격리 수준 선택과 SELECT FOR UPDATE 적용 시 InnoDB 특성 의식. 단순 SELECT는 비잠금 일관성 읽기지만 SERIALIZABLE에서는 자동 락 승격됨
