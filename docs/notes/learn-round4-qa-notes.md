## Q1. "트랜잭션이면 안전한 줄 알았다" — `@Transactional`의 한계

**[질문]**
`Product.stock = 5`인 상태에서 사용자 A(3개)와 사용자 B(4개)가 거의 동시에 `OrderFacade.placeOrder()`를 호출. `@Transactional` + 도메인 음수 방지 가드(`StockQuantity` VO)는 모두 갖춰져 있음.

```kotlin
@Transactional
fun placeOrder(userId: Long, productId: Long, quantity: Int): Order {
    val product = productService.findById(productId)   // SELECT stock
    product.deductStock(quantity)                       // 도메인 가드
    productService.save(product)                        // UPDATE stock
    return orderRepository.save(Order(...))
}
```

(a) 이 코드는 동시 실행 시 어떤 시나리오가 발생할 수 있는가?
(b) DB 격리 수준을 `SERIALIZABLE`로 올리면 (a)가 해결되는가?
(c) "재고 음수가 안 됐으니 괜찮은 거 아닌가요?"라는 동료에게 어떻게 반박할 것인가?

**[1차 답변]**
> a : A와 B가 동시에 Product.stock = 5 를 조회하고, A는 2를 저장, B 는 1을 저장 시도하면서 A가 먼저하면 B 값으로 덮어씌고 B가 먼저하면 A 값으로 덮어씌가 된다
>
> b : 해결된다. db 가 직렬화로 된다. 그러나 데드락 발생이 될 수 있다.
>
> c : db는 모든 서비스에서 같이 사용하기 때문에 SERIALIZABLE 로 변경하면 성능 뿐만 아니라 다른 문제를 발생할 수 있다

**[1차 평가]**
- (a) ✅ Lost Update 타임라인 정확
- (b) ⚠️ "데드락 발생 가능" 키워드는 맞지만 *왜* 발생하는지 메커니즘 설명 부족
- (c) ❌ 질문 의도 빗나감 — 동료의 *"음수 안 됐으니 괜찮다"* 말의 잘못을 짚어야 했음 (SERIALIZABLE 단점이 아님)

**[후속 질문 (b'): SERIALIZABLE은 "직렬 실행"인가? 데드락은 왜 발생하는가?]**
**[후속 질문 (c'): 동료의 "음수 안 됐으니 OK"가 잘못된 이유 — 재고와 주문의 관점에서]**

**[2차 답변]**
> b : a, b 가 공유락을 동시에 획득하고, 쓰기를 위해 배타락을 획득해야하지만 공유락을 모두 반환하기를 기다리다가 영원히 기다리는 상황이 발생하게 된다.
>
> c : a = 3, b = 4 를 주문하면 총 7개가 팔렸다. 근데 결과는 1 또는 2 인 상황이다. 우리는 a, b 고객에게 배송을 해야하는데 재고가 부족하다. 데이터 정합성 문제 뿐만아니라 신뢰성 문제까지 발생한다.

**[2차 평가]**
- (b') ✅ S Lock → X Lock 승격 충돌 메커니즘 정확
- (c') ✅ "7개 팔렸는데 DB는 1~2개" — Lost Update 본질을 한 줄로 압축

**[악마의 변호인: "영원히 기다린다"는 정말인가?]**
힌트: MySQL InnoDB의 `innodb_deadlock_detect=ON` 기본 동작 — wait-for graph로 사이클 감지 시 희생자(victim) 트랜잭션 자동 롤백. → 애플리케이션은 `DeadlockLoserDataAccessException` 수신 → **재시도(retry) 패턴 필요**.

**[Q1 종합 정리]**
1. **`@Transactional` ≠ 동시성 안전** — ACID는 단일 트랜잭션의 원자성/일관성/격리성/지속성을 보장하지만, 동시 실행 시 격리성은 격리 수준에 의존
2. **SERIALIZABLE의 동작 메커니즘** — 직렬 실행이 아니라 *결과가 직렬 실행과 동일하도록 락을 강제*. MySQL InnoDB는 일반 SELECT를 `SELECT ... LOCK IN SHARE MODE`로 자동 변환 → S Lock 동시 획득 → UPDATE 시 X Lock 승격 충돌 → 데드락 빈발
3. **데드락 ≠ 영원한 대기** — InnoDB는 wait-for graph로 사이클 감지, 희생자 트랜잭션 자동 롤백. 애플리케이션은 재시도 로직으로 대응
4. **"음수 방지 ≠ 동시성 안전"** — 도메인 가드(VO)는 단일 트랜잭션 내 invariant. Lost Update 시 *총 차감량과 실제 재고 감소량의 불일치*가 더 치명적 [글감]
5. **격리 수준 상승은 "트랜잭션 단위" 옵션** — Spring `@Transactional(isolation = SERIALIZABLE)`로 메서드별 적용 가능. 사용자가 (c)에서 "DB 전체 설정이라 다른 서비스에 영향"이라고 한 표현은 미묘하게 부정확
6. **결론: 동시성 제어는 별도 메커니즘** — 격리 수준 상향은 비용 큼(데드락+처리량 저하). 실무 표준은 **명시적 락(낙관적/비관적) + 재시도** [글감]

## Q2. 쿠폰의 동시성 — 어떤 락이 적절한가?

**[질문]**
쿠폰 도메인에는 두 가지 동시성 위험 지점이 있음:
- 시나리오 A: 쿠폰 사용(use) — 같은 사용자가 모바일/PC 동시 주문 시 한 쿠폰의 중복 사용
- 시나리오 B: 쿠폰 발급(issue) — 선착순 100장 한정에 200명 동시 발급 요청

(a) 시나리오 A에 적합한 락은? 근거는?
(b) 시나리오 B에 적합한 락은? A와 다른 선택을 할 이유는?
(c) 시나리오 B에서 락 외 대안은?

**[1차 답변]**
> a : 낙관적락, 하나의 쿠폰을 동시에 접근 하고, 한번의 상태만 변경하면 되기 때문에 선택했다.
> b : 충돌 빈도가 높기 때문에 비관적락을 사용하는게 좋다. 낙관적락을 하면 에러 발생 후 재시도를 계속하기 때문에 오히려 더 문제가 될 수 있다.
> c : 이건 모르겠네

**[1차 평가 + 보강 + 힌트]**
- (a) ✅ 결론 적절. "한 번의 상태 변경"이라는 표현에 충돌 빈도 낮음이 함축됨
- (b) ✅ "낙관적 락 + 재시도 폭주(retry storm)"의 핵심 문제 정확히 짚음
- (c) "모르겠다" → 1차 힌트: Redis `INCR`로 100명까지만 통과시키는 패턴

**[흔들기 (a): 낙관적 락 충돌 시 사용자에게 어떤 응답을?]**
**[1차 힌트 (c): Redis INCR의 원자성 활용]**

**[2차 답변]**
> a : DB의 쿠폰 상태는 AVAILABLE 일 것이다. 재시도를 한다면 상태 확인 을 하기 때문에 쿠폰 사용했다고 반환해야 한다.
> c : Redis 의 INCR 를 사용하여 100명까지 올리고, 101 명 부터는 소진되었다고 반환한다.

**[2차 평가]**
- (a) ⚠️ 메커니즘 오해 — *"DB는 AVAILABLE"* 은 틀림. 패배한 트랜잭션이 본 시점에 승리한 트랜잭션이 이미 커밋되어 DB는 `USED, version=1` 상태. 따라서 재시도는 무의미하고 *비즈니스 예외로 응답*이 정답
- (c) ✅ 정확. Redis 분산 카운터 패턴

**[정정: 낙관적 락 충돌의 정확한 의미]**
낙관적 락의 충돌 = "이미 다른 누군가가 처리 완료했다"는 신호. 재시도 시 SELECT 결과는 `USED`이고 도메인 가드(`require(status == AVAILABLE)`)에서 즉시 비즈니스 예외. 재시도가 의미 있는 케이스는 *경쟁* 시나리오가 아니라 *우연한 충돌*(같은 사용자가 잔액 갱신 중 적립 들어옴 등) [글감]

**[3차 흔들기 (c-1): Redis ↔ DB 두 단계 정합성]**
(c-1-α) Redis INCR 성공 + DB INSERT 실패 시 결과는?
(c-1-β) DECR 보상이 실패할 수 있는 상황은?
(c-1-γ) 완전 보장 불가 → 현실적 타협안은?

**[3차 답변]**
> c-1-α : DB INSERT 실패하면 DB INSERT 실패를 한 만큼 쿠폰 발급을 못 받았을것 이다.
> c-1-β : redis가 다운 될 수 있고, 네트워크 에러일 수 있다.
> c-1-γ : 99명 까지 받을 것이다.

**[3차 평가]**
모두 정확. 특히 (c-1-γ)의 *"under-issue is safe, over-issue is dangerous"* 비즈니스 판단이 핵심. 100장→101장 발급은 보상 필요, 99장 발급은 비즈니스 손실 미미. 이 비대칭성을 의식한 설계가 분산 시스템의 정수 [글감]

**[Q2 종합 정리]**
1. **락 선택 = 충돌 빈도 × 재시도 비용**의 곱 — 빈도 낮음=낙관적, 빈도 높음=비관적
2. **낙관적 락 충돌 = "이미 처리됨"의 신호** — 재시도 무의미, 비즈니스 예외로 응답. `@Retryable` 무지성 적용 금지
3. **비관적 락 vs 낙관적 락의 진짜 차이** = 충돌을 *기다릴 것인가*, *실패시킬 것인가*의 설계 의지
4. **분산 카운터 패턴(Redis INCR)** = 락 없는 대안. 단 Redis(in-memory) ↔ DB(persistent) 두 단계의 정합성 문제 존재
5. **두 단계 정합성의 본질적 한계** — 완전 보장 불가. *under-issue 허용* 비즈니스 트레이드오프로 해결 [글감]
6. **운영 보정 패턴** — 트래픽 종료 후 배치로 Redis 카운터와 DB 행 수 비교, 누락분 감지/보충 발급 결정. *실시간 정합성 포기 + eventual consistency + 운영 개입* 패턴

## Q3. 재고 차감 — 락을 어디에 걸 것인가?

**[질문]**
시나리오: 다음 주 *스투시 반팔티 100장 한정* 출시, 1000명 동시 주문 예상.
프로젝트 현황: `Order`에 `@Version` 적용 / `Product`는 락 없음.

(a) Order에 걸린 `@Version`이 1000명 동시 주문 충돌을 막는가?
(b) Product에 `@Version` 추가하면?
(c) 비관적 락(`SELECT FOR UPDATE`)으로 가면? 처리량/UX/대안은?

**[답변]**
> a : order에 @Version 이 있는데 의미가 없다.
> b : 락의 역할은 될 수 있지만 재시도 하는 상황이 매우 많아 성능이 안좋아 질것이다.
> c-1 : 1000 명 모두 될려면, 50000ms 이다.
> c-2 : 로딩 화면을 보거나, 대기열 화면을 볼것이다.
> c-3 : Redis의 INCR 를 사용할 수 잇다

**[평가]**
- (a) ✅ 락의 위치가 잘못됐음을 정확히 인지. *충돌 자원 = Product, 락 위치 = Order = 동시성 제어 작동 안함* [글감]
- (b) ✅ Q2 시나리오 B(쿠폰 발급)와 동일 = retry storm
- (c-1) ✅ 1000명 × 50ms = 50초. HTTP 타임아웃에 걸려 사실상 서비스 불가
- (c-2) ✅ "대기열 화면" 발상은 단순 UX가 아니라 *시스템 컴포넌트 결정*. Round 8 Redis Sorted Set 입장 토큰 패턴과 연결
- (c-3) ⚠️ "Redis INCR" 방향만. 디테일 부족 → 흐름 A/B/C 중 선택 흔들기

**[흔들기 (c-3-α): Redis INCR 적용 흐름]**
- 흐름 A: DB 먼저 → 성공 시 Redis 갱신
- 흐름 B: Redis DECR 먼저 (Redis가 진실의 원천)
- 흐름 C: Redis 사전 점유 → DB 차감 → 확정 처리

**[흔들기 (c-3-β): 재고는 쿠폰과 어떻게 다른가?]**

**[2차 답변]**
> c-3-α: 흐름 C 이 안전하다고 생각된다,
> c-3-β :  redis에서 미리 차감한다면 db 커밋전에 오류가 발생하면 redis 증가를 보상 처리해야 한다.

**[2차 평가]**
- (c-3-α) ✅ 흐름 C 선택 적절
- (c-3-β) ❌ Q2 결론 반복. *재고와 쿠폰의 결정적 차이*를 못 짚음 → 직접 보강

**[보강 (흐름 A/B/C의 본질)]**
- A: DB 락 경합 그대로 노출 → 처리량 문제
- B: Redis가 진실의 원천 → Redis 장애 = 전체 차감 불능
- C: **Redis = 게이트키퍼(gatekeeper), DB = 진실의 원천**. 1000명 → 100명 fast-path 필터 → DB로 전달. *거절(reject) 책임과 차감(deduct) 책임 분리* [글감]

**[보강 (재고 vs 쿠폰)]**
- 쿠폰: 이벤트성. 200명 몰리고 끝. 누설 발생 시 *그 이벤트 한정* 운영 보정 한 번
- 재고: 상시 작동. 주문/취소 반복. 누설이 시간이 지날수록 누적 → *지속적 운영 보정 필수* [글감]

**[Q3 종합 정리]**
1. **락의 첫 번째 질문 = "충돌 자원이 어디인가?"** — 락의 종류(낙관적/비관적)보다 *위치(scope)*가 더 본질적. 충돌 자원이 아닌 곳의 락 = 가짜 보안
2. **공유 자원 식별 = Aggregate 경계 인식과 동일** — Round 3 Q2에서 "Product와 Brand는 별도 Aggregate"라고 판단한 사고와 동일. 즉 *어떤 행이 동시에 수정되는가*를 추적
3. **비관적 락의 처리량 한계** — N명 × 트랜잭션 시간. HTTP 타임아웃에 걸려 사실상 서비스 불가능
4. **fast-path 게이트키퍼 패턴** — Redis 같은 in-memory 자원에 *거절 결정*을 위임, DB는 *통과한 것만 처리*. 처리량과 정합성을 모두 잡는 실무 표준
5. **재고의 운영 보정은 상시화 필요** — 쿠폰의 *이벤트성 보정*과 달리 *주기적 동기화* 필요. DB stock을 source of truth로 두고 Redis는 hot-path 캐시
6. **대기열 패턴과의 연결** — c-2의 "대기열 화면"은 단순 UX가 아니라 시스템 컴포넌트. Round 8의 Redis Sorted Set 입장 토큰 = "거절을 결정하는 게이트키퍼"의 또 다른 형태

## Q4. 좋아요 카운터 — "한 번에 수십 개씩 빠져요!" *(진행 중 — 답변 대기)*

**[질문]**
시나리오: 인기 인플루언서 추천 → 1000명 동시 좋아요 → 결과는 723. *수십 개가 빠짐*.

```kotlin
@Transactional
fun like(userId: Long, productId: Long) {
    if (likeRepository.existsBy(userId, productId)) return
    likeRepository.save(Like(userId, productId))
    val product = productRepository.findById(productId)
    product.increaseLike()
    productRepository.save(product)
}
```
