## Q1. 왜 Redis ZSET인가? — DB ORDER BY vs ZSET

**[질문]**
product_metrics 테이블에 ORDER BY로 정렬해서 랭킹을 제공하면 안 되는 건가요? 왜 별도의 Redis 자료구조가 필요한지 설명해보세요.

**[답변]**
> 상황에 따라 다르다고 생각해. 서비스가 작다면 테이블 ORDER BY 만으로 괜찮을거야. product_metrics 테이블에 필요한 인덱스가 생기면 쓰기에 부하가 생길 것이고, 실시간 랭킹이 아닌 준실시간 랭킹을 제공할 것이다.
> 하지만 redis는 인메모리를 사용해 db 보다 성능이 더 좋고, Redis ZSET 을 사용하여 데이터를 쓰기하면 logN 의 성능을 가지기 때문에 ORDER BY 보다는 redis 사용이 좋다

**[후속 질문: 비용 발생 시점]**
"ORDER BY보다 Redis가 좋다"고 했는데, 정확히 어떤 시점의 비용을 비교한 건가요? DB ORDER BY의 비용이 발생하는 시점과, ZSET이 비용을 지불하는 시점이 같은가요?

**[답변]**
> db 에서는 비용이 읽을 때 발생한다. 일단 fullscan하고 줄을 세운다. 하지만 redis는 데이터를 저장할 때 순위 정렬을 해서 알맞는 곳에 넣고, 읽을 때는 정렬된 순서로 읽기만 하면 되기 때문에 더 빠르게 조회가 가능하다.

**[후속 질문: 인덱스로 해결 가능하지 않은가?]**
DB도 인덱스를 걸면 full scan 없이 정렬된 순서로 읽을 수 있잖아요? 복합 인덱스를 걸면 ZSET과 비슷한 거 아닌가요?

**[답변]**
> 인덱스가 생길 수록 데이터 쓰기에 부하가 발생할 수 있고, 만약 ORDER BY 의 순서가 변하면 인덱스 실행이 안될거야. 하지만 redis는 이런 문제점이 발생하지가 않아.

**[후속 질문: ZSET도 정렬 기준 변경에 자유로운가?]**
ZSET도 단일 score 기준으로 정렬하잖아요. 가중치가 바뀌면 이미 ZSET에 쌓인 score들은 어떻게 되는 거죠?

**[답변]**
> 가중치가 변경되면 ZSET의 score은 변경되고 정렬도 변경될거야. ZSET에 있는 모든 데이터가 변경되는건데 사용자에게 영향을 최소화 하기 위해서는 한번에 모든 데이터를 변경하는게 아니라 하나씩 데이터를 변경하면 어떨까?

**[멘토 보충: 일별 키 전략과의 연결]**
ZSET도 단일 score라서 가중치 변경 시 재계산이 필요하지만, 일별 키 전략(ranking:all:20260407)을 사용하면 다음 날 키부터 새 가중치가 적용되어 관리가 용이함.

**[후속 질문: 읽기/쓰기 비율 관점]**
랭킹 API의 트래픽 특성을 생각해보세요. 홈 메인, 인기순 정렬, 상품 상세의 "현재 N위" — 이 읽기/쓰기 비율이 ZSET 선택의 핵심 근거입니다.

**[답변]**
> 1시간 마다 랭킹을 업데이트 한다면 쓰기:읽기 비율은 거의 1:99. 실시간 랭킹이라면 1:9. 쓰기의 비율이 올라갈 수록 db에서는 랭킹 이외 다른 서비스에 영향이 갈 것이다. 하지만 redis는 다른 서비스에 영향이 미비 할 것이다.

**[정리]**
- DB ORDER BY는 읽기 시점에 정렬 비용 발생, ZSET은 쓰기 시점에 O(logN)으로 정렬 완료
- 랭킹은 읽기 비중이 압도적으로 높은 유스케이스
- DB에 랭킹 부하가 집중되면 주문/상품 등 핵심 비즈니스 쿼리에도 영향 → Redis로 부하 격리
- ZSET도 단일 score 기반이라 가중치 변경 시 재계산 필요하지만, 일별 키 전략으로 관리 가능

## Q2. Key 설계 — 시간의 양자화와 콜드 스타트

**[질문]**
키를 날짜별로 분리하지 않고, `ranking:all` 하나의 키에 점수를 계속 누적하면 어떤 문제가 생길까요? 사용자 관점과 비즈니스 관점 모두에서 생각해보세요.

**[답변]**
> 만약 누적치가 변경된다면 하나의 키를 수정하게 되어 관리가 어려워 질것이다. 그리고 랭킹의 히스토리를 남겨 비즈니스적으로 사용하고자 한다면 사용하지를 못할 것이다.

**[후속 질문: 구체적 시나리오]**
6개월 전 등록된 상품 A(누적 조회 10만, 주문 5천)와 오늘 등록된 신상품 B(하루 조회 500, 주문 100)가 하나의 키에서 누적 점수로 경쟁하면, 사용자에게는 어떤 경험이 될까요?

**[답변]**
> 랭킹이 높은 상품은 계속 높을 것이고, 중간에 들어오면 계속 랭킹이 낮은 문제점이 생기겠네. 서비스 사용자는 정확한 랭킹 정보를 받지 못하고, 늘 보던 상품만 보겠네

**[후속 질문: 콜드 스타트]**
매일 자정에 새로운 키가 시작되면, 새벽 0시 1분에 사용자가 "오늘의 인기 상품"을 조회하면 어떤 결과를 받게 될까요?

**[답변]**
> 전날 데이터를 계속 보여주고 해당 일자의 데이터가 생성되면 그때 보여주는 방식으로 하든, 전날 11시 50분부터 데이터 생성 작업을 시작해서 만들어진 데이터를 보여주는 방식으로 하면 될거 같아.

**[후속 질문: Carry-Over 비율]**
전날 점수를 그대로 100% 복사해서 오늘의 초기 데이터로 쓰면 어떤 문제가 생길까요?

**[답변]**
> 전날 점수를 그대로 사용하는 방식은 일자별 키 생성이 아니라, 하나의 키를 계속 사용하는 것과 다르지 않을거야. 결국 데이터가 계속 누적되는 방식과 같기 때문이야

**[멘토 보충: Score Carry-Over]**
전날 점수에 낮은 가중치(예: 0.1)를 곱해서 복사하는 방식을 사용. Redis의 `ZUNIONSTORE ranking:all:20260408 1 ranking:all:20260407 WEIGHTS 0.1`로 구현. 콜드 스타트는 완화하되 롱테일은 방지하는 균형점.

**[정리]**
- 단일 키 누적 → 롱테일 현상 (오래된 상품이 상위 독식, 신상품 진입 불가, 악순환)
- 일별 키 분리로 공정성 확보 + 히스토리 보존
- 콜드 스타트 완화: Score Carry-Over (전날 점수 × 0.1)로 초기 데이터 생성
- 100% 복사는 누적과 동일 → 낮은 가중치가 핵심

## Q3. 가중치 합산 (Weighted Sum) 설계

**[질문]**
조회(VIEWED), 좋아요(LIKED), 주문(ORDER_COMPLETED) 세 가지 이벤트에 동일한 가중치(각 1점)를 주면 어떤 문제가 생길까요? 왜 이벤트마다 다른 가중치가 필요한지 설명해보세요.

**[답변]**
> 만약 가중치가 동일하다면 조회/좋아요 같이 쉽게 얻을 수 있는 가중치를 사용해서 악의적으로 랭킹을 조작할 수 있을것이다. 가중치는 정말 랭킹에서 중요한 곳에 가중치를 높게 둬 신뢰성을 높이는게 좋다

**[멘토 보충: 스케일 차이]**
하루 동안 조회는 수천 번이지만 주문은 수십 건 — 동일 가중치면 조회수가 score를 지배. 조회만 많고 실제 구매는 없는 상품이 1위가 될 수 있음.

**[후속 질문: ZINCRBY 증가량]**
Kafka Consumer에서 이벤트를 받아 ZSET에 점수를 반영할 때, 조회 이벤트 1건이 들어오면 score를 얼마만큼 증가시킬 건가요? 주문 이벤트 1건은요?

**[답변]**
> 조회 : 0.1, 주문 : 0.7을 증가시킬거 같아

**[후속 질문: 주문 금액 반영 여부 — 악마의 변호인]**
1,000원짜리 상품 주문 1건과 1,000,000원짜리 상품 주문 1건이 똑같이 0.7점을 받는 게 맞을까요?

**[답변]**
> 난 같다고 생각해. 금액이 랭킹에 영향을 준다면 금액이 높으면 랭킹 순위가 높을 확률이 높다는건데 그거는 아니야.

**[후속 질문: 저가 충동구매 지배 문제]**
1,000원짜리 케이스가 500건 주문, 100만원 노트북이 3건 주문이면 케이스가 훨씬 상위에 올라가는데, 이게 "인기 상품" 랭킹으로 맞는 걸까요?

**[답변]**
> 잘 모르겠네. price × quantity가 랭킹에 영향을 주는게 맞을까? 라는 생각을 계속하고 있어. 너의 생각을 말해줘

**[멘토 의견: 트레이드오프 정리]** `[글감]`
정답이 없는 설계 결정. "인기"를 어떻게 정의하느냐에 따라 달라짐:
- 건수만 반영: 많이 산 상품 = 인기. 공정하지만 저가 충동구매 지배 가능
- 금액 반영: 매출 기여도 높은 상품. 비즈니스 가치 있지만 고가 상품 유리
- 절충안: `log(price × quantity)`로 금액 차이 완화, 또는 인기/매출 랭킹 분리

**[결정]**
> log(price × quantity) 방식으로 결정

**[정리]**
- 동일 가중치 → 조회수가 score 지배 + 랭킹 조작 취약
- 가중치 예시: view=0.1, like=0.2, order=0.7
- 주문 score: `0.7 × log(price × quantity)`로 금액 차이 완화
- "인기"의 정의에 따라 설계가 달라지는 트레이드오프

## Q4. 랭킹 적재 로직의 아키텍처 위치

**[질문]**
랭킹 ZSET 적재 로직을 추가해야 하는데, 이 로직은 어디에 위치시킬 건가요? 기존 Consumer에 직접 넣을 건지, 별도 Consumer를 만들 건지 — 레이어드 아키텍처를 고려해서 설명해보세요.

**[답변]**
> 지금 상황에서는 Consumer에서 바로 넣어도 될거 같아. 아니면 db에 넣어야 한다면, 우선 redis에 넣고, 따로 스프링이벤트리스너 만들어서 db에 넣을거 같아

**[후속 질문: 기존 패턴 확인]**
기존 `OrderEventConsumer`가 직접 DB에 쓰나요? Consumer → Processor → Service → Repository 흐름에서, Consumer에서 Redis를 직접 호출하면 어떤 레이어를 건너뛰는 건가요?

**[답변]**
> Processor의 트랜잭션이 모두 끝난 후 스프링이벤트리스너를 만들어서 따로 랭킹을 적재할거야. Processor의 역할은 주문이지 product_metrics의 역할이 아니고, 주문이 완료되어야 product_metrics도 비로소 존재 가능하다고 생각해.

**[후속 질문: 이중 이벤트 구조의 복잡도]**
commerce-streamer의 Processor는 주문을 처리하는 게 아니라, 이미 완료된 이벤트의 부수 효과를 처리하는 것. 이벤트 안에서 또 이벤트를 발행하면 복잡도 대비 얻는 게 있을까요? Application 계층의 역할이 "서로 다른 도메인을 조합해 유스케이스 기능 제공"인데, Processor에서 직접 조합하는 게 맞지 않나요?

**[답변]**
> 그러네 맞는거 같아. 근데 productMetricsRepository 대신 랭킹 서비스를 만들어서 랭킹과 productMetricsRepository를 저장해도 괜찮을거 같아

**[후속 질문: 서비스 책임 분리]**
ProductMetrics는 랭킹만을 위한 데이터인가요? 상품 상세의 "조회수 1,234회" 같은 건 랭킹과 무관한 용도. RankingService 안에 넣으면 랭킹과 관계없는 metrics 조회까지 RankingService를 거쳐야 하는 어색한 구조가 됨.

**[답변]**
> 그러네 그게 맞을거 같아

**[정리]**
- Consumer에서 Redis 직접 호출 → 레이어 건너뜀, 아키텍처 위반
- Processor는 이미 이벤트의 부수 효과 처리자 → 여기서 Spring 이벤트로 또 분리하면 과도한 복잡도
- Processor(Application 계층)가 오케스트레이터 역할:
  - `ProductMetricsService.increment(...)` → DB 집계
  - `RankingService.updateScore(...)` → Redis ZSET
- 각 서비스는 자기 책임만 갖고, Processor가 조합

## Q5. Ranking API 설계 — 페이지네이션과 상품 정보 Aggregation

**[질문]**
ZSET의 `ZREVRANGE`로 페이지네이션을 어떻게 구현할 건가요? page=2, size=20이면 Redis 명령을 어떻게 날릴 건지 구체적으로 설명해보세요.

**[답변]**
> ZREVRANGE ranking:list 21 40 WITHSCORES

**[후속 질문: 인덱스 보정]**
ZREVRANGE는 0-based, inclusive. page=2, size=20이면 몇부터 몇까지?

**[답변]**
> 20 39

**[후속 질문: 상품 정보 Aggregation]**
ZREVRANGE로 가져오는 건 (productId, score) 쌍뿐. 상품명, 가격 같은 정보는 어떻게 합칠 건가요? 성능 문제는?

**[답변]**
> productId를 list로 해서 db에 IN 절로 조회해서 애플리케이션 레이어에서 response를 만들거 같아.

**[후속 질문: DB 부하 격리와의 모순 — 악마의 변호인]**
Q1에서 Redis를 선택한 이유가 DB 부하 격리였는데, 매 랭킹 조회마다 DB를 치면 결국 DB에 부하가 가는 거 아닌가요? 프로젝트의 ProductCacheManager를 활용할 수 있지 않나요?

**[답변]**
> ProductCacheManager를 이용해서 조회하면 좋을거 같아. 로컬캐시/redis 캐시를 이용하기 때문에 성능에 이점도 있고, cache stampede 현상은 스케줄러로 방어하면 좋을거 같아

**[후속 질문: 응답 순서 보장]**
ZREVRANGE의 랭킹 순서와 캐시 조회 결과의 순서가 같다는 보장이 있나요?

**[답변]**
> ProductCacheManager에서 캐시 key를 productId를 사용하면 쉽게 판단할 수 있다고 생각되요

**[정리]**
- 페이지네이션: `ZREVRANGE key (page-1)*size page*size-1 WITHSCORES` (0-based, inclusive)
- 상품 정보: ProductCacheManager(로컬/Redis 캐시)로 조회 → DB 부하 방지
- 순서 보장: ZSET에서 받은 ID 순서대로 캐시 조회하면 랭킹 순서 유지
- Cache stampede 방어: 스케줄러로 캐시 워밍

## Q6. 상품 상세의 랭킹 정보 — ZREVRANK

**[질문]**
상품 상세 조회 시 "이 상품은 현재 N위입니다"를 추가해야 해요. ZSET에서 특정 상품의 순위를 조회하려면 어떤 명령을 쓸 건가요? 랭킹에 진입하지 못한 상품은 어떻게 처리할 건가요?

**[답변]**
> ZREVRANK key member을 사용하고, 랭킹에 진입하지 못한 상품은 ZREVRANK 명령에서 -1이 나올것이다. -1이면 비즈니스로 어떻게 처리할지 정해지면 그에 맞게 반환하면 된다.

**[후속 질문: ZREVRANK의 실제 반환값]**
ZREVRANK에서 member가 ZSET에 없으면 정말 -1을 반환하나요?

**[답변]**
> 모르겠다

**[멘토 보충: nil(null) 반환]**
Redis `ZREVRANK`는 member가 없으면 `nil`(null)을 반환. -1이 아님. Spring Data Redis의 `reverseRank()`도 `Long?`(nullable) 반환. 프로젝트의 `OrderQueueRedisRepository.getPosition()`에서도 `rank()` 결과를 `Long?`으로 처리하고 있음.

**[정리]**
- `ZREVRANK key member`: 특정 상품의 순위 조회 (0-based)
- member가 없으면 null 반환 (not -1)
- Kotlin에서 `Long?`로 받아 null 체크로 처리

## Q7. TTL 전략

**[질문]**
ZSET의 TTL을 2일로 설정하라고 되어 있는데, 일별 키를 쓰면서 TTL이 1일이 아니라 2일인 이유는? TTL은 언제 설정할 건가요?

**[답변]**
> 우선 만들고자 하는게 일별 랭킹이라는걸 짚고 넘어가자. 랭킹 데이터는 언제 정확히 만들어진다는 약속을 할 수 없다. 데이터가 많으면 많아질 수록 더 오래걸린다. 그렇게 때문에 다음날 00시 00분에 정확히 그날 데이터를 조회하면 없을 수 있기 때문에 그리고 데이터를 만들다가 오류가 날 수 있기 때문에 1일의 여유를 가지는 ttl 을 설정한다

**[후속 질문: Score Carry-Over와의 관계]**
Score Carry-Over(`ZUNIONSTORE ranking:all:20260409 1 ranking:all:20260408 WEIGHTS 0.1`)가 실행되려면 전날 키가 아직 살아있어야 하는데, TTL이 정확히 1일이었으면 전날 키가 만료될 수 있다. TTL 2일이 어떤 의미를 갖는 거죠?

**[답변]**
> 그거도 의미가 있겠네요. 전날 데이터에 가중치 0.1을 곱하고 나온 값에 지금 새로 생성할 데이터를 더하는 과정. 이거까지 미쳐 생각하지 못했습니다.

**[후속 질문: TTL 설정 타이밍]**
ZINCRBY로 점수를 올릴 때마다 TTL을 설정할 건지, 키가 처음 생성될 때 한 번만 설정할 건지?

**[답변]**
> 처음 생성될때 ttl 설정만 하고 이후 ZINCRBY 에서는 ttl 갱신은 하지 않을 것이다. 이유는 이미 ttl 은 2일 이라는 충분한 여유가 있고, 점수를 올릴때 마다 ttl을 갱신하게 되면 최대 3일동안 랭킹이 살아있게 되므로 불필요한 데이터가 redis 메모리를 차지하게 된다

**[후속 질문: 키 생성 책임과 동시성]**
Consumer가 ZINCRBY를 날리는데, 여러 Consumer 인스턴스가 동시에 같은 날짜의 첫 이벤트를 처리할 수 있다. "키가 처음 생성될 때"를 어떻게 판단하고, TTL 설정이 중복/누락되지 않으려면?

**[답변]**
> 스케쥴러나 배치를 사용해서 키 생성(Score Carry-Over + TTL)을 담당하고, Consumer 인스턴스에서는 랭킹 업데이트(ZINCRBY)만 한다. Consumer에서 데이터를 생성하면 랭킹 계산으로 쓰레드를 잡아먹어 같은 애플리케이션의 다른 기능에 영향을 줄 수 있다. 만약 다음 날짜의 key가 아직 없더라도 Redis는 ZINCRBY 시 자동 생성하므로 문제없다.

**[후속 질문: 스케줄러 장애 시 TTL 누락]**
스케줄러가 장애로 실패하면 키가 TTL 없이 ZINCRBY로 자동 생성될 수 있는데, 이 상황을 어떻게 방어할 건가요?

**[답변]**
> 이것은 운영의 관점이라 생각해. 스케줄러 장애를 수정하면 redis key에 ttl 설정을 하면서 업데이트할 것이다. 모든 에러에 방어 로직을 만들면 좋지만, 스케줄러 에러 상황은 서버 다운/db 다운/redis 네트워크 오류 등이고, 기본적으로 스케줄러에 재시도 처리가 있을 것이다.

**[멘토 보충: 저비용 방어 패턴]**
운영 레벨 대응은 현실적인 판단. 추가로 Consumer의 ZINCRBY에서 Lua 스크립트로 "TTL이 없으면 설정"하는 방어 로직은 한 줄짜리 조건문이라 복잡도가 거의 없으므로, 저비용 방어 패턴으로 알아두면 좋음.

**[정리]**
- TTL 2일인 이유: (1) 데이터 생성 타이밍 불확실성 + 장애 대응 여유 (2) Score Carry-Over 시 전날 키가 살아있어야 함
- TTL 설정 타이밍: 키 생성 시 한 번만. ZINCRBY마다 갱신하면 최대 3일 생존 → 메모리 낭비
- 키 생성 책임: 스케줄러가 Score Carry-Over + TTL 담당, Consumer는 ZINCRBY만
- 스케줄러 장애 방어: 운영 레벨 재시도로 대응 + Lua 스크립트 저비용 방어 패턴 가능

## Q8. ZSET 메모리와 Top-N 전략

**[질문]**
상품이 10만 개라고 가정할 때, 모든 상품의 점수를 하나의 ZSET에 넣으면 메모리를 얼마나 쓸까요? 10만 개를 다 ZSET에 유지할 필요가 있을까요?

**[답변]**
> zset은 120바이트이고, 10만개라면 120mb 일것이다. 그리고 10만개를 모두 zset에 넣을 필요 없다고 생각된다. 처음 top 100을 넣고 다음 계산에서 만약 101개라면 다음 계산에서 101개를 넣고 하면 될것이라 판단된다. 주로 랭킹에 올라오는 상품은 유지될 확률이 높기 때문에 누적 형식으로 가면 좋을거 같다

**[후속 질문: Top N만 유지하면?]**
Consumer가 이벤트를 받아서 ZINCRBY를 날릴 때, 그 상품이 현재 top 100 안에 있는지 아닌지를 어떻게 판단할 건가요? 지금 101위인 상품에 주문 이벤트가 5건 들어오면 1위가 될 수도 있는데, 그 이벤트를 버리면?

**[답변]**
> 너가 말한게 맞는거 같아. 101위 상품에 대한 계산도 해야하니 모든 상품을 담는 형식으로 가도 괜찮을거 같아.

**[후속 질문: 메모리 계산 보정]**
120 bytes × 100,000 = 12,000,000 bytes = 약 12MB. 120MB가 아님.

**[정리]**
- ZSET 엔트리당 약 120바이트, 10만 개 = 약 12MB → Redis에서 부담 없는 수준
- Top N만 유지하면 랭킹 진입 기회를 차단하는 문제 발생 + 판단 로직의 복잡도 증가
- 모든 상품을 ZSET에 넣는 것이 단순하고 정확한 전략

## Q9. Top-N 캐싱 전략

**[질문]**
랭킹 API에서 매 요청마다 ZREVRANGE로 Redis를 치는 것과, 주기적으로 Top-N 결과를 캐싱해두고 제공하는 것 — 어떤 트레이드오프가 있을까요? 홈 메인의 "오늘의 인기 상품 Top 10"이 초당 1,000번 요청된다고 가정하면?

**[답변]**
> 비즈니스에 따라 다를거 같아. 랭킹이 중요한 비즈니스라서 실시간성 랭킹이라면 캐시를 하는거 보다 redis에서 바로 조회할거야. redis에서 바로 조회한다고 해서 캐시에서 바로 꺼내느거와 큰 차이가 없을거라 생각해. 하지만 준실시간성으로 캐시에 설정된 ttl 만큼 오차가 있어도 된다고 한다면 캐시를 사용할거 같아.

**[후속 질문: 로컬 캐시 vs Redis — 악마의 변호인]**
Redis도 결국 네트워크 I/O가 필요하다. 초당 1,000번이면 1,000번의 네트워크 왕복. ProductCacheManager처럼 로컬 캐시(Caffeine)를 쓰면 네트워크 없이 메모리에서 바로 꺼내는데, 이 둘의 차이가 정말 무시할 수준인가?

**[답변]**
> 로컬 캐시는 또 다르지. 나의 기준은 redis 였어. 로컬캐시라면 캐시 사용도 괜찮다고 생각해. ProductCacheManager에서 구현한 것 처럼 로컬캐시의 ttl을 짧게 가져가고, redis 캐시에서 가져와 갱신한다고 하면 좋을거 같아.

**[정리]**
- 실시간 랭킹이 필수라면 Redis ZREVRANGE 직접 조회도 가능
- 초당 수천 QPS 환경에서는 로컬 캐시(Caffeine, 짧은 TTL) → Redis ZSET fallback 구조가 네트워크 I/O 절감에 효과적
- ProductCacheManager의 로컬캐시 + Redis 캐시 패턴을 랭킹에도 동일하게 적용 가능

## 핵심 개념 정리

1. **ZSET 선택 근거**: 읽기 비중이 압도적인 랭킹 유스케이스에서, 쓰기 시점에 O(logN) 정렬을 완료하는 ZSET이 DB ORDER BY 대비 유리. DB 부하 격리 효과.
2. **일별 키 전략**: 롱테일 방지 + 히스토리 보존. TTL 2일로 Score Carry-Over 의존성과 장애 대응 여유 확보.
3. **가중치 합산**: view=0.1, like=0.2, order=0.7 × log(price × quantity). "인기"의 정의에 따라 설계가 달라지는 트레이드오프.
4. **아키텍처**: Processor(Application 계층)가 ProductMetricsService + RankingService를 조합. 각 서비스는 단일 책임.
5. **캐싱 전략**: 랭킹 목록은 로컬 캐시(짧은 TTL) → Redis ZSET fallback. 상품 정보는 ProductCacheManager 활용.
