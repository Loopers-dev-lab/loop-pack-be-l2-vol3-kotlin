## Q1. 테스트 피라미드 — E2E만으로 충분한가?

**[질문]**
"단위 테스트를 가장 많이, E2E 테스트를 가장 적게 작성해야 한다"고 하는데, 왜 그래야 할까요? E2E 테스트만으로 모든 걸 검증한다면 어떤 문제가 생기는지 구체적인 시나리오로 설명해 주세요.

**[답변]**
> - E2E 테스트만 진행한다면 심리적으로 성공 케이스만 검증할 확률이 매우 높을거 같습니다.
> - E2E 테스트는 블랙박스 테스트와 같다고 생각됩니다. 인풋/아웃풋 만 검증하는 경우가 많을겁니다.
> - 실제 운영환경과 같은 환경을 만들기가 어렵습니다. 만약 로컬에서 h2 를 실행하여 e2e 테스트를 진행한다면 실제 mysql 에서 환경과 다르기 때문에 테스트에서는 없던 에러가 발생할 수 있습니다.
> - 잘 못 환경을 나누면 실제 운영 db에서 테스트를 실행하여 장애를 발생 시킬 수 있습니다.

**[후속 질문: 성공 케이스 편향은 E2E만의 문제인가?]**
"성공 케이스만 검증할 확률이 높다"는 건 E2E만의 문제일까요? 단위 테스트에서도 같은 문제 아닌가요? 그리고 "블랙박스라서 인풋/아웃풋만 검증한다"는 게 구체적으로 어떤 상황에서 문제가 되나요?

**[답변]**
> e2e 테스트는 말 그대로 end-to-end 테스트로 시작점과 끝점을 테스트하는 과정으로 내부에서 어떤 절차를 가지는지 알 필요가 없는 테스트라고 생각된다.
> 1+1=2 인 것처럼 정답만 필요한 테스트라고 생각되고, 만약 1+1=3 이면 왜 실패인지 내부를 살펴봐야 하는데 과연 이 과정이 e2e 테스트에서 원하는 결과이고, 과정일까? 라고 생각된다. 그래서 e2e 테스트에서 성공 케이스만 검증하는 심리적 편향이 크다고 생각된다.
> 물론 단위 테스트에서도 성공 케이스만 할 수 있지만, 단위 테스트는 작은 함수를 테스트하기 때문에 엣지 케이스가 바로 눈에 보이기에 실패 테스트 검증을 하기 수월하다고 생각된다.
>
> 회원가입 테스트에서 아이디 정규화, 비밀번호 정규화, 이용약관 검증, 인증 여부 등 검증할 절차가 많은데 e2e에서 이 모든 실패 테스트를 검증해야 한다는것은 e2e 테스트에서 모든 비즈니스를 알아야 한다는것인데, e2e 테스트의 본질일까 라는 생각이 든다. 그리고 e2e 테스트의 볼륨이 매우 커지게 된다. 이런 테스트는 통합 테스트에서 검증하는게 좋다고 생각이 든다.

**[후속 질문: 정규화 검증은 통합 테스트가 맞나?]**
비밀번호 패턴 검증 같은 건 스프링 컨텍스트나 DB가 필요한 작업인가요?

**[답변]**
> 제가 잘못 말했네요 정규화는 단위테스트에서 하는게 좋습니다.

**[정리]**
- E2E 테스트는 블랙박스 특성상 실패 원인 추적이 어렵고, 성공 케이스 편향이 강해진다
- 단위 테스트는 작은 범위라 엣지 케이스가 눈에 잘 보여 실패 검증이 수월하다
- 각 검증의 성격에 따라 적절한 테스트 레벨을 선택해야 한다: 순수 값 검증 → 단위, 비즈니스 흐름 → 통합, 전체 시나리오 → E2E
- E2E에 모든 비즈니스 규칙을 넣으면 테스트 볼륨이 폭발하고 본질에서 벗어난다

## Q2. Stub과 Mock의 핵심 차이

**[질문]**
Stub과 Mock의 핵심 차이가 뭔가요? "상태 기반 vs 행위 기반"이라는 정의를 넘어서, 테스트에서 검증하려는 것 자체가 어떻게 다른지 설명해 주세요.

**[답변]**
> stub은 내가 구현한 코드대로 값을 반환하는 것에 초점이 있습니다.
> stub은 테스트 검증을 위해 미리 지정해놓은 값을 반환합니다.
> 반환된 값에 초점을 맞추어 검증합니다.
>
> mock은 특정 메소드(행동)을 지정하고, 의도대로 수행되었는지 검증합니다.

**[후속 질문: verify 없이 반환값만으로 충분한가?]**
프로젝트의 회원가입 테스트에서 `whenever(save).thenReturn`은 Stub, `verify(save)`는 Mock인데 — verify를 빼고 반환값만 검증해도 충분하지 않나요? 반대로 verify만 있고 thenReturn이 없어도 되는 건 아닌가요?

**[답변]**
> 잘 모르겠다 → 힌트 요청 ("부수 효과" 키워드 제공) → 알려달라 요청

**[정리 — 멘토 설명]**
- **Stub (thenReturn)**: 테스트가 동작할 수 있게 흐름을 제어하는 "환경 설정" 역할. 없으면 반환값이 null이 되어 테스트 자체가 깨짐
- **Mock (verify)**: 반환값으로 확인할 수 없는 부수 효과(DB 저장, 이벤트 발행 등)가 실제로 발생했는지 검증. 없으면 핵심 동작이 빠져도 테스트가 통과할 위험
- Stub은 "환경 설정", Mock은 "눈에 안 보이는 행위의 검증"
- 반환값으로 확인 가능한 것 → Stub 충분, 부수 효과 → verify 필요

## Q3. Fake vs Mock — 어떤 기준으로 선택하나?

**[질문]**
이 프로젝트에서는 Fake 대신 Mockito의 mock()으로 Repository를 대체하고 있는데, Fake와 Mock 중 어떤 걸 쓸지는 어떤 기준으로 결정하나요? `InMemoryUserRepository`로 바꾸면 어떤 게 달라질까요?

**[답변]**
> Fake 를 사용했을 때 장점은 빠른 테스트 피드백 확인, 외부 라이브러리나 인프라 미 의존
> 단점은 fake 객체를 만든다는게 stub과 다르게 stub은 반환값이 정해진 반면, fake는 객체 내부에서 동작까지 합니다. 그래서 fake 객체에서 잘못된 값을 반환할 수 있습니다. 그리고 fake 객체를 구현하는 시간이 생각보다 오래 걸릴 수 있습니다. 오히려 배보다 배꼽이 더 커질 수도 있습니다.
> 그래서 개인적으로 fake 객체보다는 mock 사용을 선호합니다.

**[후속 질문 (악마의 변호인): Mock에는 문제가 없나?]**
Mock을 선호한다고 했는데, 테스트가 10개, 20개로 늘어나면 stub 설정들은 어떻게 되나요? 내부 로직 변경 시 Fake가 오히려 유리한 상황이 있지 않을까요?

**[답변]**
> 테스트가 10개, 20개 늘어나게 된다면 mock 설정에서 중복이 발생할 것입니다. 그렇다면 리팩토링을 통해 공통 함수를 만들어 해결할 수 있습니다.
> 그리고 내부 로직이 변경된다면 mock이나 stub, fake도 추가 구현이 필요할텐데 구현에 있어 어떤게 유리하고 불리하다라는 관점에서 벗어나는게 좋다고 생각이 듭니다.

**[멘토 반론: 내부 구현 결합도]**
- Mock: `findByLoginId()` 추가 시 모든 관련 테스트에 `whenever()` 추가 필요. 테스트가 내부 구현(어떤 메서드를 호출하는지)에 결합됨
- Fake: 이미 구현이 있으므로 테스트 코드 변경 없이 통과. 내부 구현 변경에 덜 민감

**[정리]**
- **Mock 선호**: 상호작용을 정밀하게 통제하고 싶을 때, 구현이 안정적일 때
- **Fake 선호**: 내부 구현이 자주 바뀌고, 테스트가 구현 세부사항에 결합되는 걸 피하고 싶을 때
- `[글감]` Mock vs Fake — 내부 구현 결합도 관점에서의 트레이드오프

## Q4. 왜 UserRepository 인터페이스를 두는가?

**[질문]**
왜 `UserService`가 `UserJpaRepository`를 직접 의존하지 않고, 중간에 `UserRepository` 인터페이스를 두는 건가요? "테스트 가능성" 외에 다른 이유도 있을까요?

**[답변]**
> UserService 내부 구현이 자주 바뀌게 되어, fake 테스트를 한다고 했을 때, UserRepository 인터페이스를 사용한다면 단순하게 몇개의 함수만 재정의 하면될 것이고, 만약 인터페이스의 크기가 크다면 인터페이스 분리를 통해 작게 만들거나, UserService에서 사용하는 함수만 있게하고, 나머지는 다른 인터페이스에 둘 수 있지.
> 하지만 UserJpaRepository를 직접 사용한다면 정말 많은 함수를 재정의 해야하고, 불필요한 함수들까지 의존받기 때문에 혼란만 줄 수 있어.
> 그리고 SOLID 원칙의 ISP 원칙에 위배되어서 좋지않아

**[후속 질문: 테스트 외의 이유는?]**
지금 답변은 다 테스트 관점인데, `UserRepository`가 domain 패키지에 있고 `UserJpaRepository`가 infrastructure 패키지에 있는 이유는?

**[답변]**
> 지금은 jpa를 사용하지만 만약 mybatis를 사용한다면? mysql를 사용하지만 redis나 mongodb를 사용한다면? UserRepository를 사용한다면 UserService 내부 코드는 수정하지 않고 UserRepositoryImpl 내부만 수정하면 되지만, UserJpaRepository를 직접 사용한다면 UserService 내부 코드를 수정하게 되므로 좋지 못합니다.

**[정리]**
- **테스트 관점 (ISP)**: Fake/Mock 구현이 쉽고, 불필요한 메서드에 의존하지 않음
- **아키텍처 관점 (DIP)**: 인프라 기술 변경 시 도메인 코드 변경 없음
- 이 프로젝트에서는 ArchUnit으로 레이어 간 의존성 방향을 테스트로 강제
- `[글감]` DIP — 테스트 가능성과 아키텍처 유연성, 두 마리 토끼

## Q5. TDD Red 단계 — 비밀번호 검증 테스트 설계

**[질문]**
TDD로 비밀번호 검증을 구현한다면, Red 단계에서 어떤 테스트 케이스들을 먼저 작성하겠어요? 순서와 함께 설명해 주세요.

**[답변]**
> 8~16자의 영문 대소문자, 숫자, 특수문자만 가능을 먼저 확인하고, 생년월일 포함 여부를 확인할 것이다. 이유는 생년월일은 DB 조회가 필요하므로 비용이 큰 검증을 나중에 하기 위해서.

**[후속 질문: 생년월일 검증에 DB 조회가 필요한가?]**
Password를 Value Object로 설계하면 회원가입 요청에 이미 생년월일이 포함되어 있으므로 DB 조회 없이 검증 가능하지 않은가? 그리고 테스트 케이스를 좀 더 세분화해서 얘기해 달라.

**[답변]**
> 정규식을 사용해 검증할 것이고, 8~16자, 영문 대소문자, 숫자, 특수문자의 모든 조건을 하나씩 테스트로 만들어서 각각 검증할 것입니다

**[후속 질문: 테스트를 한꺼번에 다 작성하나? 하나씩 하나?]**
Red 단계에서 모든 테스트를 한번에 작성하나요, 하나씩 작성하면서 Green을 반복하나요?

**[답변]**
> 한번에 모든 테스트를 작성하고 green 단계로 갈 것입니다. 이유는 비밀번호의 조건은 or 조건이 아니라 and 조건이기 때문입니다.

**[후속 질문 (악마의 변호인): 처음부터 정규식으로 가는 것은?]**
하나씩 가면 정규식은 Refactor 단계에서 자연스럽게 등장하는데, 모든 테스트를 먼저 쓰면 이미 "정규식으로 구현하겠다"고 결정한 상태. "가장 단순한 구현으로 통과시킨다"는 원칙과 어떤 차이가 있나?

**[답변]**
> "가장 단순한 구현으로 통과시킨다"와 "처음부터 정규식으로 간다"의 차이는 개인 능력의 차이라고 생각됩니다. 정규식을 통달한 사람이라면 간단하게 구현하지 않을까요? TDD의 가장 단순한 구현으로 통과시킨다는 것은 방법론이지 절대적인 규칙이라고 생각하지 않습니다.

**[멘토 코멘트]**
- 실용적 관점에서 일리 있으나, 핵심은 능력 차이가 아니라 **실패 시 디버깅 범위를 얼마나 좁힐 수 있느냐**
- 모든 테스트 한꺼번에 + 정규식 → 여러 테스트 실패 시 원인 파악 어려움
- 하나씩 → 방금 추가한 테스트 하나만 실패하므로 원인이 명확
- 절대적 규칙은 아니며 상황에 따라 유연하게 가는 것도 실력

**[정리]**
- Red 단계에서는 각 조건별로 테스트를 분리하여 작성
- TDD의 한 번에 하나씩 사이클은 디버깅 범위를 좁히는 실용적 이점이 있음
- 단, 방법론은 유연하게 적용할 수 있으며 상황과 숙련도에 따라 조절 가능
- `[글감]` TDD의 "가장 단순한 구현" — 방법론 vs 절대 규칙, 실무에서의 균형

## Q6. Password VO의 책임 범위

**[질문]**
`Password`라는 Value Object가 `birthday`를 알아야 하는 게 맞을까요? 비밀번호의 본질적인 책임(형식 검증)과, "생년월일을 포함하면 안 된다"는 비즈니스 규칙 — 이 둘을 같은 객체에서 처리하는 것에 대해 어떻게 생각하세요?

**[답변]**
> 이미 문제에 답이 나와 있다고 생각된다. "생년월일을 포함하면 안 된다"는 비즈니스 규칙이기 때문에 Password.kt에 있어야 된다고 생각된다. Password.kt에 없고 다른 validated 파일에서 한다고 하면 비즈니스 규칙이 분산된다고 생각된다.

**[후속 질문: 규칙이 늘어나면?]**
"비밀번호에 전화번호도 포함하면 안 된다", "로그인 ID도 포함하면 안 된다"는 규칙이 추가되면 `Password.of(rawPassword, birthday, phoneNumber, loginId)` 이렇게 되는 건가요?

**[답변]**
> 규칙이 추가된다는것은 Password의 응집도를 더 높여야 되는 상황인거고, 확장성을 키울 수 있는 방향으로 코드를 수정하면 된다고 생각된다.

**[후속 질문: 응집도의 방향]**
Password가 알아야 하는 정보가 birthday, phoneNumber, loginId로 점점 늘어나는 게 — 정말 Password의 응집도를 높이는 방향인가요, 아니면 오히려 Password와 관련 없는 정보가 흘러들어오는 방향인가요?

**[답변]**
> 생각해보자. 만약 비밀번호 비즈니스에 생년월일 정보 포함 여부 상관없었다고 하면 Password.of(rawPassword, birthday) 함수가 필요했을까? Password의 책임과 역할은 올바른 비밀번호인지 검사하는 책임도 있다고 생각된다. 그리고 그게 비즈니스라고 생각된다.

**[후속 질문: 자기 완결적 검증 vs 외부 의존 검증]**
Password가 하는 검증 중 "8~16자, 대소문자, 숫자, 특수문자"는 rawPassword만으로 가능하고, "생년월일 포함 불가"는 외부 정보(birthday)가 필요합니다. 이 두 성격의 검증이 같은 곳에 있어야 할까요?

**[답변]**
> 너가 말하고자 하는거는 회원 도메인에서 하는게 어떨까? 라고 하는거 같아. 나도 그거에 대해 고민 했어. 하지만 나의 선택은 password에서 하는게 좋다고 생각했어. 이유는 user 도메인을 거쳐야 완전한 비밀번호 검증이 끝나는 거잖아. 만약 password만 따로 사용한다면? 그러면 password 검증은 완전히 되지는 않을거야. 그래서 나는 password에서 모든 검증을 하자고 생각했어.

**[후속 질문 (악마의 변호인): 비밀번호 변경 시나리오]**
Password.of를 호출하려면 birthday를 넘겨야 하는데, 비밀번호 변경 시 birthday를 어디서 가져오나요? 그 흐름이 자연스러운가요?

**[답변]**
> 생년월일은 user에서 가져오기 때문에 흐름을 생각하면 너의 의도가 맞기는 해. 근데 그거는 단순히 코드 흐름만 생각하면이고, 우리는 단순히 코드만 하는게 아닌 유지보수와 주변 팀으로 일하기 때문에 Password.of(newPassword, birthday) 이렇게 코딩을 하면 나말고 다른 팀원이 금방 알 수 있지 않을까?

**[후속 질문: 규칙 폐지 시나리오]**
"생년월일 포함 불가" 규칙이 폐지되면 Password.of 시그니처가 바뀌고 모든 호출처를 수정해야 하는데, 이건 어떻게 생각해요?

**[답변]**
> 그럼 이건 어때 user 도메인에 Password.of(rawPassword, birthday) 이 함수 사용을 넣는거는?
> Password 자체의 변경은 없어. user 생성자에서 Password.of(rawPassword, birthday)를 호출한다면 birthday 받는거도 처리가능하고, 다 해결 가능하다고 생각돼.

**[후속 질문: 호출 위치만 옮긴 건 아닌지?]**
이 방식은 Password 자체의 설계는 그대로 두고 호출 위치만 User 안으로 옮긴 거잖아요. 규칙 폐지 시 Password 시그니처 변경은 여전히 필요하지 않나요?

**[답변]**
> Password는 변경되어야 하는거지 왜냐면 비즈니스가 변경된거잖아. 코드는 결국 비즈니스 즉 요구사항에 맞게 구현 해야 하는거 아닐까?

**[정리]**
- **사용자의 설계 판단**: Password는 비밀번호 비즈니스 규칙의 주인. 형식 검증이든 생년월일 포함 여부든 비밀번호에 관한 규칙은 Password가 담당
- **호출 위치**: User에서 Password.of를 호출하면 birthday를 자연스럽게 넘길 수 있고, 외부 호출자는 birthday를 몰라도 됨
- **비즈니스 변경 시 코드 변경은 당연** — 변경 자체를 회피하는 게 목표가 아니라, 변경의 영향 범위를 합리적으로 관리하는 게 목표
- **반대 관점**: Password를 형식 검증만 하는 순수 VO로 두고, 교차 검증은 도메인 서비스나 User에서 처리하면 재사용성과 독립성이 높아짐
- 정답이 있는 문제가 아니라 팀 컨텍스트와 비즈니스 복잡도에 따른 트레이드오프
- `[글감]` VO의 책임 범위 — 비즈니스 규칙은 어디까지 VO에 넣어야 하는가?

## Q7. 통합 테스트 — 무엇을 검증해야 하는가?

**[질문]**
`UserService`의 회원가입 기능을 통합 테스트로 검증한다면, 단위 테스트에서 이미 Password 형식, Email 형식, 이름 검증 등을 다 했는데, 통합 테스트에서는 무엇을 검증해야 하나요? 단위 테스트와 겹치면 안 되나요?

**[답변]**
> 이게 항상 고민이야. 단위 테스트에서 모든걸 검증 했는데 통합 테스트에서도 해야하나? 라고. 근데 우리가 잘 아는 테스트 피라미드를 생각해 보면 나는 정말 중요한 실패 검증이 아니라면 넘어가도 된다고 생각해.

**[후속 질문: 단위 테스트에서 절대 검증할 수 없는 것?]**
단위 테스트에서는 절대 검증할 수 없는데 통합 테스트에서만 잡을 수 있는 것 — 회원가입 흐름에서 어떤 게 있을까요?

**[답변]**
> 데이터의 흐름, 함수 호출, 파라미터 전달, 데이터 일관성 등을 보는게 통합 테스트라고 생각해.

**[후속 질문: 구체적으로 3가지만?]**
"데이터 흐름, 함수 호출, 파라미터 전달"은 단위 테스트에서 Mock/Stub으로도 검증할 수 있지 않나요? 통합 테스트에서만 잡을 수 있는 것의 핵심은 실제 인프라와 연결되었을 때 발생하는 문제입니다. 구체적으로 3가지만 꼽아보세요.

**[답변]**
> db에 정확히 회원 데이터가 들어가 있는지, 회원 아이디나 다른 데이터의 중복 검사를 잘 하는지. 이 2가지만 생각나네.

**[멘토 보충: 비밀번호 암호화 흐름]**
단위 테스트에서 `whenever(passwordEncoder.encode(...)).thenReturn("encoded")`로 stub했다면, 실제로 encode된 값이 DB에 저장되는지, 나중에 로그인할 때 그 값으로 matches가 되는지는 통합 테스트에서만 검증 가능

**[정리]**
- 통합 테스트의 핵심: **단위 테스트에서 stub으로 대체한 부분이 실제 인프라에서도 의도대로 작동하는지** 검증
- 회원가입 통합 테스트 필수 항목:
  1. DB에 회원 데이터가 정확히 저장되는지 (실제 insert 동작)
  2. 중복 검사가 실제 DB에서 작동하는지 (unique 제약, 조회 쿼리)
  3. 비밀번호 암호화 → 저장 → 검증 흐름 (encode된 값 저장, matches 성공)

## Q8. TDD Refactor 단계 — 언제, 무엇을 리팩토링하는가?

**[질문]**
Red → Green을 마치고 테스트가 통과하는 상태입니다. Refactor 단계에서 "리팩토링해야 할 것"을 어떻게 판단하나요? 동작도 하고 테스트도 통과하는데 굳이 왜 건드려야 하죠?

**[답변]**
> 보통 보는건 중복 코드 검사, 함수나 필드명 검사, 만약 통합테스트와 e2e 테스트도 red에 포함된다면 트랜잭션 관련 기능도 검사할 수 있어

**[후속 질문: 트랜잭션 검사는 리팩토링인가?]**
트랜잭션이 제대로 동작하는지 확인하는 건 리팩토링인가요, 아직 Green 단계에서 끝내지 못한 기능 검증인가요? Refactor 단계의 핵심 원칙이 뭐라고 생각해요?

**[답변]**
> 내가 말한거는 하나의 트랜잭션에서 원자성을 확보하나, 아니면 부수적인 코드라 따로 트랜잭션으로 관리하냐, 이것을 의도했어.
> 리팩토링은 기능에 영향이 안가는 상태로 구조적 변경만 하는거라 생각해.

**[후속 질문: Refactor를 하면 안 되는 타이밍?]**
Refactor를 하면 안 되는 타이밍이 있을까요? 어떤 상태에서만 리팩토링을 해야 안전한가요?

**[답변]**
> Refactor를 하면 안 되는 타이밍은 잘 모르겠네.. 이거는 알려줘
> 리팩토링 안전은 당연히 주기적인 테스트코드 실행에 있다고 생각해

**[정리 — 멘토 설명]**
- Refactor의 핵심: **동작은 그대로, 구조만 개선**
- 리팩토링 대상: 중복 코드, 네이밍, 책임 분리 (트랜잭션 경계 분리 등)
- **Refactor를 하면 안 되는 타이밍 = 테스트가 깨져있을 때** — Green이 확보되지 않은 상태에서 리팩토링하면 실패 원인을 구분할 수 없음
- 모든 테스트가 통과하는 상태에서만 리팩토링을 시작하고, 리팩토링 후에도 테스트가 통과해야 함
- Q5와 연결: TDD 사이클은 디버깅 범위를 좁히는 장치. Refactor도 Green 위에서만 해야 리팩토링에 의한 실패를 바로 식별 가능
