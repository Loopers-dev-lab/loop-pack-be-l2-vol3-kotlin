## TL;DR

일간 랭킹은 Redis ZSET으로 충분했지만, 주간과 월간 랭킹은 요청 시점에 다시 계산하지 않고 `product_metrics`를 일자별로 쌓은 뒤 Spring Batch가 조회 전용 테이블로 압착하는 방식이 더 맞다고 판단했습니다.

## 🧭 왜 Redis 랭킹만으로는 부족했을까요?

지난 단계의 일간 랭킹은 이벤트가 들어올 때마다 Redis 점수를 갱신하는 방식이었습니다.
좋아요, 조회, 주문 이벤트가 발생하면 바로 점수에 반영되기 때문에 사용자에게는 빠른 피드백을 줄 수 있습니다.

하지만 주간과 월간 랭킹까지 같은 방식으로 처리하려고 하면 문제가 달라집니다.
일간 점수 하나만 보면 단순한 ZSET 갱신이지만, 주간 랭킹은 여러 날짜의 지표를 다시 합쳐야 하고 월간 랭킹은 그 범위가 더 넓어집니다.
요청마다 `product_metrics`를 읽고 상품별 점수를 계산하면 API가 집계 엔진 역할까지 떠안게 됩니다.

그래서 API는 이미 계산된 결과를 읽고, 계산은 Batch가 맡도록 경계를 나눴습니다.
이 판단의 기준은 실시간성이 아니라 비용이었습니다.
주간과 월간 랭킹은 몇 초 안에 바뀌는 값보다 안정적으로 조회되는 값에 가깝기 때문에, 미리 만들어 둔 결과를 읽는 쪽이 더 낫다고 봤습니다.

📌 **포기한 것**

주간과 월간 랭킹이 이벤트 직후 즉시 바뀌는 경험은 포기했습니다.
대신 API 요청마다 대량 집계를 수행하지 않는 구조를 얻었습니다.

## 🧱 왜 `product_metrics`에 `bucket_date`를 넣었을까요?

처음에는 상품별 누적 카운터만 있어도 랭킹을 만들 수 있다고 생각하기 쉽습니다.
하지만 상품별 전체 누적값만 남기면 “이번 주”와 “이번 달”을 구분할 수 없습니다.
기간 랭킹을 만들려면 같은 상품이라도 어느 날짜에 발생한 조회, 좋아요, 주문인지가 남아 있어야 합니다.

그래서 `product_metrics`를 `product_id` 단위가 아니라 `product_id`와 `bucket_date` 조합으로 유일하게 만들었습니다.
Streamer는 이벤트의 `occurredAt`에서 날짜를 뽑아 해당 날짜 버킷에 누적하고, Batch는 `bucket_date >= 시작일`과 `bucket_date < 종료일` 조건으로 필요한 기간만 읽습니다.

이 구조에서 중요한 점은 “집계 기준”이 데이터에 남는다는 것입니다.
Batch가 주간인지 월간인지에 따라 같은 원천 테이블을 다른 기간으로 잘라 읽을 수 있고, 기간 밖 데이터가 섞이는 문제도 테스트로 확인할 수 있습니다.

📌 **포기한 것**

`product_metrics`의 row 수는 상품 수만큼이 아니라 상품 수와 날짜 수의 곱에 가깝게 늘어납니다.
대신 기간 집계의 기준을 명확하게 저장할 수 있게 됐습니다.

## 🧮 왜 Chunk 기반 Batch로 압착했을까요?

주간과 월간 랭킹은 `product_metrics`를 읽고 상품별로 합산한 뒤 상위 100개만 저장합니다.
이 작업은 요청 흐름 안에서 처리하기에는 무겁지만, Batch의 Chunk-Oriented Processing에는 잘 맞습니다.

Reader는 기간 조건이 들어간 SQL로 상품별 점수를 계산합니다.
Writer는 읽힌 순서대로 rank를 부여해서 `mv_product_rank_weekly` 또는 `mv_product_rank_monthly`에 저장합니다.
같은 기간의 Job을 다시 실행할 수 있도록 Cleanup Step을 먼저 실행해 기존 MV 데이터를 지우고, 그 다음 Aggregate Step이 새 결과를 적재하도록 했습니다.

동점 정렬도 명시했습니다.
`ORDER BY score DESC`만 두면 같은 점수의 상품 순서는 DB 실행 계획에 따라 달라질 수 있습니다.
랭킹은 숫자 자체가 사용자에게 노출되는 값이기 때문에, `product_id ASC`를 보조 정렬로 두어 같은 입력이면 같은 순서가 나오도록 했습니다.

📌 **포기한 것**

복잡한 증분 갱신은 넣지 않았습니다.
이번 구현에서는 같은 기간을 삭제 후 재적재하는 방식이 더 단순하고, 실패했을 때 다시 실행하기도 쉽습니다.

## 🧩 API는 왜 period만 추가했을까요?

기존 API는 `GET /api/v1/rankings?date=yyyyMMdd&size=20&page=1` 형태로 일간 랭킹을 제공합니다.
여기에 별도 엔드포인트를 늘리는 대신 `period` 파라미터를 추가해 `DAILY`, `WEEKLY`, `MONTHLY`를 선택하도록 했습니다.

API 소비자 입장에서는 랭킹이라는 리소스는 그대로이고 조회 기준만 바뀝니다.
그래서 `/weekly-rankings`, `/monthly-rankings`처럼 엔드포인트를 나누기보다, 같은 리소스에 기간 조건을 더하는 쪽이 자연스럽다고 봤습니다.

Application 계층은 period에 따라 저장소를 선택합니다.
일간은 Redis 기반 랭킹을 읽고, 주간과 월간은 Batch가 만들어 둔 MV 테이블을 읽습니다.
이렇게 나누면 Controller는 요청 파라미터 해석만 맡고, 어떤 저장소를 읽을지는 UseCase 안에서 결정할 수 있습니다.

📌 **포기한 것**

기간별 API를 완전히 분리했을 때 얻을 수 있는 명시성은 포기했습니다.
대신 클라이언트가 같은 응답 형태로 기간만 바꿔 조회할 수 있는 단순함을 얻었습니다.

## 🔁 다시 한다면 무엇을 더 확인할까요?

이번 구현은 학습 과제 기준으로는 필요한 경계를 갖췄지만, 운영 시스템이라면 두 가지를 더 확인해야 합니다.

먼저 Batch 실행 시점의 스냅샷 기준입니다.
현재 구조는 Batch가 읽는 동안 Streamer가 계속 `product_metrics`를 갱신할 수 있습니다.
정확히 “어느 시점까지의 데이터”인지가 중요한 서비스라면, 집계 마감 시간을 명시하거나 별도 스냅샷 테이블을 두는 쪽을 검토해야 합니다.

다음은 Schema migration입니다.
JPA entity에는 `bucket_date`와 MV 테이블 구조가 들어갔지만, 운영 DB에서는 DDL 변경과 기존 데이터 보정이 별도 작업입니다.
학습 환경에서는 테스트 컨테이너와 자동 스키마 생성으로 충분하지만, 운영에서는 이 부분이 배포 리스크가 됩니다.

📌 **포기한 것**

이번 단계에서는 운영 마이그레이션 자동화까지는 넣지 않았습니다.
과제의 초점이 Batch 집계와 MV 조회 구조였기 때문에, 먼저 기간 집계의 데이터 흐름을 완성하는 데 집중했습니다.
