# Round 8 — Redis 기반 대기열 시스템

## 배경

현재 주문 API는 모든 요청을 즉시 처리하는 구조다.
블랙 프라이데이 행사로 주문 요청이 초당 100건에서 10,000건으로 폭증하면
DB 커넥션 풀 고갈, 응답 지연, 전체 시스템 장애로 이어진다.

스케일업/아웃으로도 DB와 PG의 처리 한계는 해결할 수 없다.
하류 시스템이 감당할 수 있는 속도만큼만 상류 요청을 흘려보내는 Back-pressure가 필요하다.

Redis Sorted Set 기반 대기열 시스템을 구축하여
시스템을 보호하면서도 유저에게 공정한 대기 경험을 제공한다.

### 학습 목표

- Redis Sorted Set으로 순서 보장 대기열을 구현한다
- 입장 토큰 기반 처리량 제어(Back-pressure)를 설계한다
- Thundering Herd 문제를 이해하고 완화 전략을 적용한다
- Polling 기반 실시간 순번 조회로 유저 이탈을 방지한다

### 키워드

- 대기열 (Waiting Queue), Redis Sorted Set
- Back-pressure, Rate Limiting vs Queuing
- 입장 토큰 (Entry Token), TTL
- 순번 조회, 예상 대기 시간
- Thundering Herd, Graceful Degradation
- Polling / SSE

### 우선순위

**Must-Have**

- Redis Sorted Set 기반 대기열
- 입장 토큰 발급 & 검증 (TTL)
- 스케줄러 기반 순차 입장 처리
- Polling 기반 순번 조회 API

**Nice-to-Have**

- SSE 기반 실시간 순번 Push
- Polling 주기 동적 조절 (순번 구간별)
- Thundering Herd 완화 (발급 간격 분산 / Jitter)
- Graceful Degradation (Redis 장애 시 Fallback)

## 1. 문제 정의

### 핵심 목표

- 시스템이 처리할 수 있는 속도로 유저 요청을 조절하여 과부하 방지 (Back-pressure)
- 공정한 순서(FIFO)로 유저를 처리하여 선착순 보장
- 실시간 순번 피드백으로 대기 중 유저 이탈 최소화
- 입장 토큰 기반 진입 제어로 하류 시스템(DB, PG) 보호

### 대기열 시스템

| 관점 | 문제 |
|------|------|
| 사용자 | 트래픽 폭증 시 주문이 타임아웃되거나 실패하여 구매 경험이 끊김. 누가 먼저 요청했는지와 무관하게 운에 따라 성공/실패가 결정됨 |
| 비즈니스 | 행사 트래픽에 대한 공정한 처리 보장 필요. Rate Limiting(거부)은 유저 이탈과 재시도 폭풍을 유발 |
| 시스템 | DB 커넥션 풀 고갈, 스레드 풀 포화로 전체 서비스 장애. 스케일업/아웃으로도 DB/PG의 처리 한계는 해결 불가 |

### 입장 토큰 & 처리량 제어

| 관점 | 문제 |
|------|------|
| 사용자 | 대기 후 입장 시 제한 시간 내 주문을 완료해야 함. 토큰 만료 시 기회 상실 |
| 비즈니스 | 토큰 미사용(이탈) 시 자리 낭비를 최소화하고 다음 유저에게 기회를 넘겨야 함 |
| 시스템 | 토큰 발급 직후 Thundering Herd 발생 가능. 발급 간격 분산으로 하류 부하 평탄화 필요 |

### 실시간 순번 조회

| 관점 | 문제 |
|------|------|
| 사용자 | "내가 몇 번째인지", "얼마나 기다려야 하는지" 실시간 확인을 원함 |
| 비즈니스 | 순번이 보이지 않으면 유저가 새로고침(재시도 폭풍)하거나 이탈함 |
| 시스템 | 대기 인원 x Polling 빈도 = 서버 부하. Redis 인메모리로 감당 가능하나 동적 주기 조절 고려 필요 |

## 2. 유비쿼터스 언어

| 한글 | 영문 | 정의 |
|------|------|------|
| 대기열 | Waiting Queue | 유저 요청을 순서대로 보관하는 Redis Sorted Set 기반 자료구조 |
| 입장 토큰 | Entry Token | 대기열에서 빠진 유저에게 발급되는 주문 API 진입 권한. TTL 있음 |
| 순번 | Position | 대기열에서의 현재 위치 (0-based, ZRANK 기반) |
| 예상 대기 시간 | Estimated Wait Time | 순번 / 초당 처리량으로 추정한 대기 시간 |
| 스케줄러 | Queue Scheduler | 일정 주기로 대기열에서 N명씩 꺼내 입장 토큰을 발급하는 컴포넌트 |
| 배치 크기 | Batch Size | 스케줄러가 한 번에 대기열에서 꺼내는 인원 수 |
| 처리량 | Throughput (TPS) | 시스템이 안정적으로 처리할 수 있는 초당 주문 건수 |
| 백프레셔 | Back-pressure | 하류 시스템이 감당할 수 있는 속도만큼만 상류 요청을 흘려보내는 개념 |
| 썬더링 허드 | Thundering Herd | 토큰 발급 직후 다수 유저가 동시에 주문 API를 호출하는 현상 |
| 우아한 성능 저하 | Graceful Degradation | Redis 장애 시 서비스를 완전히 중단하지 않고 제한된 기능을 유지하는 전략 |

## 4. 유저 시나리오

### 4.1 대기열 진입 및 대기 (인증된 사용자)

**사전 조건:** 사용자가 인증됨.

**대기열 진입:**
- `POST /queue/enter` -> Redis Sorted Set에 `userId(member) + timestamp(score)` 저장
- 이미 대기열에 있는 유저는 기존 순번 유지 (Sorted Set의 Set 특성으로 중복 방지)
- 즉시 현재 순번과 예상 대기 시간을 응답

**순번 조회 (Polling):**
- `GET /queue/position` -> ZRANK로 현재 순번 조회
- 예상 대기 시간 = 순번 / 초당 처리량
- 토큰이 발급된 상태면 순번 조회 응답에 토큰 포함

**예외 흐름:**

| 조건 | 응답 | 설명 |
|------|------|------|
| 이미 대기열에 있음 | 기존 순번 응답 | 중복 진입이 아니라 현재 상태 반환 |
| 이미 토큰 보유 | 토큰 정보 응답 | 대기열이 아닌 토큰 상태를 반환 |
| 대기열에 없는 유저가 순번 조회 | 404 NOT_FOUND | 대기열 진입 안내 |

### 4.2 입장 토큰 발급 및 주문 (인증된 사용자)

**사전 조건:** 사용자가 대기열에 진입해 있음. 스케줄러가 해당 유저의 순번까지 처리.

**토큰 발급:**
- 스케줄러가 ZPOPMIN으로 대기열 앞에서 N명을 꺼냄
- 각 유저에게 입장 토큰 발급 (Redis `SET entry-token:{userId} {token} EX 300`)
- 다음 순번 조회 시 응답에 토큰이 포함되어 유저에게 전달

**주문:**
- `POST /orders` (Header: `X-Entry-Token: {token}`)
- 토큰 검증 -> 유효하면 주문 처리 -> 토큰 삭제
- 주문 이후 흐름은 R7의 이벤트 파이프라인이 그대로 동작

**예외 흐름:**

| 조건 | 응답 | 설명 |
|------|------|------|
| 토큰 없이 주문 시도 | 403 FORBIDDEN | 대기열 진입 안내 |
| 토큰 만료 (TTL 초과) | 403 FORBIDDEN | 재진입 필요 |
| 토큰 불일치 | 403 FORBIDDEN | 다른 유저의 토큰 사용 시도 |

## 5. 도메인 규칙 (Business Rules)

### 대기열 규칙

- 대기열은 Redis Sorted Set으로 구현한다. score는 진입 시각(timestamp), member는 userId.
- 동일 userId의 중복 진입은 Sorted Set 특성으로 자동 방지된다.
- 대기열 순서는 진입 시각 기준 FIFO로 보장된다.
- 대기열은 항상 활성 상태다. 모든 주문 요청은 대기열을 경유한다.
- 대기열 최대 인원은 상한선을 설정한다. 초과 시 "잠시 후 다시 시도해주세요" 응답.

### 입장 토큰 규칙

- 토큰은 Redis String으로 저장한다. Key: `entry-token:{userId}`, Value: 토큰 값.
- TTL은 5분 (300초). 만료되면 자동 삭제.
- 토큰은 1회 사용 시 삭제된다 (주문 완료 후).
- 토큰 만료 후에는 대기열 맨 뒤로 재진입해야 한다. 우선 재진입은 지원하지 않는다.
- 만료된 토큰 수만큼의 추가 발급은 스케줄러의 다음 배치에서 자연스럽게 처리된다.

### 스케줄러 규칙

- 처리량 설계 기준:
  - DB 커넥션 풀: 50
  - 주문 1건 평균 처리 시간: 200ms
  - 이론적 최대 TPS: 50 / 0.2 = 250 TPS
  - 안전 마진 70%: 175 TPS
- 스케줄러 실행 주기: 100ms마다 ~18명씩 토큰 발급 (Thundering Herd 완화)
- 1초에 175명을 한 번에 발급하지 않고 분산 발급하여 부하 평탄화

### 순번 조회 규칙

- 예상 대기 시간 = 순번 / 초당 처리량 (추정치, "약 N분"으로 표현)
- Polling 주기: 클라이언트가 2초마다 조회

## 10. 설계 결정 사항

### 대기열 항상 활성 (Q1-A)

- 모든 주문 요청은 대기열을 경유한다. 평시/행사 구분 없이 동일한 흐름을 사용한다.
- 이유: 평시에는 대기열이 비어있으므로 즉시 토큰이 발급되어 사실상 지연이 없다. 코드 경로를 단일화하여 복잡도를 낮추고, 행사 시 별도 전환 없이 자연스럽게 대기열이 동작한다.
- 트레이드오프: 평시에도 Redis 호출이 추가되나, 인메모리 연산이므로 오버헤드 미미.

### 토큰 만료 후 맨 뒤 재진입 (Q2-A)

- 토큰이 만료되면 대기열 맨 뒤로 재진입해야 한다. 우선 재진입은 지원하지 않는다.
- 이유: 공정성 보장. 우선 재진입을 허용하면 의도적으로 토큰을 만료시키는 어뷰징이 가능해진다.
- 5분 TTL은 주문을 완료하기에 충분한 시간이므로, 정상 유저가 만료될 가능성은 낮다.

### 대기열 최대 인원 상한 설정 (Q3-B)

- 대기열에 최대 인원 제한을 둔다. 초과 시 429 응답과 함께 "잠시 후 다시 시도해주세요" 안내.
- 이유: 대기 시간이 비현실적으로 길어지면 유저 경험이 오히려 악화된다. 상한선을 두어 합리적인 대기 시간을 보장한다.
- 상한선 수치는 처리량(175 TPS) 기준으로 최대 대기 시간이 10분 이내가 되도록 산정한다.

### Polling 우선, SSE는 Nice-to-Have

- 구현 난이도를 고려하여 Polling으로 시작한다.
- 대기 인원이 많아 Polling 부하가 문제가 되면 SSE로 전환을 검토한다.

### 토큰 전달 방식

- HTTP Header(`X-Entry-Token`)로 토큰을 전달한다.
- 기존 주문 API의 Request Body를 변경하지 않기 위함.

### 스케줄러 배치 크기 산정

- DB 커넥션 풀(50) x 평균 처리 시간(200ms) 기반으로 175 TPS를 산정.
- 100ms 간격으로 ~18명씩 발급하여 Thundering Herd를 완화.
- 이 수치는 실측 후 조정이 필요할 수 있음.

### 대기열은 주문 API 앞단의 관문

- 대기열 통과 후 주문 이후의 흐름(이벤트 발행, Kafka 파이프라인, Metrics 집계)은 R7에서 구축한 구조를 그대로 활용한다.

## Redis 키 설계

| 키 패턴 | 자료구조 | 용도 | TTL |
|---------|---------|------|-----|
| `waiting-queue` | Sorted Set | 대기열. score=timestamp, member=userId | 없음 (스케줄러가 ZPOPMIN으로 제거) |
| `entry-token:{userId}` | String | 입장 토큰. value=토큰 값 | 300초 (5분) |

### 핵심 Redis 명령어

| 명령어 | 용도 |
|--------|------|
| `ZADD waiting-queue {timestamp} {userId}` | 대기열 진입 |
| `ZRANK waiting-queue {userId}` | 순번 조회 (0-based) |
| `ZCARD waiting-queue` | 전체 대기 인원 |
| `ZPOPMIN waiting-queue {N}` | 스케줄러가 앞에서 N명 꺼내기 |
| `SET entry-token:{userId} {token} EX 300` | 입장 토큰 발급 |
| `GET entry-token:{userId}` | 토큰 검증 |
| `DEL entry-token:{userId}` | 토큰 삭제 (주문 완료 후) |

## Step별 구현 범위

### Step 1 — Redis 기반 대기열

- [ ] Redis Sorted Set 기반 대기열 진입 API 구현 (`POST /queue/enter`)
- [ ] 순번 조회 API 구현 (`GET /queue/position`)
- [ ] userId 기반 중복 진입 방지
- [ ] 전체 대기 인원 조회
- [ ] 대기열 최대 인원 상한 검증

### Step 2 — 입장 토큰 & 스케줄러

- [ ] 스케줄러가 100ms 주기로 대기열에서 ~18명을 꺼내 입장 토큰 발급
- [ ] 토큰 TTL 설정 (5분)
- [ ] 주문 API 진입 시 토큰 검증 (X-Entry-Token 헤더)
- [ ] 주문 완료 후 토큰 삭제
- [ ] 처리량 기준으로 스케줄러 배치 크기 산정 근거 문서화

### Step 3 — 실시간 순번 조회

- [ ] 예상 대기 시간 계산 로직 구현 (순번 / 초당 처리량)
- [ ] Polling 기반 순번 + 예상 대기 시간 응답
- [ ] 토큰 발급 시 순번 조회 응답에 토큰 포함

### 검증

- [ ] 동시 진입 테스트 — 대기열 순서가 정확히 보장되는지 확인
- [ ] 토큰 만료 테스트 — TTL 초과 시 토큰이 무효화되는지 확인
- [ ] 처리량 초과 테스트 — 스케줄러 배치 크기 이상의 요청이 들어와도 시스템이 안정적인지 확인
- [ ] 대기열 상한 테스트 — 최대 인원 초과 시 429 응답 확인
