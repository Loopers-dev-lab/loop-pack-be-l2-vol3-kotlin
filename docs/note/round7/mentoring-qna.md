# 7주차 멘토링 Q&A 종합 리포트: 이벤트 드리븐과 분산 시스템 설계

## Part 1. Kev 멘토링

**Q1. 같은 productId 이벤트를 같은 partition으로 보내더라도, offset reset 같은 재처리 상황에서는 like_count가 음수가 될 가능성이 있는지, 이런 경우 실무에서는 어떻게 방어하는지 궁금합니다.**
* **A.** 실무에서는 오프셋 리셋(Offset Reset)을 웬만하면 하지 않는 것이 원칙입니다. 만약 리셋이나 재처리가 일어날 경우를 대비해, 메시지 처리 여부를 기록하는 **'핸들링 테이블(멱등성/로그 테이블)'을 두어 이미 처리된 메시지인지 확인하고 스킵**하는 방식으로 방어해야 합니다.

**Q2. like_count 같은 집계성 데이터에서, Exactly-Once로 갈 수 있어도 성능과 단순성을 이유로 At-Least-Once를 선택하는 판단이 실무적으로 괜찮은지 궁금합니다.**
* **A.** 과거와 달리 현재 카프카 최신 버전은 정합성을 보장하는 옵션(`acks=all`, `idempotence=true`)이 디폴트로 설정되어 있습니다. 이 설정을 사용한다고 해서 구현 복잡도가 늘어나는 것이 아니기 때문에, 굳이 성능과 단순성을 핑계로 **At-Least-Once로 정합성 수준을 낮출 이유가 전혀 없습니다.**

**Q3. 관심사 분리를 할 때, 별도의 서비스 클래스로 책임을 분리하는 것과 이벤트로 분리하는 것 중 선택함에 있어서 갖는 판단 기준과 트레이드 오프가 궁금합니다.**
* **A.** 핵심은 "이 로직이 메인 트랜잭션 내에서 즉시 확정되어야 하는 핵심 비즈니스인가?"입니다.
    * **서비스 분리:** 동일 트랜잭션에서 성공/실패를 함께 해야 하는 메인 로직.
    * **이벤트 분리:** 메인 프로세스가 몰라도 되며, 알림이나 통계 적재처럼 실패하더라도 비즈니스 흐름을 롤백시키면 안 되는 부가 로직.

**Q4. 선착순 쿠폰 발급 요청은 Command(요청)입니다. Event가 아닌 Command라서 Outbox가 불필요하다고 판단했지만, DB와 Kafka의 원자성이 걸립니다. Outbox를 사용해야 할지 조언 부탁드립니다.**
* **A.** Outbox를 생략하고 트랜잭션 안에서 카프카를 직접 쏘게 될 경우, **카프카 메시지는 발행되었는데 DB 트랜잭션이 롤백되는 가장 크리티컬한 상황(고스트 이벤트)** 이 발생할 수 있습니다. Command 성격이더라도 고객의 요청 접수 사실을 유실 없이 안전하게 처리하기 위해 Outbox 패턴을 사용하는 것이 정석입니다.

**Q5. Kafka Consumer의 멱등성을 보장하기 위해 DB event_handled와 Redis SET NX 중 어떤 것을 선택하나요?**
* **A.** 멱등성을 완벽히 보장하기 위해서는 트랜잭션으로 묶일 수 있는 **DB 테이블(`event_handled`) 방식이 훨씬 안전**합니다. 레디스는 휘발성 메모리 데이터이기 때문에, 영속성 저장소로는 잘 사용하지 않습니다 (보통 대규모 트래픽 앞단 제어용).

**Q6. partition key = couponId로 설정하면 같은 쿠폰은 순차 처리되므로 DB CAS의 행 락 경합 문제가 발생하지 않습니다. 이 상황에서 DB CAS만으로 충분한지, 아니면 Redis DECR을 함께 사용하는 게 좋을지 궁금합니다.**
* **A.** 설계하신 대로 파티션 키로 순차 처리를 보장하면, 일반적인 상황에서는 DB CAS(또는 락 없는 처리)만으로도 충분합니다. 다만 블랙프라이데이 같은 초대규모 트래픽 시에는 카프카+DB 속도조차 병목이 되므로, 그때는 아예 Redis를 Source of Truth로 삼아 앞단에서 처리해 버리는 특수한 설계를 씁니다.

**Q7. 쿠폰 차감을 AFTER_COMMIT으로 분리하면 이중 할인이 발생할 수 있습니다. 동기 유지가 합리적으로 보이는데, 이벤트로 분리하는 이유가 궁금합니다.**
* **A.** 단일 DB 환경에서는 동기로 묶는 것이 합리적입니다. 하지만 실무 MSA 환경에서는 주문 DB와 쿠폰 DB가 물리적으로 분리될 가능성이 높아 **애초에 하나의 트랜잭션으로 동기화할 수 없습니다.** 강제로 동기 호출 시 분산 트랜잭션 불일치가 더 위험하므로, 이벤트 기반으로 풀고 멱등성 처리로 이중 할인을 막는 것이 장기적 관점에서 맞습니다.

**Q8. 실무에서 "이건 동기로 확정, 이건 이벤트로 뺀다"의 기준이 "사용자 응답에 포함되어야 하는가"인가요?**
* **A.** "사용자가 즉시 알아야 하는가"는 아주 좋은 1차적인 기준입니다. 하지만 절대적이진 않습니다. 서버는 비동기(이벤트)로 던져 PENDING 상태로 두고, 프론트엔드가 결과를 알 때까지 폴링(Polling)하게 만드는 UX 트릭으로 우회할 수 있습니다. 중요한 것은 **어떤 방식을 택하든 발생할 수 있는 실패와 결과적 일관성(Eventual Consistency)을 복구하도록 설계했는가**입니다.

**Q9. 메시지 규격(스키마)이 바뀌어야 하는 경우도 있을 것 같은데, 컨슈머 그룹 측에서는 처리를 어떻게 하나요?**

## Part 3. Devin 멘토링

**Q16. Kafka Consumer Auto Commit vs Manual Ack 및 event_handled 멱등 처리 시 DB와 Redis 중 어떤 방식을 선택하시나요?**
* **A.** 카운트(좋아요, 조회수 등)처럼 **'반드시 한 번만(Exactly-Once) 처리'** 되어야 하는 경우 멱등성 키 저장이 필수입니다. 하지만 DB에 수억 건의 event_handled를 남기면 마스터 DB 부하와 시간 단위 파티셔닝 관리가 극도로 까다로워집니다. 따라서 실무에서는 DB보다는 **Redis 클러스터를 활용하여 쓰기 부하를 분산하고, TTL을 걸어 관리하는 방식을 훨씬 선호**합니다.

**Q17. Outbox 릴레이 구현 시 Polling과 CDC 중 멘토님의 선택 기준이 궁금합니다.**
* **A.** CDC(Debezium)를 사용하면 어플리케이션과 분리되어 메인 트랜잭션(API)의 지연을 막을 수 있다는 큰 장점이 있습니다. 하지만 **운영 복잡도가 극단적으로 높습니다.** 멘토 본인도 실무에서 2년간 CDC를 운영하다가 모니터링이 너무 귀찮고 힘들어서 결국 최근에 떼어내고 어플리케이션 폴링 방식으로 롤백했습니다. 특별한 성능 한계가 오기 전까지는 운영 편의성을 위해 Polling을 쓰는 것이 낫습니다.

**Q18. 실무에서 같은 DB를 쓰는 멀티모듈 구조일 때, 앱 간 엔티티 공유를 어떻게 하시나요?**
* **A.** 공유 모듈(Common 모듈)을 두어 엔티티를 공유하는 정석적 방식을 매우 싫어합니다. 여러 요구사항이 합쳐져 엔티티가 '개뚱뚱해지고', 배치 시스템이 불필요한 인프라(Redis 등) 의존성까지 주입받아야 하는 문제가 터집니다. 도메인을 분리하거나, 배치에서 API를 직접 호출하게 하거나, 모듈별로 JPA 엔티티를 따로 재정의하는 방식을 더 선호합니다.

**Q19. 파티션 키로 순차 처리를 보장할 때 특정 인기 쿠폰 파티션에만 트래픽이 몰리는 (Hot Partition) 문제는 실무에서 어떻게 다루시나요?**
* **A.** 파티션을 10개에서 20개로 늘려도, 파티션 키(해시)가 같으면 무조건 동일한 출입구(단일 파티션)로 몰립니다. 부하를 분산시키기 위해 키를 쪼개면(예: 100-1, 100-2) 동시성 문제가 다시 발생해 결국 DB 락을 잡아야 합니다. 이는 물리적인 한계이며, 카프카가 죽는 것이 아니라 랙(Lag)이 길어지며 처리가 지연될 뿐입니다.

**Q20. BEFORE_COMMIT을 사용하는 경우가 있나요? 트랜잭션이 외부 I/O만큼 길어질 것 같습니다.**
* **A.** `BEFORE_COMMIT`은 단지 코드 표현식을 조금 아름답게 꾸미려는 용도에 가깝습니다. 실질적으로 트랜잭션 하나에 다 때려 박아서 처리하는 것과 동일하게 동작하므로 실무에서 거의 쓸 일이 없습니다. 외부 호출이나 발행은 `AFTER_COMMIT`을 사용해야 합니다.

**Q21. 선착순 쿠폰 동시성 제어 시 Kafka와 Redis DECR 방식의 트레이드오프와 정합성 깨짐 처리 방식이 궁금합니다.**
* **A.** Redis DECR 연산 자체는 원자적이나, DB 커밋 과정에서 롤백이 발생하면 한정된 수량(1만 개)을 다 소진하지 못하고 꼬이는 문제가 발생합니다. 또한 Redis는 인메모리 특성상 마스터가 죽고 슬레이브로 전환되는 짧은 순간이나 브로드캐스팅 시 데이터가 유실될 수 있습니다. 따라서 강한 정합성이 필요하다면 파일 기반의 메인 DB를 최우선으로 고려해야 합니다.
