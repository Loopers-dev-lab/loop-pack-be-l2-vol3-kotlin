# 인덱스를 걸었는데 왜 느릴까

## MySQL(InnoDB)에서 점검할 것들

이전 글에서는 상품 조회 성능을 높이기 위해 어떤 캐시를 둘지, 어떤 인덱스가 필요한지 하나씩 살펴봤다.

이번 글에서는 그중에서도 가장 기본이 되는 세 가지, `index`, `optimizer`, `query plan`을 정리해보려 한다.

조회 성능 이야기를 할 때 가장 먼저 나오는 해법은 보통 인덱스다.  
실제로 도움이 될 때도 많다.

그런데 실무에서는 인덱스를 추가했다고 해서 바로 해결되지 않는 경우도 자주 만난다.

인덱스는 있는데 `full scan`이 나오기도 하고,  
인덱스를 타는데도 `Using filesort` 때문에 느리기도 하고` ,  
실행 계획은 괜찮아 보이는데 실제 부하에서는 응답 시간이 기대만큼 줄지 않기도 한다.

처음에는 인덱스가 있는지만 확인했다.  
하지만 그걸로는 설명되지 않는 경우가 있었다.

그때부터는 단순히 인덱스 유무보다,  
MySQL이 실제로 어떤 실행 경로를 선택하는지를 같이 보게 됐다.

이번 글에서는 그 과정을 정리해보려 한다.

## 먼저 정리하면

상품 조회가 느릴 때 가장 먼저 떠오르는 해법은 보통 인덱스다.  
하지만 실제로는 인덱스만으로 설명되지 않는 경우가 더 많았다.

이번 글에서는 InnoDB 인덱스 구조를 먼저 정리하고,  
옵티마이저가 왜 어떤 인덱스는 쓰고 어떤 인덱스는 버리는지,  
그리고 실행 계획을 어떤 순서로 읽어야 하는지를 함께 정리해보려 한다.

마지막에는 `5M rows` 기준 실측 결과도 함께 넣었다.  
복합 인덱스를 적용한 뒤 조회가 어느 정도까지 줄었는지,  
그 다음에는 왜 캐시 계층까지 같이 보게 됐는지도 함께 남겼다.

## 문제 정의

처음 문제는 단순했다.

`상품 목록 조회가 느리다.`

그런데 실제로 이 문제를 풀어보려면 생각보다 더 많은 질문이 따라왔다.

- 정말 느린 구간은 DB 쿼리인가?
- 인덱스가 없어서 느린가, 인덱스를 못 타서 느린가?
- 정렬 비용이 큰가, 읽는 `rows`가 많은가?
- DB 구간을 줄인 뒤에도 전체 응답 시간은 왜 남아 있는가?

결국 이 문제는 단순한 조회 최적화라기보다,

`Slow Query 탐지 + Index 설계 + Optimizer 판단 + Query Plan 해석`

을 함께 보는 문제에 가까웠다.

## Slow Query

튜닝을 시작할 때 가장 먼저 정리해야 했던 건 "무엇을 느리다고 볼 것인가"였다.

MySQL에서는 일정 시간 이상 걸린 SQL을 `slow query`로 기록할 수 있다.  
보통 `long_query_time`을 기준으로 잡는다.

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
SET GLOBAL log_output = 'FILE';
```

예를 들어 `long_query_time = 1`이면 1초 이상 걸린 쿼리가 로그에 남는다.

다만 운영 환경에서는 이것만으로 충분하지 않았다.  
실행 시간이 긴 쿼리도 문제지만, 실행 시간은 짧아도 너무 자주 호출돼 전체 DB 시간을 많이 잡아먹는 쿼리도 같이 봐야 했기 때문이다.

예를 들면 이런 식이다.

- 1.8초 걸리지만 하루 몇 번만 호출되는 쿼리
- 120ms지만 초당 수백 번 호출되는 쿼리

두 쿼리 모두 문제일 수 있지만, 서비스 전체에 더 큰 부하를 만드는 쪽은 후자일 수도 있다.

그래서 슬로우 쿼리는 보통 아래 경로를 함께 확인하게 된다.

- `Slow Query Log`
- `performance_schema`, `sys`
- APM, 애플리케이션 로그
- `pt-query-digest` 같은 집계 도구

여기서 중요한 건, 슬로우 쿼리는 원인이라기보다 출발점이라는 점이었다.  
느린 SQL을 찾은 뒤에야, 그다음에 인덱스와 실행 계획을 볼 수 있었다.

> 이미지 위치  
> `slow-query-to-plan.excalidraw`  
> Slow Query를 찾고 병목 SQL을 식별한 뒤 `EXPLAIN`과 개선으로 이어지는 흐름

## Index

기존에는 인덱스를 "조회 속도를 높여주는 기능" 정도로만 이해했다.

그런데 찾아보니 InnoDB에서 인덱스는 조회를 빠르게 만드는 옵션이라기보다,  
애초에 데이터를 읽는 방식을 바꾸는 구조에 가까웠다.

InnoDB 인덱스는 일반적으로 `B+Tree` 구조를 사용한다.  
값이 정렬된 상태로 저장되고, 탐색할 때는 루트에서 시작해 범위를 좁혀 내려간다.

직관적으로는 이분 탐색과 비슷하게 느낄 수 있다.  
다만 배열에서 가운데 값을 찍는 전형적인 binary search와 완전히 같은 개념으로 보기는 어렵고,  
트리의 각 노드를 따라 내려가는 탐색으로 이해하는 편이 더 자연스러웠다.

### InnoDB의 PK와 보조 인덱스

이 부분은 직접 정리하면서 다시 보게 됐다.

InnoDB에서 기본 키는 단순한 식별자가 아니라 `clustered index`다.  
즉, 실제 row 데이터가 PK 순서로 저장된다.

반면 `brand_id`, `price`, `like_count` 같은 컬럼의 인덱스는 `secondary index`다.  
보조 인덱스의 리프 노드에는 보통 인덱스 컬럼 값과 기본 키 값이 함께 들어간다.

그래서 보조 인덱스로 후보를 찾았더라도, 실제 row 본문이 더 필요하면 다시 PK로 데이터를 찾아가야 한다.

이 구조를 보고 나니 왜 `SELECT *`가 생각보다 비쌀 수 있는지도 조금 더 명확해졌다.  
인덱스를 탔다고 끝난 게 아니라, 그 뒤에 lookup 비용이 추가될 수 있기 때문이다.

반대로 조회 컬럼이 인덱스 안에 다 들어 있다면 테이블 본문까지 가지 않고 끝낼 수도 있다.  
이때 실행 계획의 `Extra`에 `Using index`가 보이기도 한다.

### 인덱스가 있어도 느린 경우

실무에서 자주 만나는 경우는 "인덱스가 없어서 느리다"보다  
"인덱스는 있는데 지금 쿼리와 잘 맞지 않는다" 쪽에 더 가까웠다.

예를 들어 브랜드별 상품 목록을 가격순으로 보여주는 쿼리를 생각해보면 이렇다.

```sql
SELECT id, name, price
FROM product
WHERE status = 'ACTIVE'
  AND brand_id = ?
ORDER BY price ASC, id DESC
LIMIT 20;
```

처음에는 `brand_id` 인덱스만 있어도 어느 정도 괜찮지 않을까 생각하기 쉽다.  
브랜드 조건으로는 줄일 수 있으니, 나머지 정렬은 감당할 수 있을 것처럼 보이기 때문이다.

그런데 실제로는 이 쿼리가 `brand_id` 조건만 보는 게 아니다.  
`status = 'ACTIVE'`로 다시 걸러야 하고,  
결과는 `price ASC, id DESC` 순서로 정렬되어 있어야 하며,  
거기서 상위 20개만 잘라야 한다.

이때 `brand_id` 단일 인덱스는 브랜드별로 후보를 좁히는 데는 도움이 된다.  
문제는 그다음이다. 브랜드에 속한 상품들을 다시 `status`로 걸러내고,  
남은 결과를 `price ASC, id DESC`로 정렬해야 한다.  
이 과정에서 `Using filesort`가 붙기 쉽다.

반대로 `price` 단일 인덱스는 정렬 방향만 보면 맞아 보일 수 있다.  
하지만 이 경우에는 전체 상품을 가격순으로 읽으면서 그중 `brand_id`, `status` 조건에 맞는 것만 골라야 해서 효율이 떨어진다.

즉, 문제는 인덱스 유무보다도  
`WHERE 조건과 ORDER BY를 한 흐름으로 처리할 수 있느냐`에 있었다.

그래서 이 패턴에서는 아래 쪽이 더 자연스러웠다.

```sql
CREATE INDEX idx_product_brand_status_price
  ON product (brand_id, status, price ASC, id DESC);
```

이렇게 두면 `brand_id`, `status`로 먼저 범위를 줄이고,  
그 범위 안에서 이미 `price ASC, id DESC` 순서가 맞춰진 상태로 읽을 수 있다.  
정렬을 따로 다시 하지 않아도 될 가능성이 커지는 이유가 여기 있다.

복합 인덱스는 왼쪽부터 사용된다.  
이 규칙이 계속 중요하게 느껴졌던 것도 결국 이런 쿼리 때문이었다.

### 인덱스의 비용

읽기 성능만 보면 인덱스는 많을수록 좋아 보인다.  
하지만 결국 트레이드오프다.

- 저장 공간이 추가로 발생한다
- `INSERT`, `UPDATE`, `DELETE` 때 인덱스도 같이 갱신된다
- 인덱스가 많을수록 쓰기 비용과 관리 복잡도가 커진다

그래서 무엇을 더 만들까보다는  
자주 호출되는 쿼리에 정말 필요한 인덱스만 추가했는가를 먼저 보게 됐다.

## Optimizer

인덱스를 만들고 나서 `EXPLAIN`을 찍어봤는데, 기대한 인덱스를 안 타는 경우가 있다.

처음에는 인덱스를 잘못 만든 건가 싶었다.  
하지만 꽤 자주, MySQL 입장에서는 그 인덱스를 안 쓰는 쪽이 더 싸다고 판단한 결과이기도 했다.

옵티마이저는 SQL을 그대로 실행하지 않는다.  
가능한 실행 경로를 몇 개 놓고, 그중 비용이 가장 낮아 보이는 쪽을 고른다.

쉽게 말하면:

- 인덱스는 갈 수 있는 길이고
- 옵티마이저는 그 길이 정말 싼지 계산한다

비교 대상은 보통 이런 것들이다.

- 테이블 전체를 읽을지
- 인덱스로 일부 범위만 읽을지
- 어떤 인덱스를 탈지
- 조인 순서를 어떻게 잡을지
- 정렬을 인덱스로 풀지, 따로 할지

### Full Scan이 선택되는 경우

이 질문은 생각보다 자주 하게 된다.

핵심은 단순하다.  
옵티마이저는 인덱스의 존재보다 비용을 먼저 본다.

그래서 아래 상황에서는 `full scan`이 꼭 이상한 결과는 아니다.

- 테이블이 작다
- 조건의 선택도가 낮다
- 인덱스를 타고도 너무 많은 row를 다시 읽어야 한다
- 정렬이나 집계 비용 때문에 인덱스 이점이 크지 않다

그래서 "데이터가 적으면 full scan"이라는 말은 조금 단순화된 표현에 가깝다.  
좀 더 정확히 말하면, 옵티마이저가 full scan이 더 싸다고 계산하면 그 방향으로 탐색한다.

### 인덱스를 어렵게 만드는 SQL

인덱스가 문제라기보다, SQL이 인덱스를 활용하기 어렵게 쓰인 경우도 있다.

```sql
WHERE DATE(created_at) = '2026-03-13'
```

이렇게 쓰면 `created_at` 인덱스를 예쁘게 쓰기 어렵다.  
컬럼 값 자체를 비교하는 게 아니라 함수 결과를 비교하고 있기 때문이다.

보통은 아래와 같은 쿼리가 더 낫다.

```sql
WHERE created_at >= '2026-03-13 00:00:00'
  AND created_at < '2026-03-14 00:00:00'
```

인덱스 최적화는 인덱스를 추가하는 일만이 아니라,  
쿼리를 인덱스가 먹기 좋은 형태로 다시 쓰는 일도 포함된다는 얘기다.

### 통계와 옵티마이저

옵티마이저는 감으로 판단하지 않는다.  
카디널리티, 선택도, 예상 `rows` 같은 통계로 비용을 계산한다.

그래서 통계가 실제 데이터 분포를 잘 못 잡고 있으면 실행 계획도 엇나갈 수 있다.  
괜찮은 인덱스가 있는데도 이상한 플랜이 나오는 경우가 여기서 나온다.

짧게 줄이면 이 정도로 정리할 수 있다.

- 인덱스는 가능성이고
- 옵티마이저는 비용으로 고르며
- 통계가 틀리면 결정도 틀릴 수 있다

## Query Plan

인덱스는 구조고, 옵티마이저는 판단자다.  
그렇다면 실제로 봐야 하는 건 그 판단 결과다.

그걸 확인하는 도구가 `EXPLAIN`이다.

```sql
EXPLAIN
SELECT id, name, price
FROM product
WHERE status = 'ACTIVE'
  AND brand_id = 10
ORDER BY price ASC, id DESC
LIMIT 20;
```

이걸 읽기 시작하면 질문도 조금 달라진다.

`인덱스가 있나?` 보다  
`왜 이런 방식으로 읽고 있지?`

### EXPLAIN 보는 순서

빠르게 볼 때는 아래 순서가 가장 실용적이었다.

1. `type`
2. `rows`
3. `Extra`
4. `key`

좀 더 엄밀하게 보려면 `key_len`, `possible_keys`도 함께 봐야 한다.  
다만 첫 번째 판별은 `type -> rows -> Extra`로 들어가는 편이 훨씬 빨랐다.

### 1) type

`type`은 접근 방식이다.

- `const`, `eq_ref`: 거의 최상
- `ref`: 대체로 양호
- `range`: 보통 괜찮지만 범위가 넓으면 위험
- `index`: 인덱스 전체 스캔
- `ALL`: 테이블 전체 스캔

`ALL`이 나왔다고 무조건 틀렸다고 보긴 어렵다.  
테이블이 아주 작으면 순차 읽기가 더 쌀 수도 있다.

다만 아래 조합이면 바로 눈에 들어온다.

- `type = ALL`
- `rows`도 크다
- 호출 빈도도 높다
- `Using filesort`, `Using temporary`까지 붙는다

실무에서 진짜 위험한 건 `ALL` 하나보다 `ALL + large rows` 조합에 더 가까웠다.

### 2) rows

인덱스를 탔다고 해서 끝난 건 아니다.  
성능은 결국 얼마나 많이 읽느냐에서 갈린다.

예를 들어 `type = range`인데 `rows = 800000`이면,  
형식상 인덱스를 쓰고 있어도 이미 엄청 많이 읽고 있는 계획이다.

그래서 `rows`는 절대값보다 전체 데이터 대비 비율로 보는 편이 낫다.  
100만 건 테이블에서 80만 건을 읽는 계획은 건강하다고 보기 어렵다.

조인에서는 더 조심하게 된다.  
앞 단계에서 많이 읽고 뒤에서 여러 건씩 붙으면 처리량이 금방 커진다.

### 3) Extra

`Extra`에서 자주 보는 위험 신호는 둘이었다.

- `Using filesort`
- `Using temporary`

`Using filesort`는 인덱스 순서로 정렬하지 못해서 별도 정렬이 들어간다는 뜻이다.  
`rows`가 적으면 버틸 만하지만, 많아지는 순간 바로 비용이 커진다.

`Using temporary`는 중간 결과를 담기 위해 임시 테이블이 필요하다는 신호다.  
`GROUP BY`, `DISTINCT`, 조인 집계에서 자주 보게 된다.

둘이 같이 나오면 대체로 마음이 편하지 않다.  
중간 결과를 만들고, 그걸 다시 정렬하고 있다는 뜻이기 때문이다.

### 먼저 보는 위험 신호

운영에서 먼저 걸러내는 기준은 이 정도였다.

- `type = ALL` 이고 `rows`가 크다
- `type = ALL` 인데 `Using filesort`가 붙는다
- `Using temporary`와 `Using filesort`가 같이 나온다
- `type = range`인데 `rows`가 테이블의 큰 비율을 차지한다
- 조인에서 앞 단계와 뒤 단계의 `rows`가 곱해지며 커진다
- `type = index`로 인덱스 전체를 사실상 다 읽고 있다

반대로 아래는 바로 문제라고 단정하진 않았다.

- `Using filesort`가 있어도 정렬 대상이 아주 적다
- `ALL`이지만 테이블이 매우 작다
- `rows`가 커도 `Using index`로 커버링 인덱스만 읽고 끝난다

실행 계획에서 보려던 건 결국 하나였다.

`인덱스를 탔는가?` 보다  
`얼마나 넓게 읽고, 어디서 추가 비용이 붙는가?`

> 이미지 위치  
> `explain-triage.excalidraw`  
> `EXPLAIN`을 `type -> rows -> Extra` 순서로 읽는 기준과 위험 신호 요약

## 상품 조회에 적용해보기

이 프로젝트의 상품 목록은 `LATEST`, `PRICE_ASC`, `LIKES_DESC` 세 가지 정렬을 쓴다.

코드로 보면 더 분명하다.

```kotlin
when (sort) {
    ProductSort.LATEST -> arrayOf(product.id.desc())
    ProductSort.PRICE_ASC -> arrayOf(product.price.asc(), product.id.desc())
    ProductSort.LIKES_DESC -> arrayOf(product.likeCount.desc(), product.id.desc())
}
```

정렬 기준은 이미 정해져 있다.

- 최신순: `id DESC`
- 가격순: `price ASC, id DESC`
- 좋아요순: `like_count DESC, id DESC`

여기에 `status = ACTIVE`, 선택적으로 `brand_id = ?`가 붙는다.

이 패턴에 맞춰 현재 DDL은 아래 인덱스를 두고 있다.

```sql
CREATE INDEX idx_product_status_price
  ON product (status, price ASC, id DESC);

CREATE INDEX idx_product_status_like_count
  ON product (status, like_count DESC, id DESC);

CREATE INDEX idx_product_brand_status_price
  ON product (brand_id, status, price ASC, id DESC);

CREATE INDEX idx_product_brand_status_like
  ON product (brand_id, status, like_count DESC, id DESC);
```

이건 컬럼별로 인덱스를 흩뿌린 결과가 아니다.  
`WHERE + ORDER BY + LIMIT` 패턴을 따라간 결과에 가깝다.

예를 들어 아래 쿼리를 보자.

```sql
SELECT *
FROM product
WHERE status = 'ACTIVE'
  AND brand_id = 10
ORDER BY like_count DESC, id DESC
LIMIT 20;
```

`brand_id` 단일 인덱스만 있으면 브랜드로 먼저 줄인 뒤, 다시 `like_count`로 정렬해야 할 가능성이 크다.  
그럼 `Using filesort`가 붙는다.

반면 `(brand_id, status, like_count DESC, id DESC)` 인덱스가 있으면  
필터와 정렬을 한 흐름으로 처리할 여지가 훨씬 커진다.

실제로 복합 인덱스를 추가한 뒤에는 `Using filesort`가 사라지고 `rows`도 크게 줄었다.

정리하면, 여기서 한 일은 "인덱스를 더 만들었다"보다 이쪽에 가까웠다.

상품 목록이 실제로 읽히는 순서에 맞춰 인덱스를 다시 잡았다고 보는 편이 더 자연스러웠다.

## 5M rows 실측

수치를 붙여보면 조금 더 선명해진다. 이번 비교는 로컬 Docker 환경에서 `MySQL 5M rows` 기준으로 측정했고, 상품 목록 쿼리에는 복합 인덱스를 적용한 상태였다.

먼저 DB 자체는 생각보다 충분히 빨랐다.

- 상품 상세 PK 조회: `~0.96ms`
- 브랜드 + 좋아요 순 목록: `~2.28ms`
- 브랜드 + 가격 순 목록: `~3.53ms`
- 전체 + 좋아요 순 목록: `~1.87ms`

적어도 이번 케이스에서는 "대용량이라서 어쩔 수 없다"기보다는, 접근 경로가 더 큰 변수였다.  
`5M rows`여도 쿼리 패턴과 맞는 복합 인덱스를 잡으면 목록 조회를 밀리초 초반대로 가져갈 수 있었다.

그다음으로 본 건 캐시 계층이었다.

- Redis GET: `p50 0.127ms`
- Redis SET: `p50 0.183ms`
- Caffeine GET/PUT: `~0.001ms`

물론 Caffeine이 가장 빠르다.  
다만 속도만 보고 결정하기엔 분산 환경에서의 무효화와 메모리 사용량이 같이 따라온다.

그래서 실제로는 "어떤 캐시가 제일 빠른가"보다,  
"어떤 데이터에 어떤 캐시가 맞는가"를 더 보게 됐다.

전체 플로우 기준으로 요약하면 이 정도였다.

| 조회 유형 | DB 직접 | Redis Hit | Caffeine Hit |
|------|------|------|------|
| 상품 상세 | `~1.5ms` | `~0.4ms` | `~0.001ms` |
| 상품 목록 | `~3.5ms` | `~0.6ms` | `~0.001ms` |

상품 상세는 Redis만 써도 DB 직접 조회 대비 충분히 줄어들었다.  
상품 목록도 마찬가지였다. 다만 인덱스 튜닝으로 DB 쿼리를 줄였다고 해서 응답 전체가 같이 끝까지 줄어드는 건 아니었다. 브랜드 조회, 직렬화 같은 비용은 여전히 남아 있었다.

### 캐시 전략

이번 비교에서 더 중요했던 건 "가장 빠른 캐시는 무엇인가"보다  
"어떤 데이터에 어떤 캐시가 맞는가"였다.

판단 기준은 대략 이랬다.

- 키 수가 제한적인가
- 변경 빈도는 어떤가
- `stale` 허용 범위는 어디까지인가
- scale-out 환경에서 무효화 일관성이 필요한가

현재 기준으로는 아래 판단이 가장 자연스러웠다.

| 캐시 대상 | 판단 | 근거 |
|------|------|------|
| 인증 | `Caffeine 유지` | BCrypt CPU 절감 목적, `~0.001ms`, 인스턴스 독립적으로 동작 가능 |
| 상품 상세 | `Redis 유지` | CUD 이후 evict 일관성이 중요, DB 대비 `~3.7x` 향상으로 충분 |
| 상품 목록 | `Redis 유지` | `brand x sort x size x cursor` 조합으로 키 폭발 가능, 로컬 힙 캐시는 부담이 큼 |
| 브랜드 정보 | `Caffeine 추가 검토` | 건수가 매우 적고 변경 거의 없음, 현재는 반복 DB 조회 비용 존재 |

이 실험이 보여준 건 "Caffeine이 Redis보다 빠르다"는 너무 당연한 사실보다,  
어떤 데이터는 로컬 캐시가 맞고 어떤 데이터는 글로벌 캐시가 맞는지였다.

> 이미지 위치  
> `cache-tier-comparison.excalidraw`  
> No Cache, Redis, Caffeine의 응답 시간 차이와 캐시 계층 선택 기준 비교

### 2-tier 캐시

`L1 Caffeine + L2 Redis` 같은 2-tier 캐시는 분명 매력적이다.

가장 자주 읽히는 데이터는 애플리케이션 메모리에서 바로 응답하고,  
로컬에 없을 때만 Redis를 보게 만들 수 있기 때문이다.

다만 이 구조는 "더 빠르니까 넣자"로 결정하기엔 생각할 게 꽤 많다.

먼저, 이런 경우에는 2-tier 캐시가 비교적 잘 맞는다.

- 조회 빈도가 매우 높다
- 키 수가 어느 정도 제한적이다
- 여러 인스턴스에서 반복적으로 같은 데이터를 읽는다
- 약간의 `stale`을 허용할 수 있다
- Redis 지연도 아깝다고 느껴질 만큼 응답 시간을 더 줄여야 한다

반대로 아래 같은 경우에는 오히려 복잡성만 늘 수 있다.

- 키 조합이 너무 많아 로컬 캐시가 쉽게 커진다
- 데이터 변경이 잦아 무효화가 자주 일어난다
- 강한 일관성이 필요하다
- 현재 병목이 Redis가 아니라 DB나 애플리케이션 로직에 있다

적합한 데이터도 어느 정도 나뉜다.

- 상품 상세처럼 hot key가 반복 조회되는 데이터
- 브랜드 정보처럼 건수가 적고 변경이 드문 데이터
- 사용자별 개인화가 약하고, 여러 요청이 같은 값을 재사용하는 데이터

반대로 상품 목록처럼 `brand x sort x size x cursor` 조합으로 키가 계속 늘어나는 데이터는 로컬 캐시까지 얹을 때 신중해야 한다.  
Redis는 `allkeys-lfu` 같은 정책으로 어느 정도 정리를 기대할 수 있지만, 애플리케이션 힙은 그렇게 편하게 다루기 어렵기 때문이다.

고민해야 할 지점도 명확하다.

- L1과 L2의 TTL을 같게 둘지 다르게 둘지
- Redis evict 이후 로컬 캐시를 어떻게 정리할지
- CUD 발생 시 어떤 단위로 무효화할지
- 히트율이 낮을 때도 L1 유지 비용이 의미가 있는지
- 인스턴스 수가 늘어날 때 메모리 사용량이 어떻게 커지는지

트레이드오프도 분명하다.

- 장점: 가장 자주 읽히는 데이터는 Redis보다 더 빠르게 응답할 수 있다
- 장점: Redis 트래픽과 네트워크 홉을 줄일 수 있다
- 단점: 무효화 전략이 복잡해진다
- 단점: 인스턴스별 메모리 사용량이 늘어난다
- 단점: L1, L2, DB 사이의 상태 차이를 디버깅하기 어려워진다

그래서 이번 글에서는 2-tier 캐시를 "지금 당장 넣자/말자"로 결론내리기보다,  
어떤 조건에서 검토할 수 있는 선택지로 보는 편이 맞다고 생각했다.

현재 수치만 보면 상품 상세에서 `Redis Hit ~0.4ms`를 `Caffeine Hit ~0.001ms`로 더 줄일 여지는 분명 있다.  
다만 그 차이가 당장 필요한 수준인지는, 실제 부하에서 Redis가 병목으로 드러나는지까지 보고 판단하는 편이 더 자연스럽다.

현 단계에서는 이 정도가 가장 무난한 정리였다.

`우선은 현재 구조를 유지하고, 실제 부하 테스트에서 Redis 구간이 병목으로 드러날 때 2-tier 캐시를 다시 검토하자.`

## 마무리

조회 최적화는 인덱스를 더 추가하는 작업이라기보다,  
어떤 방식으로 읽게 만들 것인지 정리하는 작업에 가까웠다.

이번 내용을 정리하면서 결국 다시 돌아오게 된 흐름은 이랬다.

- `slow query`로 진짜 문제 쿼리를 찾고
- 그 쿼리에 맞는 `index`를 고민하고
- 왜 MySQL이 그 경로를 택했는지 `optimizer` 관점으로 보고
- 마지막으로 `query plan`에서 `type`, `rows`, `Extra`를 확인한다

이 흐름을 머리에 두고 나니 질문도 조금 달라졌다.

- 왜 옵티마이저는 이 인덱스를 싸다고 보지 않았을까
- 왜 `EXPLAIN`에서 `ALL`이 나왔을까
- 왜 인덱스를 타는데도 `Using filesort`가 붙었을까
- 왜 `rows`가 이렇게 크게 잡혔을까

성능 튜닝은 보통 그 질문에서부터 다시 시작되는 것 같다.
