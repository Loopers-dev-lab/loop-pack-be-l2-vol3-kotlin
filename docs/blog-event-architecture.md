# 이벤트는 어디까지 책임져야 할까

## 발행된 이벤트, 그 이후는 누가 책임지는가

간단한 커머스 프로젝트를 공부하며 이벤트에 대해 오래 고민했다.

처음에는 이벤트를 도입하면 로직이 깔끔해질 거라고 생각했고, 실제로도 관심사가 분리되는 느낌을 받았다.

하지만 시나리오를 계속 그려보다 보니 고민이 깊어졌다.

- 도메인 경계를 어떻게 나눌 것인가
- 트랜잭션 경계를 어디까지 묶을 것인가
- 이벤트는 어디까지 책임져야 하는가
- 이벤트 핸들러가 또 하나의 거대한 서비스가 되지는 않는가
- 실패했을 때는 어떻게 다시 정합성을 맞출 것인가

결국 내 고민의 핵심은 이것이었다.

> "이벤트는 어디까지 책임져야 하고, 그 이후의 실행 책임은 누가 가져가야 하는가?"

이번 글은 고민 끝에 왜 단순한 Event-Handler 구조보다 **Event-Command-Handler** 구조를 더 선호하게 되었는지, 그리고 왜 이벤트의 책임을 의도적으로 잘게 나누려 했는지 정리한 글이다.

---

## 문제는 책임

처음에는 로직이 그럭저럭 단순해 보였다.

```text
주문 생성 -> 재고 차감 -> 쿠폰 차감 -> 결제 처리
```

하지만 커머스 로직은 금방 복잡해진다.

- 결제 실패 -> 재고 복원, 포인트 복원
- 브랜드 삭제 -> 상품 연쇄 삭제 -> 좋아요 삭제 -> 캐시 무효화
- 상품 상태 변경 -> 캐시 무효화, 통계 반영, 검색 인덱스 갱신

이 흐름을 Service가 다른 Service를 직접 호출하는 방식으로 풀면, 어느 순간 하나의 트랜잭션 안에 여러 도메인의 관심사가 섞인다. 그때부터는 코드보다 의존성이 먼저 눈에 들어온다.

- 주문 Service가 상품 Service를 알고
- 상품 Service가 쿠폰 Service를 알고
- 쿠폰 Service가 결제 결과를 신경 쓰고
- 결제 실패가 다시 주문과 상품 쪽 보상 로직으로 되돌아온다

즉 **도메인 간 결합을 어떻게 풀면서도, 필요한 정합성은 어떻게 유지할 것인가**가 문제였다.

---

## 도메인 경계가 먼저다

Spring Event에는 여러 수신 방식이 있지만, 구현 방식을 결정하기 전에 먼저 이 프로젝트를 어떤 도메인들로 봐야 하는지부터 정리했다.
- 회원
- 브랜드
- 상품
- 좋아요
- 주문
- 쿠폰
- 결제

이때 가장 흥미로웠던 건 `좋아요`였다.

좋아요는 얼핏 보면 하나의 기능 같지만, 실제로는 두 가지 역할이 섞여 있다.

- 사용자가 어떤 상품을 좋아요했는지 저장하는 **행위 기록**
- 상품의 좋아요 수를 집계하는 **집계 모델**

처음에는 묶어두기 편하지만, 이벤트 기반으로 분리하려고 보면 경계가 애매해진다.
예를 들어 브랜드 삭제 시 상품이 연쇄 삭제되면, 좋아요 삭제는 "행위 기록 정리"고 like_count 갱신은 "집계 모델 보정"이다. 이 둘은 실패 비용도 다르고 처리 시점도 다를 수 있다.

그래서 이번 설계의 출발점은

> "이벤트를 어떻게 붙일까?"

가 아니라

> "어떤 변화가 어떤 도메인의 사실인가?"

였다.

이 질문을 먼저 붙잡아야 나중에 이벤트 이름도 자연스러워지고, 누가 무엇에 반응해야 하는지도 정리된다.

---

## 사실 발행까지가 도메인의 몫

개인적으로 도메인은 서비스가 고도화되면 결국 하나의 마이크로 서비스로 분리된다고 봤다. 그래서 위에 정리한 도메인들을 각각 독립된 서비스로 가정하고 고민해봤다.

그리고 그 결과 정리된 기준은 하나였다.
**도메인은 상태 변화의 사실을 발행하는 것까지만 책임진다.**

예를 들어 주문이 생성되었다면 주문 도메인은

- 주문을 생성하고
- `OrderRequestedEvent` 혹은 `OrderCreatedEvent` 같은 이벤트를 발행한다

여기까지가 주문 도메인의 몫이다.

그 다음에 재고를 차감할지, 쿠폰을 소비할지, 외부 결제를 요청할지, 통계를 쌓을지 — 이런 결정까지 주문 도메인이 끌어안으면 다시 다른 도메인의 관심사를 품게 된다.

그래서 **도메인이 다른 도메인의 후속 책임까지 끌어안지 않는 구조**가 필요했다. 그런데 단순히 이벤트를 도입하면 해결될까?

---

## 비대해지는 Event-Handler

처음에는 Event-Handler만으로도 충분해 보였다. 이벤트가 발생하면 리스너가 받아서 필요한 작업을 하면 되기 때문이다.

그런데 생각해보면 Event-Handler 하나에 너무 많은 역할이 들어간다.

- 사실을 해석하는 역할
- 어떤 후속 작업이 필요한지 결정하는 역할
- 실제 작업을 수행하는 역할

이 셋이 섞이면 핸들러가 금방 커진다. 주문 생성을 예로 들어보자.

초기에는 단순하다.

```text
OrderCreatedEvent → 재고 차감
```

하지만 서비스가 확장되면 하나의 이벤트 핸들러가 점점 많은 일을 떠안는다.

```text
OrderCreatedEvent → 재고 차감 → 쿠폰 차감 → 포인트 차감 → 메일 발송
```

결국 "Service가 EventHandler로 이름만 바뀐 것 아닌가?" 싶은 순간이 온다. 이벤트를 도입해서 느슨한 연결을 기대했는데, 핸들러가 거대한 진입점이 되어버리는 것이다.

> 이벤트는 사실을 전달해야지, 모든 실행 책임까지 한곳에 몰아서는 안 된다.

그래서 이벤트의 책임을 명확하게 제한하고 싶었다.

- 이벤트는 "무슨 일이 일어났는가"만 담는다
- 어떤 후속 작업이 필요한지는 별도의 Command로 분리한다
- 실제 실행은 Handler가 맡는다

**이벤트는 출발점이지 종착점이 아니다.** 이렇게 나누지 않으면 이벤트 계층이 또 다른 서비스 계층처럼 비대해진다.

Event-Command-Handler 구조로 나누면 흐름이 깔끔해진다.

```text
Event → Command → Handler
```

아까의 주문 생성 예시를 이 구조로 바꾸면 이렇다.

```text
OrderRequestedEvent
  → DeductStockCommand      → StockCommandHandler
  → ConsumeIssuedCouponCommand → CouponCommandHandler
  → RequestPaymentCommand   → PaymentCommandHandler
```

하나의 이벤트에서 여러 후속 작업이 분리되고, 각 Command는 독립적으로 실행된다.

### 이 구조의 장점

**1. 사실과 의도가 분리된다.** `주문이 생성되었다`는 사실과 `재고를 차감해야 한다`는 의도는 같은 것이 아니다. 분리해두면 이벤트 모델과 실행 모델을 따로 다룰 수 있다.

**2. 후속 작업 추가가 쉽다.** 알림 발송이나 분석 적재가 필요해지면 Command 하나만 추가하면 된다. 기존 핸들러를 수정할 필요가 없다.

**3. 전송 수단을 갈아끼우기 쉽다.** 나중에 특정 Command만 Kafka 같은 별도 메시징으로 넘기고 싶을 때, Event를 건드리지 않고 CommandHandler 구현체만 바꾸면 된다.

정리하면 Event-Command-Handler의 각 역할은 이렇다.

- **Event**: 이미 일어난 사실. "주문이 생성되었다"
- **Command**: 그 사실을 보고 실행할 의도. "재고를 차감해라"
- **Handler**: 그 의도를 실제로 수행하는 구현. 트랜잭션 경계와 실행 방식을 결정한다

## 커밋 시점이라는 새로운 질문

Event-Command-Handler로 "무엇을 분리할지"는 정리됐다. 그런데 곧바로 다음 질문이 따라왔다 — 이벤트를 **언제** 발행할 것인가?

Spring은 이벤트 수신 시점에 대해 몇 가지 선택지를 제공한다.

- `@EventListener` — `publishEvent()` 호출 즉시 실행
- `@TransactionalEventListener(BEFORE_COMMIT)` — 트랜잭션 커밋 직전 실행
- `@TransactionalEventListener(AFTER_COMMIT)` — 트랜잭션 커밋 확정 후 실행

처음엔 프레임워크 옵션을 고르는 문제처럼 느껴졌다. 하지만 계속 생각해보니 질문 자체가 달랐다.

> "이 변화는 언제 시스템의 사실이 되는가?"

이 주제에 대해 좀 더 찾아본 결과 핵심은 두 가지 선택지의 실패 특성이 완전히 다르다는 것이었다.

`@EventListener`는 같은 트랜잭션 안에서 실행된다. 리스너가 실패하면 발행자 트랜잭션도 함께 롤백된다. 정합성은 강하지만 그만큼 결합도도 강하다. 주문을 저장하는 트랜잭션이 캐시 evict 실패 때문에 롤백되는 상황을 떠올려보면, 이게 항상 바람직한 건 아니다.
사실상 코드 분리 그 이상의 효과를 기대할 수 없다고 판단했다.

`@TransactionalEventListener(BEFORE_COMMIT)`은 발행자 커밋이 확정되기 전에 실행된다. 리스너가 실패하면 발행자도 실패한다. 처음엔 `@EventListener`와 뭐가 다른지 회의감이 들었는데, 차이는 **실행 시점**에 있었다. `@EventListener`는 `publishEvent()`를 호출하는 그 줄에서 즉시 실행되고, `BEFORE_COMMIT`은 트랜잭션 커밋 직전까지 실행이 지연된다. 결과적으로 리스너 실패 시 롤백된다는 점은 같지만, 발행 코드 이후의 로직이 먼저 실행될 수 있다는 차이가 있다.

`@TransactionalEventListener(AFTER_COMMIT)`은 발행자 커밋이 확정된 후에 실행된다. 리스너가 실패해도 발행자에 영향이 없다. 대신 리스너 실패 시 자동 롤백이 안 되기 때문에, 별도의 복구 전략이 필요하다.

결국 논의의 결론은 이것이었다 — **이 선택은 "실패했을 때 누가 책임지느냐"의 문제다.**

커밋도 되지 않은 사실을 다른 도메인이 신뢰하고 움직이게 만들면, 로컬에서는 편할 수 있어도 경계는 흐려진다. 확정된 사실을 기준으로 다음 흐름을 시작하고, 실패 책임은 각 후속 처리가 스스로 지게 하는 편이 낫다.

그래서 **`AFTER_COMMIT`을 기본값으로 두고**, 정말 같은 트랜잭션 안에 묶여야 하는 케이스에서만 `BEFORE_COMMIT`을 검토하는 쪽으로 정리됐다.

다만 `AFTER_COMMIT`에도 약점은 있다. 커밋 직후 앱이 죽으면 리스너가 실행되지 않아 이벤트가 유실될 수 있다. 이 문제는 Outbox Pattern 같은 별도의 전달 보장 전략으로 풀어야 하는 영역이고, 인지는 하고 있지만 이번 글의 범위에서는 다루지 않는다.

## 같은 방식으로는 안 된다

모든 후속 작업을 같은 방식으로 다룰 수는 없었다. 도메인의 성격과 실패 비용에 따라 전략이 달라져야 한다.

### 재고 / 쿠폰

재고나 쿠폰은 주문 흐름과 밀접하게 연결되어 있고, 경우에 따라 강한 정합성이 필요하다.
특히 재고 차감 실패가 주문 성공보다 뒤에 오면 사용자 경험과 데이터 모두가 어색해진다.

이런 케이스는 같은 프로세스 안에서 동기적으로 실행하되, 트랜잭션은 REQUIRES_NEW로 분리해서 각 도메인의 정합성을 독립적으로 보장하는 쪽을 택했다.

### 캐시 무효화 / 통계성 후처리

캐시 무효화나 일부 통계 처리는 실패 비용이 상대적으로 낮다.
실패해도 다음 조회나 다음 배치에서 다시 맞출 수 있다.

이런 작업에 무거운 메시징 보장을 요구하는 것은 오히려 과할 수 있다.

### 결제 / 보상 / 외부 연동

결제는 다른 도메인과 온도가 달랐다. 좋아요 수 증가나 캐시 무효화는 한 번쯤 실패해도 다음 기회에 복구된다. 결제는 다르다.

- 유실되면 안 되고
- 실패 원인이 추적 가능해야 하고
- 재처리 전략이 있어야 하고
- 보상 흐름까지 함께 설계돼야 한다

결제 실패 시나리오를 그려보면, "에러가 났으니 즉시 롤백"보다 **polling 기반으로 상태를 다시 맞춰가는 복구 전략**이 더 자연스러운 경우가 많다. 사용자는 결제 버튼을 눌렀지만 결과가 즉시 확정되지 않을 수 있고, 시스템은 동일 이벤트를 중복 처리하더라도 망가지지 않아야 한다.

이 지점부터는 로컬 이벤트만으로 설명하기 어렵다. 조용히 사라지면 안 되는 이벤트를 다룰 때는, Kafka 같은 더 강한 전달 보장을 가진 메시징 수단을 검토하게 됐다.

내 기준은 "모든 이벤트를 통일하자"가 아니라,

> "도메인의 성격과 실패 비용에 따라 다르게 처리하자"

쪽에 가까웠다. 정합성을 보장하려 할수록 더 많은 비용이 든다는 점을 실감했다.

## 브랜드 삭제로 검증하기

이 설계가 실제로 괜찮은지 보려면, 복잡한 연쇄 흐름에 대입해보는 게 가장 좋다.

현재 프로젝트는 브랜드 - 상품, 1:N 구조였기에
브랜드 삭제는 좋은 예시였다.

```text
BrandDeletedEvent
  -> CascadeDeleteProductsCommand
      -> Product 삭제
          -> ProductDeletedEvent
              -> DeleteProductLikesCommand
              -> EvictProductCacheCommand
```

이 흐름에서 중요한 건 다음이었다.

- 브랜드 도메인은 브랜드 삭제 사실만 발행한다
- 상품 삭제 여부는 별도 Command가 결정한다
- 좋아요 삭제, 캐시 무효화는 또 다른 후속 작업으로 분리된다

즉 한 도메인이 모든 후처리를 직접 끌고 가지 않는다.

흐름이 길어져도 책임이 확실하게 유지된다는 점이 이 구조의 장점이다. 모놀리스 안에서도 도메인 간 결합을 최소화하는 습관을 들일 수 있다.

---

## 실패는 예외가 아닌 기본 시나리오

이벤트 구조를 그릴 때 가장 쉽게 빠지는 함정은 성공 흐름만 보고 끝내는 것이다.
하지만 실제로는 실패 시나리오가 더 중요하다.

- 이벤트는 발행됐지만 소비가 실패한 경우
- 결제 요청은 갔지만 응답이 늦는 경우
- 일부 후처리만 끝나고 나머지는 지연되는 경우

이때 필요한 건 화려한 패턴 이름이 아니라 아래 같은 장치들이다.

- 재시도
- 멱등성
- 보상 처리
- polling
- 후처리 배치

"실패할 수 있다"보다 **실패가 조용히 묻히지 않는 구조**가 더 중요하다. 이벤트 발행 자체보다도, **실패했을 때 어떻게 정합성을 회복할 것인가**를 더 오래 보게 됐다.

---

## 이 설계에서 일부러 피한 것들

### 1. 도메인 객체가 직접 이벤트를 발행하는 방식

도메인 객체가 자기 안에 이벤트를 쌓고, 저장 시점에 자동으로 발행하는 패턴도 있다.
깔끔하지만, 도메인 객체가 프레임워크에 의존하게 된다. 지금 프로젝트는 도메인과 프레임워크를 분리하는 방향을 유지하고 있어서, Service 계층에서 이벤트를 발행하는 방식으로 충분하다고 봤다.

### 2. 모든 실패를 즉시 보상으로 해결하려는 접근

모든 실패를 즉시 보상으로 풀려는 접근은 언뜻 깔끔해 보이지만, 실제로는 더 복잡한 동시성 문제를 만들 수 있다.

특히 결제처럼 외부 시스템과 맞물린 흐름은,
"실패했으니 즉시 취소"보다
"현재 상태를 확인하고, 확정적으로 보상 가능한 시점에 맞춘다"가 더 현실적일 때가 많다.

---

## 지금 시점의 결론

결국 이 설계는 이벤트를 붙이는 작업이 아니라, **도메인의 책임 경계를 다시 정의하는 작업**이었다.

도메인은 사실 발행까지만 책임지고, 후속 실행은 Command-Handler가 맡는다. 커밋 확정 후(`AFTER_COMMIT`)에 사실을 공개하고, 실패 복구 전략까지 설계에 포함한다.

그리고 지금 내 기준에서 더 중요한 질문은 "이벤트를 누가 발행하느냐?"보다

> "그 이후의 책임을 누가 가져가느냐?"

이 질문에 답이 서야, 구현 수단은 그 다음에 따라온다.

---

## 남은 고민들

아직 끝난 건 아니다. 여전히 남아 있는 질문들도 있다.

- 이벤트 스키마 버전은 어떻게 관리할 것인가
- 실패한 Command의 재처리 정책은 어디에서 가져갈 것인가
- polling과 streamer의 책임을 어디까지 분리할 것인가
- 유실되면 안 되는 이벤트를 프로세스 밖(Kafka 등)으로 내보낼 때, 실행되지 않은 이벤트를 어떻게 감지하고 재실행할 것인가

그래도 적어도 지금은 한 가지가 분명하다.

이벤트 아키텍처는 "비동기를 붙이는 방법"이 아니라,
**시스템이 어떤 사실을 어떻게 받아들이고, 그 이후의 책임을 어떻게 나눌지 정하는 방법**에 가깝다.
