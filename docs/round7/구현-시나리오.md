## TL;DR

- 이번 라운드는 `Step 1 ApplicationEvent → Step 2 Kafka 이벤트 파이프라인 → Step 3 Kafka 기반 선착순 쿠폰 발급` 순서로 진행한다.

## Assumptions

- Quest 문서의 `commerce-collector`는 현재 저장소 기준으로 `commerce-streamer`에 대응시킨다.
- Step 1에서는 핵심 주문 명령 자체를 무조건 비동기로 바꾸지 않는다. 우선 분리 대상은 로깅, 알림, 집계 같은 후속 처리다.
- Step 2의 전달 보장 목표는 `exactly once`가 아니라 `at-least-once + idempotent consumer`다.
- Step 3의 결과 확인 방식은 기본안을 `polling`으로 둔다. callback은 선택 확장으로 본다.
- Step 2의 Outbox 릴레이 기본안은 별도 워커의 polling으로 두고, CDC는 선택 확장으로 남긴다.
- 테스트 전략은 구현 후 보강이 아니라 `TDD`를 기본으로 둔다.

## Not In Scope

- Consumer Group 분리를 필수 범위로 넣지 않는다.
- Consumer 배치 처리 최적화를 필수 범위로 넣지 않는다.
- DLQ 구성을 필수 범위로 넣지 않는다.
- Redis 기반 선착순 처리로 별도 재설계하지 않는다.
- 새 consumer 앱을 추가로 만들지 않는다.

## 공통 기반 작업

### 목표

- Step 1~3 전체에서 흔들리지 않는 경계와 용어를 먼저 고정한다.

### 정리할 것

1. **Command vs Event 경계 정리**
   - Command: 지금 바로 성공/실패가 결정되어야 하는 작업
   - Event: 이미 발생한 사실을 후속 처리에 전달하는 작업
2. **Consumer 앱 고정**
   - Quest 문서 표현과 별개로 구현 대상 consumer 앱은 `commerce-streamer`
3. **토픽/키 기준 초안**
   - `catalog-events` / key=`productId`
   - `order-events` / key=`orderId`
   - `coupon-issue-requests` / key=`couponId`
4. **신규로 필요한 저장 모델 목록 정리**
   - outbox
   - `event_handled`
   - `product_metrics`
   - 쿠폰 발급 요청/결과 상태 모델

### 검증 포인트

- 이후 Step 설명에서 `commerce-collector`를 새 앱처럼 쓰지 않는지 확인한다.
- 핵심 명령과 후속 이벤트를 혼동하지 않는지 확인한다.

## Step 1 — ApplicationEvent로 경계 나누기

### 목표

- 주문–결제 플로우와 좋아요–집계 플로우에서 **후속 처리**를 이벤트로 분리한다.
- “무조건 이벤트화”가 아니라, **무엇이 핵심 명령이고 무엇이 후속 처리인지**를 판단 기준과 함께 고정한다.

### 관련 파일

- `apps/commerce-api/src/main/kotlin/com/loopers/application/order/OrderFacade.kt`
- `apps/commerce-api/src/main/kotlin/com/loopers/domain/like/LikeService.kt`
- Step 1 구현 시 추가될 가능성이 높은 영역
  - `application` 또는 `domain` 하위 event 클래스
  - 이벤트 리스너 클래스

### 구현 순서

1. 주문 흐름에서 핵심 명령과 후속 처리를 나눈다.
   - 유지: 주문 생성, 검증, 재고/쿠폰 정합성과 직접 연결된 핵심 흐름
   - 분리 후보: 유저 행동 로그, 알림, 집계성 후처리
2. 주문 완료 이벤트를 발행하는 구조를 추가한다.
3. `@TransactionalEventListener(phase = AFTER_COMMIT)`를 써서 커밋 이후 후속 처리가 실행되도록 만든다.
4. 좋아요 처리와 좋아요 집계를 분리한다.
   - 좋아요 성공과 집계 성공을 분리해 eventual consistency 방향으로 바꾼다.
5. 서버 레벨 행동 로그(조회, 클릭, 좋아요, 주문 등)를 이벤트 처리 대상으로 정리한다.

### 검증 포인트

- 주문의 핵심 성공/실패 기준이 이벤트 리스너 성공 여부에 종속되지 않아야 한다.
- 트랜잭션이 롤백되면 커밋 이후 리스너가 실행되지 않아야 한다.
- 좋아요 집계 실패가 좋아요 성공을 되돌리지 않아야 한다.

### 다음 구현 요청 예시

- `Step 1 구현해줘. 주문 후속 처리와 좋아요 집계를 ApplicationEvent로 나눠줘`

## Step 2 — Kafka 이벤트 파이프라인

### 목표

- Step 1에서 분리한 이벤트 중 **시스템 간 전파가 필요한 이벤트**를 Kafka로 발행한다.
- `commerce-api → Kafka → commerce-streamer` 파이프라인을 만든다.
- Outbox와 멱등 처리를 포함해 신뢰 가능한 소비 구조를 만든다.

### 관련 파일

- `modules/kafka/src/main/kotlin/com/loopers/config/kafka/KafkaConfig.kt`
- `apps/commerce-streamer/src/main/kotlin/com/loopers/CommerceStreamerApplication.kt`
- `apps/commerce-streamer/src/main/kotlin/com/loopers/interfaces/consumer/DemoKafkaConsumer.kt`
- Step 2 구현 시 추가될 가능성이 높은 영역
  - `commerce-api`의 outbox 저장/발행 로직
  - `commerce-streamer`의 metrics consumer
  - `event_handled`, `product_metrics` 관련 모델/저장소

### 구현 순서

1. Kafka로 나가야 하는 이벤트를 고른다.
   - 예: 좋아요 수, 판매량, 조회 수 등 시스템 간 전파와 집계가 필요한 이벤트
2. Producer 설정을 Quest 요구사항에 맞춘다.
   - `acks=all`
   - `idempotence=true`
3. Transactional Outbox Pattern을 도입한다.
   - 비즈니스 상태 변경과 이벤트 기록을 같은 DB 트랜잭션 안에 넣는다.
4. Outbox를 읽어 Kafka로 발행하는 흐름을 추가한다.
5. `commerce-streamer`에 consumer를 만든다.
6. Consumer에서 `product_metrics` upsert를 구현한다.
7. `event_handled(event_id PK)` 기반 멱등 처리를 추가한다.
8. `manual ack`와 `version` 또는 `updated_at` 기준 최신 이벤트 반영 조건을 넣는다.

### 검증 포인트

- 비즈니스 상태는 저장됐는데 이벤트가 유실되는 상황을 Outbox로 줄여야 한다.
- 같은 이벤트가 다시 들어와도 중복 반영되지 않아야 한다.
- 오래된 이벤트가 최신 집계를 덮어쓰지 않아야 한다.
- consumer는 DB 반영 성공 이후에만 ack 해야 한다.

### 다음 구현 요청 예시

- `Step 2 구현해줘. Outbox, Kafka 발행, commerce-streamer consumer, product_metrics 집계까지 진행해줘`

## Step 3 — Kafka 기반 선착순 쿠폰 발급

### 목표

- 현재의 동기 쿠폰 발급을 Kafka 기반 비동기 구조로 전환한다.
- API는 요청을 접수하고 발행만 하며, 실제 발급은 consumer가 처리한다.
- 수량 제한과 중복 발급 방지를 포함한 선착순 시나리오를 검증한다.

### 관련 파일

- `apps/commerce-api/src/main/kotlin/com/loopers/application/coupon/CouponFacade.kt`
- `apps/commerce-api/src/main/kotlin/com/loopers/domain/coupon/CouponIssueService.kt`
- `apps/commerce-api/src/test/kotlin/com/loopers/application/ConcurrencyTest.kt`
- Step 3 구현 시 추가될 가능성이 높은 영역
  - 쿠폰 발급 요청 발행 API
  - 쿠폰 발급 결과 조회 모델/API
  - `commerce-streamer`의 쿠폰 발급 consumer

### 구현 순서

1. 현재 동기 발급 흐름을 기준선으로 정리한다.
2. API를 “즉시 발급”이 아니라 “발급 요청 저장/발행”으로 바꾼다.
3. `coupon-issue-requests` 토픽으로 요청을 발행한다.
4. consumer에서 선착순 수량 제한과 동일 사용자 중복 발급 방지를 처리한다.
5. 발급 성공/실패 결과를 별도 상태로 저장한다.
6. 사용자가 결과를 조회할 수 있도록 polling 구조를 제공한다.
   - 예: 요청 접수됨 / 처리 중 / 발급 완료 / 중복 요청 / 품절 / 만료
7. 동시성 테스트를 통해 초과 발급이 없는지 검증한다.

### 검증 포인트

- 수량이 100개면 어떤 시점에도 성공 건수는 100개를 넘지 않아야 한다.
- 같은 사용자에게 같은 쿠폰이 중복 발급되지 않아야 한다.
- 실패 상태가 모호하지 않아야 한다.
- API는 “요청 접수”와 “실제 발급 결과”를 분리해서 보여줘야 한다.

### 다음 구현 요청 예시

- `Step 3 구현해줘. 쿠폰 발급 요청 API, Kafka consumer, polling 결과 조회, 동시성 테스트까지 진행해줘`
