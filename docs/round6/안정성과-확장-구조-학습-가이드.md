# 루프팩 BE L2 - Round 6: 안정성과 확장 구조 설계

> 결제/PG 연동, Resilience 패턴, 스케줄러, 콜백 처리 등 안정적 시스템 운영을 위한 구조를 설계한다.

---

## 학습 목표

- 결제 시스템이 왜 "성공 경로"보다 "실패 경로"를 더 많이 설계해야 하는지 이해한다.
- 외부 PG 연동에서 자주 쓰이는 안정성 개념인 서킷 브레이커, 재시도, 타임아웃, 폴백, 벌크헤드, Rate Limiting을 설명할 수 있다.
- 중복 결제와 중복 요청을 막기 위한 멱등성, Exponential Backoff + Jitter의 의미와 필요성을 이해한다.
- 동기 요청, 비동기 콜백, 스케줄러 보정 작업이 함께 있는 결제 흐름을 큰 그림으로 설명할 수 있다.
- 면접에서 "왜 이 패턴이 필요한가", "어떤 부작용이 있는가", "어디에 적용해야 하는가"를 실무 맥락으로 답할 수 있다.

**키워드:** 결제 처리, PG 연동, Resilience 패턴, 스케줄러, 콜백 처리, 폴백 전략, 멱등성

## Agent와 의도한 대로 협업하기

이번 라운드에서는 구현보다 먼저 "실패를 어떻게 다룰 것인가"를 문장으로 분명하게 정리하는 것이 중요하다.
특히 결제 시스템은 잘못된 가정 하나가 중복 승인, 누락 환불, 상태 불일치로 이어질 수 있으므로, Agent에게도 현재 사실과 미래 설계를 구분해서 전달해야 한다.

### Rule-based Collaboration

- 현재 저장소에 있는 것과 없는 것을 먼저 분리해서 적는다. 없는 기능은 "앞으로 설계할 대상"으로 표현하고, 이미 구현된 것처럼 쓰지 않는다.
- "결제 요청이 실패했다"처럼 뭉뚱그리지 말고, 타임아웃인지, 중복 호출인지, 콜백 누락인지까지 나눠서 질문한다.
- 재시도, 폴백, 스케줄러 같은 용어를 요청할 때는 "어떤 실패를 복구하려는가"를 함께 적는다.
- 멱등성은 단순 키워드가 아니라 중복 승인 방지 전략이므로, 주문 ID, 결제 시도 ID, 상태 전이 규칙과 함께 다룬다.
- Agent에게 구현안을 요청할 때는 "현재 저장소에는 payment/PG/resilience flow가 없다"는 전제를 유지하게 한다.

## 결제 시스템 개요

### 현재 저장소 상태

현재 저장소의 `apps/`, `modules/`, `supports/` 영역에는 결제 도메인, PG 클라이언트, Resilience4j 설정, 콜백 처리기, 스케줄러 보정 작업이 확인되지 않는다.
구체적인 코드 경로와 현재 주문 도메인의 상태는 [`구현-시나리오.md`](./구현-시나리오.md)의 Current State 표를 참고한다.
즉, 이 문서는 현재 구현 설명서가 아니라, 앞으로 Round 6 구현 시 어떤 개념을 이해하고 어떤 실패를 대비해야 하는지 정리하는 학습 가이드이다.

### 결제 시스템의 핵심 개념

결제 시스템은 "돈이 실제로 움직이는 요청"을 다룬다.
그래서 일반 CRUD보다 훨씬 더 강하게 다음 질문을 따라가야 한다.

- 요청이 한 번만 처리되었는가?
- 외부 PG는 성공했는데 우리 서버만 실패한 것은 아닌가?
- 사용자 응답과 최종 결제 결과가 다른 시점에 도착할 수 있지 않은가?
- 실패를 복구하는 과정이 오히려 중복 결제를 만들지는 않는가?

결제 흐름을 이해할 때는 보통 아래 네 가지 축으로 생각하면 정리가 쉽다.

| 축 | 왜 중요한가 | 면접에서 설명하는 포인트 |
|----|-------------|--------------------------|
| **정합성** | 주문 상태, 결제 상태, 재고 상태가 서로 어긋나면 장애가 된다. | "결제 성공"만이 아니라 "성공했는데 우리 시스템이 아직 모르는 상태"도 설계 대상이라고 설명한다. |
| **멱등성** | 같은 요청이 여러 번 들어와도 결과가 한 번만 반영되어야 한다. | 네트워크 재전송, 사용자 새로고침, 콜백 중복 수신을 예로 들 수 있다. |
| **관찰 가능성** | 실패 원인을 알아야 복구 정책을 조정할 수 있다. | 실패율, 타임아웃, 재시도 횟수, 오픈된 서킷 수 같은 지표를 말하면 좋다. |
| **복구 가능성** | 즉시 처리되지 못한 결제를 나중에 바로잡아야 한다. | 콜백, 폴링, 스케줄러, 수동 보정이 왜 필요한지 연결해서 설명한다. |

결제 시스템은 흔히 "요청-응답 한 번"으로 끝나지 않는다.
사용자 결제 요청, PG 승인 요청, PG 콜백, 내부 상태 갱신, 실패 보정 작업이 따로 움직일 수 있으므로, 상태 전이를 명확히 설계하는 것이 핵심이다.

## Resilience 패턴

### 현재 저장소 상태

현재 저장소에는 Resilience4j 의존성이나 관련 설정이 확인되지 않는다.
따라서 이 섹션은 "이미 적용된 라이브러리 사용법"이 아니라, 결제/PG 연동을 설계할 때 어떤 보호 장치를 고려해야 하는지 정리하는 개념 문서로 읽어야 한다.

실무 구현 단계에서는 Resilience4j를 대표적인 참고 도구로 검토할 수 있지만, 이 저장소에서 이미 채택된 결정이라고 보아서는 안 된다.

### 결제/PG 연동에서 알아야 할 핵심 패턴

#### 1. 서킷 브레이커

- **왜 중요한가:** PG가 이미 장애 상태인데도 계속 요청을 보내면 우리 애플리케이션의 스레드와 커넥션까지 같이 고갈된다.
- **어떻게 동작하는가:** 최근 실패율이나 느린 호출 비율이 임계치를 넘으면 회로를 열고(Open), 잠시 동안 실제 호출을 막는다. 이후 일부 요청만 시험적으로 흘려보내며(Half-Open) 회복 여부를 본다.
- **트레이드오프:** 임계치를 너무 민감하게 잡으면 일시적 흔들림도 장애로 오인하는 false positive가 생긴다. 반대로 너무 둔감하면 이미 실패가 확산된 뒤에야 차단한다.
- **면접에서는 이렇게 설명하면 좋다:** "서킷 브레이커는 외부 장애를 빨리 감지해서 우리 시스템까지 같이 무너지는 것을 막는 장치입니다. 결제 승인처럼 외부 의존성이 강한 구간에서 특히 중요합니다." 

#### 2. 재시도

- **왜 중요한가:** 네트워크 순간 단절, 일시적 5xx, 짧은 타임아웃은 한 번 더 시도하면 성공하는 경우가 있다.
- **어떻게 동작하는가:** 실패 원인이 일시적이라고 판단되는 경우에만 제한된 횟수 안에서 다시 요청한다.
- **트레이드오프:** 재시도는 성공률을 올릴 수 있지만, 잘못 쓰면 같은 결제를 여러 번 승인하려고 시도하는 부작용이 생긴다. 그래서 멱등성 없이 재시도부터 넣으면 위험하다.
- **면접에서는 이렇게 설명하면 좋다:** "재시도는 실패를 없애는 기능이 아니라 일시 장애를 흡수하는 기능입니다. 결제처럼 부작용이 큰 요청에서는 재시도 조건과 멱등성 보장이 함께 있어야 합니다." 

#### 3. 타임아웃

- **왜 중요한가:** 외부 응답을 무한정 기다리면 사용자 요청 하나가 스레드를 오래 점유하고, 결국 전체 서비스가 느려진다.
- **어떻게 동작하는가:** 정해진 시간 안에 응답이 오지 않으면 호출을 실패로 간주하고 다음 복구 경로로 넘긴다.
- **트레이드오프:** 타임아웃이 너무 짧으면 정상적인 느린 응답도 실패로 처리한다. 너무 길면 장애 전파를 막지 못한다. 읽기 타임아웃, 연결 타임아웃을 구분해서 생각하는 것도 중요하다.
- **면접에서는 이렇게 설명하면 좋다:** "타임아웃은 빠른 실패를 통해 자원을 보호하는 기본 장치입니다. 외부 PG 연동에서는 평균 응답 시간과 장애 시나리오를 기준으로 조정해야 합니다." 

#### 4. 폴백

- **왜 중요한가:** 일부 기능은 완전 실패 대신 제한된 응답을 반환해 사용자 경험이나 운영 복구 여지를 남길 수 있다.
- **어떻게 동작하는가:** 원래 호출이 실패했을 때 미리 정한 대체 로직으로 우회한다.
- **트레이드오프:** 결제 승인 자체에는 성급한 폴백이 위험하다. 승인 결과를 추정해서 성공처럼 보여주면 안 된다. 결제 영역의 폴백은 대개 "결제 대기 상태로 전환 후 추후 확인"처럼 보수적으로 설계해야 한다.
- **면접에서는 이렇게 설명하면 좋다:** "결제에서는 폴백을 성공 대체 수단으로 쓰기보다, 불확실한 상태를 안전하게 보류하는 방향으로 씁니다." 

#### 5. 벌크헤드

- **왜 중요한가:** 특정 외부 연동의 장애가 전체 서버 자원 고갈로 번지는 것을 막아야 한다.
- **어떻게 동작하는가:** 결제 호출 전용 스레드 풀이나 세마포어 제한을 둬서, PG 장애가 다른 주문 조회나 회원 기능까지 막지 못하게 분리한다.
- **트레이드오프:** 격리를 과하게 하면 자원 활용률이 낮아지고, 너무 적게 나누면 장애 전파를 막지 못한다.
- **면접에서는 이렇게 설명하면 좋다:** "벌크헤드는 배의 격벽처럼 장애 영향을 가두는 전략입니다. 결제 연동이 느려져도 다른 핵심 기능은 살아 있도록 자원을 분리합니다." 

#### 6. Rate Limiting

- **왜 중요한가:** 트래픽 급증이나 비정상 반복 호출이 있을 때 우리 시스템과 외부 PG 모두를 보호해야 한다.
- **어떻게 동작하는가:** 사용자, 주문, API 키, 시간 구간 단위로 허용 요청 수를 제한한다.
- **트레이드오프:** 너무 강하게 제한하면 정상 사용자도 차단된다. 너무 느슨하면 보호 장치 역할을 못 한다. 운영 환경에서는 사용자 단위와 시스템 단위 제한을 구분해 설계하는 경우가 많다.
- **면접에서는 이렇게 설명하면 좋다:** "Rate Limiting은 성능 최적화보다 보호 장치에 가깝습니다. 결제 버튼 연타나 봇성 호출로 인한 중복 시도를 줄이는 데도 도움이 됩니다." 

#### 7. 멱등성

- **왜 중요한가:** 결제 시스템에서 가장 치명적인 문제 중 하나는 같은 결제가 여러 번 승인되는 것이다.
- **어떻게 동작하는가:** 같은 idempotency key, 주문 번호, 결제 시도 번호로 들어온 요청은 한 번만 처리하고, 이후 동일 요청에는 같은 결과를 반환하거나 중복 실행을 막는다.
- **트레이드오프:** 멱등성 키 저장 기간, 키 충돌 방지, 요청 본문 동일성 검증 기준을 정해야 한다. 키만 저장하고 상태 전이 규칙이 없으면 불완전한 멱등성이 된다.
- **면접에서는 이렇게 설명하면 좋다:** "재시도와 멱등성은 같이 가야 합니다. 재시도는 중복 호출을 만들 수 있고, 멱등성은 그 중복이 실제 중복 처리로 이어지지 않게 막습니다." 

#### 8. Exponential Backoff + Jitter

- **왜 중요한가:** 장애가 난 순간 모든 인스턴스가 같은 간격으로 재시도하면 다시 한 번 트래픽 폭탄을 만들 수 있다.
- **어떻게 동작하는가:** 재시도 간격을 점점 늘리고(Exponential Backoff), 각 요청에 약간의 무작위 지연(Jitter)을 섞어서 재시도 시점을 분산한다.
- **트레이드오프:** 백오프를 너무 길게 잡으면 복구는 안전하지만 사용자 체감이 나빠질 수 있다. 너무 짧으면 장애 구간에 다시 몰린다.
- **면접에서는 이렇게 설명하면 좋다:** "Exponential Backoff + Jitter는 재시도를 똑똑하게 만드는 방식입니다. 같은 시점에 실패한 요청들이 한꺼번에 다시 몰리지 않도록 분산합니다." 

### 실무 사례: 주문 재시도 로직

결제 연동에서 재시도가 필요한 대표 상황은 아래와 같다.

- PG 연결 타임아웃이 났지만, 실제 승인이 되었는지 확정되지 않은 경우
- PG에서 일시적 5xx를 반환한 경우
- 우리 서버가 콜백을 받기 전에 사용자 응답 연결이 끊긴 경우

이때 중요한 것은 "무조건 다시 호출"이 아니라 "무엇을 다시 호출해도 안전한가"이다.

- **안전한 재시도 후보:** 조회성 상태 확인 API, 멱등성이 보장된 승인 요청
- **위험한 재시도 후보:** 멱등성 키 없이 다시 보내는 승인 요청, 이미 처리 여부를 모르는 환불 요청

면접에서 이 부분을 설명할 때는 아래처럼 말하면 구조가 잡힌다.

> "재시도는 일시 장애를 흡수하기 위한 수단이지만, 결제에서는 부작용이 큰 작업이 많아서 무조건 적용하면 안 됩니다. 저는 먼저 타임아웃과 오류 유형을 구분하고, 멱등성이 보장된 호출에만 Exponential Backoff + Jitter를 적용하겠습니다. 결과가 불확실한 경우에는 재시도보다 상태 조회나 보정 작업으로 전환하겠습니다."

## 스케줄러와 콜백 처리

### 현재 저장소 상태

현재 저장소에는 스케줄러 기반 결제 보정 작업이나 PG 콜백 처리 엔드포인트 구현이 확인되지 않는다.
따라서 이 섹션 역시 현재 기능 설명이 아니라, Round 6에서 왜 이 구성이 필요한지 이해하기 위한 설계 원칙 정리이다.

### 스케줄러 설계 원칙

스케줄러는 "실시간 요청에서 놓친 일을 나중에 바로잡는 장치"로 이해하면 쉽다.

- 콜백 누락, 일시 장애, 내부 트랜잭션 실패로 인해 남은 미완료 상태를 다시 점검한다.
- 한 번에 너무 많은 대상을 잡지 말고, 시간 범위와 배치 크기를 제한해 점진적으로 처리한다.
- 재실행되어도 안전해야 하므로, 스케줄러 작업 자체도 멱등하게 설계한다.
- 실패 원인을 로깅하고, 반복 실패 건은 별도 보정 대상로 분리한다.
- "자동 복구"와 "운영자 확인이 필요한 건"을 구분한다.

결제 시스템에서 스케줄러는 성공 경로의 주인공이 아니라, 비정상 종료와 상태 불일치를 줄이는 안전망이다.

### 콜백 처리 패턴

PG 콜백은 "외부 시스템이 최종 결과를 알려주는 비동기 이벤트"에 가깝다.
따라서 컨트롤러에서 바로 모든 후속 처리를 끝내려 하기보다, 아래 원칙으로 다루는 것이 일반적이다.

- 콜백 수신 자체는 빠르게 끝내고, 검증과 상태 반영은 분리한다.
- 서명 검증, 주문 식별, 중복 콜백 방지를 먼저 처리한다.
- 이미 완료된 상태에 다시 성공 콜백이 와도 안전해야 한다.
- 콜백 순서가 바뀌거나 늦게 도착하는 경우를 고려한다.
- 내부 상태 전이는 "PENDING -> PAID", "PENDING -> FAILED"처럼 허용 가능한 경로를 명시한다.

면접에서는 "사용자 응답과 최종 결제 결과는 같은 타이밍에 오지 않을 수 있다"는 점을 강조하면 좋다.
이 한 문장만 분명히 말해도 동기/비동기 혼합 구조를 이해하고 있다는 인상을 줄 수 있다.

## 확장성 있는 주문 처리 구조

### 현재 저장소 상태

현재 저장소에는 주문 도메인 관련 코드와 문서가 존재하지만, 주문 생성 이후 결제 승인, PG 연동, 콜백 반영, 실패 보정까지 이어지는 payment/PG/resilience flow는 아직 구현되어 있지 않다.

### 주문 플로우와 결제 연동

미래 구현을 상상할 때는 아래와 같은 흐름으로 큰 그림을 정리하면 좋다.

1. 주문 생성 요청을 받는다.
2. 주문을 즉시 확정하지 않고 결제 대기 상태로 만든다.
3. 외부 PG 승인 요청을 보낼 때 타임아웃, 재시도 정책, 멱등성 키를 함께 고려한다.
4. 즉시 응답이 불확실하면 결제 상태를 확정하지 않고 대기 또는 확인 필요 상태로 둔다.
5. PG 콜백이나 상태 조회 결과를 바탕으로 최종 결제 상태를 반영한다.
6. 누락 건은 스케줄러가 다시 확인한다.

이 구조의 핵심은 "주문 생성"과 "결제 최종 확정"을 같은 순간에 끝나는 단일 이벤트로 보지 않는 것이다.
외부 시스템이 끼는 순간, 상태는 지연될 수 있고 결과는 뒤늦게 도착할 수 있다.

면접에서는 다음 관점으로 정리하면 설명이 쉬워진다.

- **상태 분리:** 주문 상태와 결제 상태를 분리해 생각한다.
- **시간 분리:** 사용자 요청 처리 시점과 최종 확정 시점을 분리해 생각한다.
- **장애 분리:** 일시 장애, 확정 불가, 중복 콜백, 운영 보정 대상을 나눠 생각한다.

## 스스로 답해볼 질문

- 서킷 브레이커와 타임아웃은 둘 다 실패를 빨리 끊는 전략인데, 역할이 어떻게 다른가?
- 재시도는 왜 성공률을 높이면서도 동시에 장애를 키울 수 있는가?
- 결제 승인 요청에 멱등성이 없으면 어떤 사고가 날 수 있는가?
- Exponential Backoff + Jitter가 없으면 장애 순간에 어떤 현상이 생길 수 있는가?
- 폴백이 모든 외부 연동에 좋은 것은 아닌데, 결제에서는 왜 특히 조심해야 하는가?
- 콜백이 중복 수신되거나 순서가 뒤바뀌면 어떤 상태 전이 규칙이 필요할까?
- 스케줄러는 어떤 경우에 실시간 처리 대신 사후 보정 장치로 두는 것이 적절한가?
- "현재 저장소에는 아직 구현이 없다"는 사실과 "앞으로 이렇게 설계할 수 있다"는 제안을 문서에서 어떻게 구분해 설명할 것인가?

## 학습 순서 제안

1. **결제 시스템의 실패 유형부터 정리하기**
   - 중복 요청, 타임아웃, 응답 유실, 콜백 누락, 상태 불일치를 먼저 구분한다.
2. **멱등성과 상태 전이 이해하기**
   - 결제에서 왜 한 번만 처리되어야 하는지, 어떤 상태가 허용되는지 먼저 잡는다.
3. **타임아웃, 재시도, Exponential Backoff + Jitter 이해하기**
   - 일시 장애를 흡수하는 가장 기본적인 복원력 패턴을 익힌다.
4. **서킷 브레이커, 벌크헤드, Rate Limiting 이해하기**
   - 실패 흡수보다 한 단계 더 나아가 장애 전파를 차단하는 관점으로 확장한다.
5. **콜백과 스케줄러 구조 이해하기**
   - 동기 응답만으로 결제가 끝나지 않는 구조를 받아들인다.
6. **면접 답변으로 압축해보기**
   - 각 개념마다 "왜 필요했는지", "어떻게 동작하는지", "부작용은 무엇인지"를 1분 안에 설명해 본다.
