# Round 6 구현 시나리오: 결제 안정성과 확장 구조

> TL;DR: 현재 저장소에는 주문 생성/조회 흐름과 공통 에러 처리 기반은 존재하지만, 결제 도메인, PG Client, 콜백 처리, 스케줄러, Resilience4j 기반 장애 대응 흐름은 아직 없다.
> Round 6에서는 이 "없는 영역"을 한 번에 크게 만들기보다, 결제 도메인 모델링 -> PG 연동 추상화 -> 주문/결제 통합 -> 안정성 패턴 -> 후처리 순서로 단계적으로 구현한다.

### 현재 저장소에 없는 것

- 결제 도메인 패키지와 결제 관련 Kotlin 파일은 확인되지 않았다. (`**/payment/**`, `**/*Payment*` 검색 결과 없음)
- PG Client 또는 PG 연동 어댑터로 볼 수 있는 구현은 확인되지 않았다.
- `resilience4j` 문자열은 코드가 아니라 학습 가이드 문서에서만 확인됐고, 실제 애플리케이션 코드에는 없다.
- `@Scheduled` 사용처가 없어 미결제 주문 만료 같은 스케줄러 구현은 아직 없다.
- `callback` 관련 Kotlin 구현이 없어 PG 콜백 수신/검증 흐름도 아직 없다.

### 현재 상태 해석

- 이미 있는 기반: 주문 도메인, 주문 API, 트랜잭션 경계, 공통 에러 처리
- 아직 만들어야 하는 영역: 결제 상태 머신, PG 연동 추상화, 장애 대응 패턴, 비동기 후처리, 콜백/재처리 구조
- 따라서 Round 6의 핵심은 기존 주문 흐름을 뜯어고치는 것이 아니라, 기존 주문 흐름 위에 결제 계층을 안전하게 얹는 것이다.

## Assumptions

### 설계 전제

- 주문은 이미 생성 가능하므로, Round 6에서는 "주문 생성"과 "결제 승인/실패 처리"를 분리된 책임으로 다룬다.
- 결제 도메인은 `orderId`를 참조해 주문과 연결하되, 결제 시도/상태/외부 거래 식별자는 별도 엔티티가 관리한다.
- 주문 금액의 기준값은 `OrderModel.originalTotalAmount` 및 `OrderModel.totalAmount`를 재사용한다.
- 공통 예외는 기존 `CoreException` + `ErrorType` 체계를 그대로 따른다. 새로운 실패도 가능한 한 기존 에러 타입에 매핑한다.
- 실제 상용 PG 연동이 아니라, 우선은 인터페이스 + 시뮬레이터/스텁으로 애플리케이션 구조를 먼저 굳힌다.

### 패키지/레이어 전제

- `domain/payment/`: `PaymentModel`, 상태 enum, repository interface, domain service
- `application/payment/`: 결제 시작/확정/실패/조회 유스케이스를 조율하는 facade
- `interfaces/api/payment/`: 결제 요청, 콜백 수신, 조회 API
- `infrastructure/payment/`: JPA repository 구현, PG client adapter, 외부 응답 매핑
- 스케줄러가 필요하면 `infrastructure/payment/` 또는 별도 scheduler 패키지에 두되, 첫 구현은 주문/결제 만료 처리에만 집중한다.

### Must-Have vs Nice-To-Have

| 구분 | 항목 | 이유 |
|------|------|------|
| Must-Have | Fallback | PG 장애 시 사용자 응답과 내부 상태를 일관되게 정리해야 한다. |
| Must-Have | Timeout | 외부 호출 지연이 주문 트랜잭션 전체를 오래 점유하지 않게 해야 한다. |
| Must-Have | CircuitBreaker | 장애가 난 PG로 계속 호출이 몰리지 않게 해야 한다. |
| Nice-To-Have | Retry | 일시 실패 복구에 유용하지만, 중복 승인/멱등성 설계와 함께 다뤄야 하므로 후순위가 안전하다. |

## Not In Scope

- 실제 PG사 인증 연동과 운영용 상점 키 관리
- 환불, 부분 취소, 정산, 관리자 결제 대시보드
- 이벤트 기반 분산 처리 구조나 운영 가시성 고도화를 이번 라운드의 핵심 범위로 확장하는 작업
- 다중 PG 라우팅, 고급 라우팅 정책, 지역화/통화 처리
- `docs/round6/구현-현황-리포트.md` 작성 또는 확장

## 전체 구현 로드맵

```text
Phase 0  현재 주문 흐름을 깨지 않는 결제 구조 설계
   ↓
Phase 1  Payment 도메인 모델링 + 상태 전이 테스트
   ↓
Phase 2  PG Client 인터페이스/시뮬레이터 구현
   ↓
Phase 3  Order -> Payment 통합 유스케이스 구현
   ↓
Phase 4  안정성 패턴 적용 (Timeout, CircuitBreaker, Fallback 우선)
   ↓
Phase 5  미완료 결제 후처리 (만료 스케줄러 + 콜백 기초)
   ↓
Phase 6  통합/E2E 검증 및 회귀 테스트 정리
```

- 구현 우선순위는 "도메인 정합성 -> 외부 연동 추상화 -> 장애 대응 -> 후처리"다.
- Retry는 Nice-To-Have이므로 Phase 4 완료 이후 별도 소과업으로 다루는 것이 안전하다.

## 추천 테스트 흐름(TDD)

1. 도메인부터 시작한다. `PaymentModel`, `PaymentStatus`, `PaymentService`의 상태 전이 규칙을 먼저 테스트로 고정한다.
2. 그다음 PG adapter를 붙인다. 외부 응답 성공/실패/지연을 simulator로 재현해 매핑을 검증한다.
3. 이후 주문/결제 통합 테스트를 추가한다. 기존 `OrderFacade` 흐름에 결제가 들어와도 주문 규칙이 깨지지 않는지 본다.
4. 마지막으로 timeout, circuit breaker, fallback 같은 장애 시나리오 테스트를 붙인다. Retry는 멱등성 설계가 정리된 뒤 별도 추가한다.
5. 후처리 단계에서는 스케줄러와 콜백을 각각 단위 테스트한 뒤, 충돌 가능성을 통합 테스트로 검증한다.

## 구현 순서 요약

- 먼저 만들 것: `domain/payment`와 기본 상태 전이 테스트
- 다음으로 붙일 것: `infrastructure/payment`의 PG client 인터페이스와 simulator
- 그다음 확장할 것: `application/order`, `application/payment`, `interfaces/api/payment`
- 마지막에 붙일 것: Timeout/CircuitBreaker/Fallback, 스케줄러, 콜백, E2E

이 문서는 현재 저장소 사실과 앞으로의 구현 단계를 분리해 안내하는 실행 문서다. `구현-현황-리포트.md`는 이번 범위에 포함하지 않는다.
