# Round 6 기술 글쓰기 가이드 (Optional Quest)

> 이 문서는 Round 6 Optional Technical Writing Quest용 실전 작성 가이드다.
> 핵심은 "무엇을 만들었다" 나열이 아니라 "왜 그렇게 판단했는가"를 증거와 함께 설명하는 것이다.

---

## 이 가이드의 입력 문서

Optional Quest 글을 쓰기 전에 아래 두 문서를 먼저 읽고 메모한다.

1. `docs/round6/안정성과-확장-구조-학습-가이드.md`
2. `docs/round6/구현-시나리오.md`

작성 내용은 위 두 문서의 사실, 용어, 범위와 일치해야 한다.

---

## TL;DR

Round 6 글은 구현 목록이 아니라 의사결정 기록이다.
각 판단은 "문제 상황 -> 선택지 -> 선택 근거 -> 트레이드오프 -> 남은 한계" 순서로 작성한다.
근거 없는 단정, 존재하지 않는 구현 주장, 결과만 있는 회고는 감점 요인으로 본다.

---

## 왜 그렇게 판단했는가

이 섹션은 Optional Quest 글의 중심이다. 아래 템플릿 문장을 그대로 변형해서 사용한다.

### 기본 문장 패턴

- 판단 배경: "`[장애/요구 상황]` 때문에 `[...]`를 먼저 해결해야 했다."
- 선택 이유: "`[대안 A]`와 `[`대안 B]`를 비교했을 때, 현재 저장소 제약(`[...]`)상 `[`선택안]`이 더 안전했다."
- 포기 비용: "이 선택으로 `[`얻은 점]`은 커졌지만, `[`잃은 점]`을 감수했다."
- 검증 근거: "이 판단은 `[`문서/코드/테스트 근거]`로 확인했다."

### 트레이드오프를 쓰는 최소 규칙

- "장점만" 쓰지 말고, 반드시 비용이나 제약을 1개 이상 쓴다.
- "나중에 개선" 같은 추상 문장 대신, 어떤 조건에서 개선할지 기준을 적는다.
- 실패 경로(타임아웃, 중복 요청, 콜백 지연 등)를 판단 근거에 포함한다.

---

## 증거를 인용하는 방법

Round 6 글에서 주장은 아래 4종 근거 중 최소 2종 이상으로 뒷받침한다.

1. **문서 근거**: `안정성과-확장-구조-학습-가이드` 또는 `구현-시나리오`의 섹션 제목/표
2. **코드 근거**: 실제 클래스/함수/테스트 이름
3. **실험 근거**: 실패 재현 조건, 기대 결과, 실제 관찰 결과
4. **제약 근거**: 현재 저장소에 없는 컴포넌트(예: PG client 부재) 같은 사실

권장 문장 패턴:

- "`구현-시나리오`의 `Current State` 기준으로 현재 저장소에는 `[...]`가 없다. 따라서 `[...]`를 전제로 설계했다."
- "`안정성과-확장-구조-학습-가이드`의 `Resilience 패턴`에서 정리한 실패 유형을 기준으로 `[...]` 우선순위를 정했다."
- "코드 기준으로는 `[`파일/심볼]`이 현재 책임 경계를 보여 주므로 `[...]`로 분리했다."

---

## 표현 형식 가이드 (Optional Quest)

### 코드 비교

- 코드 비교는 "좋아 보이는 코드" 소개가 아니라 판단 근거 제시용으로 사용한다.
- 최소 형식: `비교 대상(전/후 또는 A/B) -> 차이 2~3개 -> 선택 이유 -> 포기한 대안의 비용`.
- 권장 문장: "코드 비교 결과, `[...]`는 읽기 쉬웠지만 `[...]` 제약 때문에 `[...]`를 채택했다."

### 흐름도

- 흐름도는 복잡한 결제/상태 전이를 요약하는 도구로만 사용하고, 그림이 없어도 텍스트 흐름 설명을 함께 적는다.
- 최소 형식: `시작 조건 -> 주요 분기(성공/실패/불확실) -> 최종 상태 -> 보정 경로`.
- 권장 문장: "흐름도 기준으로 사용자 응답 시점과 최종 확정 시점을 분리해 설명했다."

### 리팩터링 전후 예시

- 리팩터링 전후 예시는 성능 자랑이 아니라 책임 분리나 실패 처리 개선 근거를 보여 주는 데 사용한다.
- 최소 형식: `리팩터링 전 문제 1~2개 -> 리팩터링 후 변화 -> 부작용/남은 한계`.
- 권장 문장: "리팩터링 전후 예시에서 `[...]` 중복은 줄었지만, `[...]` 한계는 후속 검증 항목으로 남겼다."

## 좋은 톤

아래 톤을 유지하면 기술 글이 설득력 있게 읽힌다.

- 사실과 해석을 분리해 쓴다. (사실: 현재 상태, 해석: 선택 이유)
- 단정 대신 조건을 붙인다. ("항상"보다 "이 제약에서는")
- 과장 대신 검증 가능한 표현을 쓴다. ("완벽" 대신 "중복 결제 위험을 낮춘다")
- 결과보다 사고 과정을 먼저 보여 준다. (결론 1문장 + 근거 2~3문장)

권장 문장 예시:

- "이번 선택은 가장 빠른 구현이 아니라, 실패 전파를 줄이는 방향을 우선한 결정이다."
- "현재 저장소에는 결제 도메인이 없어, 적용 완료가 아니라 적용 전략으로 범위를 제한했다."

---

## 피해야 할 스타일

아래 표현은 Round 6 Optional Quest 문서에서 금지한다.

- 구현 사실을 확인하지 않고 "이미 적용했다"고 쓰는 문장
- 트레이드오프 없이 "베스트 프랙티스"만 나열하는 문장
- 코드/문서 근거 없이 결론만 선언하는 문장
- "좋아졌다", "안정적이다"처럼 측정 기준이 없는 문장

### 명시적 금지 규칙

**존재하지 않는 구현을 지어내서 쓰지 않는다.**
현재 저장소에 없는 payment domain, PG 연동, resilience 설정, scheduler, callback 구현을 "완료"처럼 서술하면 안 된다.
미래 설계는 반드시 "제안", "가정", "후속 구현 계획"으로 구분해서 쓴다.

## 초안 체크리스트

초안을 완성한 뒤, 아래 항목을 모두 통과해야 제출한다.

- [ ] TL;DR 2~3문장에 글 목적과 핵심 판단이 들어갔는가?
- [ ] 각 핵심 판단마다 "왜 그렇게 판단했는가"가 1회 이상 명시되었는가?
- [ ] 각 판단에 근거(문서/코드/실험/제약) 2종 이상이 연결되었는가?
- [ ] 장점과 함께 트레이드오프(비용/한계)가 같이 적혔는가?
- [ ] 현재 사실과 미래 계획을 문장에서 구분했는가? (예: "현재 없음", "향후 적용")
- [ ] 존재하지 않는 구현을 완료처럼 표현한 문장이 없는가?
- [ ] 마지막 단락에 "남은 리스크"와 "다음 검증 항목"을 적었는가?

## 권장 아웃라인 (복붙용)

1. TL;DR
2. 문제 맥락과 제약
3. 핵심 판단 1~3개 (`왜 그렇게 판단했는가` 포함)
4. 대안 비교와 트레이드오프
5. 증거(문서/코드/실험) 정리
6. 한계와 다음 검증 계획

이 구조를 따르면 Round 6 Optional Quest에서 "구현 나열"이 아니라 "판단 가능한 기술 문서"를 만들 수 있다.
