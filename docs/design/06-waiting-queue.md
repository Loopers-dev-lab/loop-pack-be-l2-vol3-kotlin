# 대기열 처리량 설계 — 배치 크기 산정 근거

## 📌 Summary

- 배경: 행사 트래픽이 몰리면 주문 API가 DB 커넥션 풀을 고갈시켜 전체 서비스가 마비될 수 있다. 주문 API 앞단에 Redis Sorted Set 기반 대기열을 두고, 스케줄러가 시스템이 감당 가능한 속도로만 유저를 입장시킨다.
- 목표: 하류 시스템(DB)의 실제 한계를 기준으로 스케줄러 배치 크기를 산정하고, 그 근거를 남긴다.
- 결과: 100ms마다 14명씩 입장 토큰을 발급한다. 설계 처리량은 140 TPS다.

## 🧮 배치 크기 산정

### 근거가 되는 실측 기준

| 항목 | 값 | 출처 |
| --- | --- | --- |
| DB 커넥션 풀 | 40 | `modules/jpa/jpa.yml`의 `maximum-pool-size: 40` |
| 주문 1건 평균 처리 시간 | 200ms | 재고 차감(비관적 락) + 쿠폰 적용 + 주문 저장 기준 추정치 |
| 안전 마진 | 70% | 주문 외 API(상품 조회, 주문 목록)도 같은 풀을 쓰므로 여유 확보 |

### 계산

```
이론적 최대 TPS = 커넥션 풀 / 평균 처리 시간 = 40 / 0.2 = 200 TPS
설계 처리량     = 200 * 0.7 = 140 TPS
배치 크기       = 140 TPS * 0.1초(스케줄러 주기) = 14명
```

처음에는 발제 예시의 커넥션 풀 50을 그대로 가져와 배치 크기를 18로 잡았습니다. 그런데 실제 설정을 확인해 보니 이 프로젝트의 풀은 40이었고, 예시 숫자로 산정한 값은 실제 시스템 기준으로 약 29% 초과 발급이었습니다. 산정 공식의 의미는 "하류가 감당 가능한 만큼만 흘려보낸다"는 것인데 입력값이 실제와 다르면 공식 자체가 무의미해지므로, 실측 설정 기준으로 14명으로 정정했습니다.

평균 처리 시간 200ms는 아직 부하 테스트로 검증하지 못한 추정치입니다. 이 값이 실측과 달라지면 배치 크기도 같이 재산정해야 하며, 그래서 계산식과 입력값의 출처를 코드 주석(`QueueEntryScheduler`)과 이 문서에 함께 남깁니다.

## ⏱️ 스케줄러 주기 100ms — Thundering Herd 완화

1초에 140명을 한 번에 입장시키면 140개의 커넥션 요청이 동시에 몰립니다. 이것은 대기열이 막으려던 문제의 축소판입니다. 그래서 발급을 1초 단위가 아니라 100ms 단위로 쪼개 14명씩 나눠 보냅니다. 순간 부하가 10분의 1로 평탄화되고, 커넥션 풀 40 대비 동시 진입 14명이므로 주문 외 API가 쓸 여유도 유지됩니다.

토큰에 랜덤 지연(Jitter)을 더하는 방법도 있지만, 100ms 분산 발급만으로 동시 진입 규모가 풀 크기 아래로 내려가므로 현 단계에서는 도입하지 않았습니다. 부하 테스트에서 스파이크가 관측되면 그때 추가합니다.

## 🎫 토큰 TTL 5분

토큰을 받은 유저가 주문을 완료할 때까지 걸리는 시간을 상품 확인과 결제 수단 선택을 포함해 넉넉히 3분 이내로 보고, 여유를 더해 5분(300초)으로 설정했습니다. TTL이 짧으면 정상 유저가 만료로 튕겨 재진입 비용이 발생하고, 길면 이탈한 유저의 토큰이 자리를 차지해 뒷사람의 대기가 늘어납니다. 5분은 추정 기반 초기값이며, 운영에서는 토큰 발급 대비 주문 완료 비율(Token Conversion Rate)을 보고 조정하는 것이 맞습니다.

## 📊 예상 대기 시간 계산

순번 조회 API는 `내 순번 * (1 / 140)초`로 예상 대기 시간을 계산합니다. 설계 처리량 140 TPS의 역수를 유저 1명당 대기 시간으로 쓰는 것입니다. 토큰 만료로 인한 재발급이나 실제 처리량 변동은 반영하지 못하는 추정값이므로, 클라이언트에는 "약 N초"로 표기하는 것을 전제로 합니다.

## ⚠️ 남은 리스크와 의도적으로 미룬 결정

- Redis 장애 시 현재 동작은 전면 차단입니다. 대기열 진입과 토큰 검증이 모두 Redis를 거치므로, Redis가 죽으면 주문 진입 자체가 막힙니다. 우회(bypass)나 Fallback 큐는 과부하 위험과 순번 공정성 훼손을 감수해야 해서, "차단이 기본, 우회는 운영 판단으로 수동 전환" 방침만 정해두고 자동 Fallback은 구현하지 않았습니다.
- 스케줄러는 단일 인스턴스 실행을 전제합니다. 다중 인스턴스로 확장하면 `ZPOPMIN` 자체는 원자적이라 중복 발급은 없지만, 인스턴스 수만큼 발급 속도가 배가되어 산정한 처리량을 초과합니다. 확장 시 분산 락 또는 리더 선출이 필요합니다.
- 평균 처리 시간 200ms와 토큰 TTL 5분은 부하 테스트와 운영 지표로 검증해야 하는 추정값입니다. Queue Depth, Avg Wait Time, Token Expiry Rate를 모니터링 대상으로 삼습니다.
- 순번 조회(폴링) 경로는 토큰 GET, ZRANK, ZCARD 3회를 순차 왕복합니다. 세 호출 모두 같은 유저와 같은 키 대상이라 Lua 스크립트나 파이프라인으로 1왕복까지 줄일 수 있고, 시점 불일치(순번과 전체 인원이 서로 다른 스냅샷)도 함께 사라집니다. 현재는 클램프로 모순 응답만 막아두었고, 폴링 부하가 실측으로 문제가 될 때 통합하기로 미뤘습니다.
