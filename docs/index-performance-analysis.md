# 인덱스 성능 분석: products 테이블

## 환경

- MySQL 8.0
- products 테이블: 100,000건
- brands 테이블: 100건 (멱급수 분포로 상품 할당)

## 대상 쿼리

```sql
SELECT * FROM products WHERE brand_id = 1 ORDER BY likes;
```

## 생성한 인덱스

```sql
CREATE INDEX idx_products_brand_id_likes ON products (brand_id, likes);
```

- `brand_id`: WHERE 절의 동등 조건(=)을 인덱스 선두 컬럼으로 배치
- `likes`: ORDER BY 대상을 후행 컬럼으로 배치하여 정렬 연산 제거

## 분석

| 항목 | 인덱스 전 | 인덱스 후 | 개선 내용 |
|------|-----------|-----------|-----------|
| type | ALL | ref | 풀 테이블 스캔 → 인덱스 참조 |
| key | NULL | idx_products_brand_id_likes | 사용 가능한 인덱스 없음 → 복합 인덱스 사용 |
| rows | 98,671 | 18,816 | 스캔 행 수 약 80% 감소 |
| filtered | 10.00% | 100.00% | 불필요한 행 필터링 제거 |
| Extra | Using where; Using filesort | NULL | WHERE 필터링 + 정렬 연산 모두 제거 |

### 핵심 개선 포인트

1. **풀 테이블 스캔 제거**: 10만 건 전체를 읽던 것이 `brand_id = 1`에 해당하는 행만 읽음
2. **filesort 제거**: `likes` 컬럼이 인덱스 후행 컬럼에 포함되어 별도 정렬 연산 불필요
3. **filtered 100%**: 인덱스에서 읽은 행 전부가 결과에 사용됨 (불필요한 필터링 없음)

## 복합 인덱스 설계 원칙

복합 인덱스의 컬럼 순서는 쿼리 패턴에 따라 결정한다.

```
(동등 조건 컬럼, 정렬 컬럼)
 ↑ WHERE =          ↑ ORDER BY
```

- **선두 컬럼**: WHERE 절의 동등 조건(=)에 사용되는 컬럼 → 범위를 좁힘
- **후행 컬럼**: ORDER BY에 사용되는 컬럼 → 이미 정렬된 상태로 저장되어 filesort 제거
