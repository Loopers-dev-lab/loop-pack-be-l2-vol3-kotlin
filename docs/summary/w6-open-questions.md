# 6주차: 아직 해결하지 못한 질문들

---

### 1. 보상 트랜잭션이 실패하면 누가 책임지는가?

현재 `restoreOrderResources()`는 try-catch로 로그만 남긴다. 재고는 차감되었고, 결제는 실패했고, 주문 취소도 실패했다. 이 상태를 누가 발견하고, 누가 고치는가?

- retry + DLQ + reconciliation batch + admin 개입까지 설계해야 하는가?
- 이 체인 중 어디까지가 "코드로 자동화"하고, 어디부터가 "사람이 개입"하는 영역인가?

---

### 2. 이벤트를 여러 서비스가 소비할 때, 하나만 실패하면 어떻게 되는가?

지금은 모놀리스라서 주문 취소 → 재고 복원 → 쿠폰 복구가 한 프로세스 안에서 일어난다. 만약 이것이 각각 다른 서비스였다면?

- 결제 실패 이벤트를 재고 서비스, 쿠폰 서비스, 주문 서비스가 각각 소비
- 재고는 복원됐는데 쿠폰 복구가 실패 → 어떤 서비스가 이 불일치를 감지하는가?
- SAGA와 Outbox 패턴 중 어떤 것이 이 문제에 더 적합한가?

### 3. 콜백 엔드포인트의 보안을 어떻게 확보하는가?

현재 `/internal/v1/payments/callback`은 **인증 없이 누구나 호출 가능**하다. 악의적인 요청이 가짜 SUCCESS 콜백을 보내면 결제 상태가 조작된다.

- IP 화이트리스트? HMAC 서명? 콜백 수신 후 PG에 재조회?
- PG사마다 보안 방식이 다를 텐데, 우리 코드는 어디까지 범용적으로 설계해야 하는가?

---

### 4. CircuitBreaker가 열렸을 때 사용자 경험은 어떻게 되는가?

CB OPEN 상태에서 결제 요청이 오면 즉시 fallback → PENDING 반환. 이것이 30초간 지속된다.

- 이 30초 동안 모든 결제 요청이 transactionKey 없이 PENDING → 10분 후 스케줄러가 전부 FAILED 처리
- PG가 5초 만에 복구되었더라도, CB는 30초간 열려 있음 → 불필요한 결제 실패가 대량 발생
- CB 파라미터(waitDuration, halfOpenCalls)의 최적값을 어떤 기준으로 정하는가?

---

### 5. 스케줄러가 단일 인스턴스에서만 안전한 문제를 어떻게 해결하는가?

`PendingPaymentScheduler`는 `@Scheduled(fixedDelay = 60_000)`로 동작한다. 서버가 2대 이상이면?

- 같은 PENDING 결제를 두 인스턴스가 동시에 처리 → PG에 중복 조회 → 상태 전이 충돌
- ShedLock, Quartz, 또는 DB 기반 분산 락이 필요한가?
- 아니면 스케줄러를 아예 별도 배치 인스턴스로 분리하는 것이 맞는가?

---

현재 테스트가 커버하지 못하는 것들:

- 동일 콜백이 **동시에 2건** 도착했을 때 race condition이 없는가?
- 스케줄러와 콜백이 **동시에** 같은 결제를 처리하면 어떻게 되는가?
- PG 요청은 성공했는데 **TX-2(transactionKey 저장)가 실패**하면?
